# `lock()` 方法

# 一、方法定义

```java
void lock();
```

最基本的使用方式：

```java
ReentrantLock lock = new ReentrantLock();

lock.lock();

try {
    // 访问共享资源
} finally {
    lock.unlock();
}
```

`lock()` 的作用是：

> 当前线程尝试获取这把 `ReentrantLock`。如果锁暂时被其他线程持有，当前线程就等待，直到成功获得锁后，`lock()` 方法才会返回。

------

# 二、lock() 的四种基本情况

当前线程执行：

```java
lock.lock();
```

大致会遇到四种情况。

## 情况一：锁当前空闲

假设：

```text
state = 0
owner = null
```

说明没有任何线程持有锁。

此时线程 A 调用：

```java
lock.lock();
```

线程 A 可以直接尝试获得锁。

成功后：

```text
state = 1
owner = Thread-A
```

然后 `lock()` 返回，线程 A 继续执行临界区代码。

```text
Thread-A 调用 lock()
        ↓
发现锁空闲
        ↓
成功获得锁
        ↓
lock() 返回
        ↓
执行临界区
```

------

## 情况二：锁已经被当前线程自己持有

假设：

```text
state = 1
owner = Thread-A
```

线程 A 再次调用：

```java
lock.lock();
```

因为持锁线程就是当前线程，所以允许重入。

状态变化：

```text
state：1 → 2
owner：仍然是 Thread-A
```

这时第二次 `lock()` 也会立即返回，不会阻塞自己。

例如：

```java
lock.lock();

try {
    System.out.println("第一次获得锁");

    lock.lock();

    try {
        System.out.println("第二次获得同一把锁");
    } finally {
        lock.unlock();
    }
} finally {
    lock.unlock();
}
```

执行过程：

```text
第一次 lock()：
state = 1

第二次 lock()：
state = 2

第一次 unlock()：
state = 1

第二次 unlock()：
state = 0
锁真正释放
```

所以：

> 同一个线程可以多次调用 `lock()`，但成功加锁多少次，就必须执行多少次 `unlock()`。

------

## 情况三：锁被其他线程持有

假设：

```text
state = 1
owner = Thread-A
```

线程 B 调用：

```java
lock.lock();
```

线程 B 发现：

```text
当前线程 = Thread-B
持锁线程 = Thread-A
```

两者不是同一个线程，因此 B 不能获得锁，也不能发生重入。

此时线程 B 会进入 AQS 的同步等待流程。

可以简化理解为：

```text
Thread-B 尝试获得锁
        ↓
锁被 Thread-A 持有
        ↓
获取失败
        ↓
进入 AQS 同步队列
        ↓
可能被 park 挂起
        ↓
等待前面的线程释放锁
```

注意：

> `lock()` 不会因为第一次获取失败就返回，它会一直等待，直到最终获得锁。

------

## 情况四：当前线程已经在等待队列中

假设当前同步队列是：

```text
head → Thread-B → Thread-C
```

其中：

```text
Thread-B：队首等待线程
Thread-C：排在 B 后面
```

当持锁线程释放锁时，AQS 通常会唤醒合适的后继线程。

此时：

```text
Thread-B 被唤醒
        ↓
重新尝试获取锁
        ↓
成功：离开等待队列
失败：继续等待
```

被唤醒并不代表已经获得锁。

正确理解是：

```text
被唤醒
≠
获得锁
```

而是：

```text
被唤醒
=
获得了重新尝试获取锁的机会
```

------

# 三、lock() 的标准使用模板

必须使用：

```java
lock.lock();

try {
    // 临界区
} finally {
    lock.unlock();
}
```

例如：

```java
public class Counter {

    private int count;

    private final ReentrantLock lock =
            new ReentrantLock();

    public void increment() {
        lock.lock();

        try {
            count++;
        } finally {
            lock.unlock();
        }
    }

    public int getCount() {
        lock.lock();

        try {
            return count;
        } finally {
            lock.unlock();
        }
    }
}
```

------

# 四、为什么 lock() 要写在 try 外面

推荐写法：

```java
lock.lock();

try {
    // 临界区
} finally {
    lock.unlock();
}
```

一般不推荐写成：

```java
try {
    lock.lock();
    // 临界区
} finally {
    lock.unlock();
}
```

核心原因是：

> `finally` 中的 `unlock()` 只能在当前线程已经成功持有锁时执行。

对于普通 `lock()` 来说，它通常会一直等到成功获得锁才返回，因此放进 `try` 在很多情况下也能运行。

但统一采用：

```java
lock.lock();
try {
} finally {
    lock.unlock();
}
```

有几个好处：

1. 结构清楚；
2. 明确表示进入 `try` 时已经持锁；
3. 与 `lockInterruptibly()`、`tryLock()` 的复杂场景更容易区分；
4. 避免把“获取锁”和“释放已获取的锁”混在同一个异常结构中。

最推荐记忆：

```text
先成功 lock
再进入 try
最后 finally unlock
```

------

# 五、为什么 unlock() 必须放在 finally 中

错误写法：

```java
lock.lock();

doSomething();

lock.unlock();
```

假设：

```java
private void doSomething() {
    throw new RuntimeException("执行失败");
}
```

那么程序执行到：

```java
doSomething();
```

时抛出异常，后面的：

```java
lock.unlock();
```

不会执行。

于是：

```text
state 一直大于 0
owner 一直是当前线程
其他线程一直无法获得锁
```

正确写法：

```java
lock.lock();

try {
    doSomething();
} finally {
    lock.unlock();
}
```

即使临界区抛出异常，`finally` 仍会执行，从而释放锁。

------

# 六、lock() 获取不到锁时会发生什么

假设线程 A 持有锁：

```java
lock.lock();

try {
    Thread.sleep(5000);
} finally {
    lock.unlock();
}
```

此时线程 B 调用：

```java
lock.lock();
```

线程 B 不会：

```text
返回 false
```

也不会：

```text
抛出获取锁失败异常
```

而是会等待。

大致流程：

```text
1. 尝试获得锁
2. 获取失败
3. 加入 AQS 同步队列
4. 判断自己是否有资格继续尝试
5. 不满足条件时 park 挂起
6. 前面线程释放锁
7. 当前线程被唤醒
8. 再次尝试获得锁
9. 成功后 lock() 返回
```

因此：

```java
lock.lock();
```

本质上是一个可能阻塞当前线程的方法。

它等待多久没有固定上限。

如果持锁线程永远不释放锁，当前线程理论上可能永远等待。

------

# 七、lock() 和 AQS 同步队列

假设线程 A 当前持有锁。

线程 B、C 先后调用：

```java
lock.lock();
```

它们都获取失败，进入同步队列：

```text
head → B → C
```

这里可以理解为：

```text
B 比 C 更早等待
```

但是否严格按照：

```text
B → C
```

获得锁，要区分公平锁和非公平锁。

------

# 八、非公平锁中的 lock()

默认创建方式：

```java
ReentrantLock lock = new ReentrantLock();
```

等价于：

```java
ReentrantLock lock = new ReentrantLock(false);
```

这是非公平锁。

假设当前情况：

```text
Thread-A 持有锁

同步队列：
head → Thread-B → Thread-C
```

这时新线程 D 调用：

```java
lock.lock();
```

当 A 释放锁时，可能发生：

```text
Thread-B：
已经排在队首，被唤醒后准备获取锁

Thread-D：
刚刚到来，直接尝试抢锁
```

此时主要有资格竞争的是：

```text
队首线程 B
+
队列外新来的线程 D
```

D 可能插队成功。

例如：

```text
A 释放锁
    ↓
B 还没有获得 CPU
    ↓
D 正在运行
    ↓
D 直接 CAS 成功
    ↓
D 获得锁
```

此时队列仍可能是：

```text
head → B → C
```

B 和 C 继续等待。

因此：

> 非公平锁虽然有同步队列，但新来的线程仍然可以插队竞争。

------

# 九、队列中的 C 能不能越过 B

假设：

```text
head → B → C
```

正常情况下，C 不能直接越过 B 抢锁。

原因是：

> 对于已经进入 AQS 同步队列的线程，一般只有队首有效等待节点，也就是前驱为 `head` 的线程，才有资格尝试获取锁。

对于 B：

```text
B 的前驱 = head
```

所以 B 可以尝试获取。

对于 C：

```text
C 的前驱 = B
```

所以 C 通常不能直接竞争锁。

因此非公平锁并不是：

```text
B、C、D 所有人一起随便抢
```

而更接近：

```text
队首线程 B
和
队列外新来的线程 D
进行竞争
```

C 需要等待 B：

```text
成功获取锁并离开队列
```

或者：

```text
因中断、超时等原因取消等待
```

C 才能向前成为新的队首候选线程。

------

# 十、公平锁中的 lock()

公平锁创建方式：

```java
ReentrantLock lock = new ReentrantLock(true);
```

假设：

```text
head → B → C
```

此时新线程 D 调用：

```java
lock.lock();
```

D 会检查：

```text
自己前面是否已经有线程排队
```

发现前面有 B、C，D 就不能直接插队，而是进入队尾：

```text
head → B → C → D
```

之后通常按照：

```text
B → C → D
```

获得锁。

公平锁的逻辑可以简化为：

```java
if (state == 0
        && !hasQueuedPredecessors()
        && compareAndSetState(0, 1)) {
    // 当前线程获得锁
}
```

其中：

```java
hasQueuedPredecessors()
```

可以理解为：

> 当前线程前面是否已经有其他等待线程。

所以公平锁的 `lock()` 更接近：

```text
前面有人：
先排队

前面没人：
尝试获得锁
```

------

# 十一、公平锁也不是绝对的“线程执行公平”

即使使用：

```java
new ReentrantLock(true);
```

也不能保证：

```text
线程启动顺序
=
获得锁顺序
=
程序执行结束顺序
```

因为线程能否及时运行，还受到操作系统调度影响。

公平锁保证的是：

> 在存在排队线程时，新线程通常不能直接插队。

它不是对整个线程调度系统进行绝对排序。

------

# 十二、lock() 被中断会怎样

`lock()` 方法没有声明：

```java
throws InterruptedException
```

因此不能这样写：

```java
try {
    lock.lock();
} catch (InterruptedException e) {
    // 编译错误
}
```

假设线程 B 正在等待锁：

```java
Thread threadB = new Thread(() -> {
    lock.lock();

    try {
        System.out.println("Thread-B 获得锁");
    } finally {
        lock.unlock();
    }
});
```

另一个线程执行：

```java
threadB.interrupt();
```

B 不会因为这次中断立刻退出锁等待。

普通 `lock()` 的语义是：

> 即使等待过程中被中断，也不会取消本次获取锁的请求，仍会继续等待，直到成功获得锁。

可以简化理解为：

```text
等待 lock
    ↓
收到 interrupt
    ↓
不抛 InterruptedException
    ↓
继续等待锁
    ↓
最终获得锁
```

如果希望线程在等待锁时能够被中断并取消等待，应使用：

```java
lock.lockInterruptibly();
```

------

# 十三、lock() 与 lockInterruptibly() 的区别

## lock()

```java
lock.lock();
```

特点：

```text
获取不到锁就继续等待
等待期间中断不会取消获取
最终获得锁后才返回
```

## lockInterruptibly()

```java
lock.lockInterruptibly();
```

特点：

```text
获取不到锁就等待
等待期间可以响应中断
被中断后抛出 InterruptedException
放弃本次锁获取
```

对比：

| 方法                  | 获取不到锁 | 等待时被中断       |
| --------------------- | ---------- | ------------------ |
| `lock()`              | 一直等待   | 不取消获取         |
| `lockInterruptibly()` | 一直等待   | 抛出异常并取消获取 |

------

# 十四、lock() 与 tryLock() 的区别

## lock()

```java
lock.lock();
```

拿不到就等待：

```text
必须获得锁以后才返回
```

## tryLock()

```java
boolean acquired = lock.tryLock();
```

拿不到立即返回：

```text
获得锁：true
没有获得锁：false
```

对比：

| 方法        | 锁被占用时 | 返回值    |
| ----------- | ---------- | --------- |
| `lock()`    | 阻塞等待   | `void`    |
| `tryLock()` | 立即返回   | `boolean` |

例如：

```java
if (!lock.tryLock()) {
    System.out.println("没有获得锁，执行降级逻辑");
    return;
}

try {
    // 临界区
} finally {
    lock.unlock();
}
```

------

# 十五、lock() 的简化底层逻辑

可以把 `lock()` 的核心过程简化成：

```java
public void lock() {
    if (尝试获取锁成功) {
        return;
    }

    加入AQS同步队列();

    while (没有获得锁) {
        判断是否需要挂起();

        if (需要挂起) {
            LockSupport.park();
        }

        被唤醒后重新尝试获取锁();
    }
}
```

这不是完整源码，只用于理解整体逻辑。

核心过程是：

```text
先尝试
    ↓
失败后排队
    ↓
条件合适时挂起
    ↓
被唤醒
    ↓
重新尝试
```

------

# 十六、非公平 lock() 的简化流程

默认非公平锁可以简化为：

```text
当前线程调用 lock()
        ↓
先直接尝试 CAS 抢锁
        ↓
成功：
记录 owner，lock() 返回
        ↓
失败：
进入 AQS 获取流程
        ↓
当前线程是 owner：
state++，完成重入
        ↓
否则：
加入同步队列等待
```

简化伪代码：

```java
void lock() {
    if (compareAndSetState(0, 1)) {
        setExclusiveOwnerThread(
                Thread.currentThread()
        );
    } else {
        acquire(1);
    }
}
```

实际实现会根据 JDK 版本存在细节差异，但核心思想一致：

> 非公平锁会优先直接尝试抢锁，失败后再排队。

------

# 十七、公平 lock() 的简化流程

公平锁不会只因为：

```text
state = 0
```

就直接获得锁。

它还要判断：

```text
前面有没有排队线程
```

简化流程：

```text
锁是否空闲？
    ↓
不是：
进入等待

是：
检查前面是否有排队线程
    ↓
有：
不能插队，进入等待

没有：
执行 CAS 抢锁
```

简化伪代码：

```java
if (state == 0) {
    if (!hasQueuedPredecessors()
            && compareAndSetState(0, 1)) {

        setExclusiveOwnerThread(current);
        return true;
    }
}
```

------

# 十八、lock() 是否会一直占用 CPU

不会简单地一直疯狂循环。

获取锁失败的线程通常会经历：

```text
短暂检查和竞争
    ↓
进入同步队列
    ↓
LockSupport.park()
```

执行 `park()` 后，线程会暂停运行，不再持续消耗 CPU 进行无意义竞争。

锁释放时，AQS 会让合适的等待线程恢复运行：

```text
unlock()
    ↓
找到合适的后继线程
    ↓
LockSupport.unpark(thread)
```

但再次强调：

```text
unpark
≠
直接获得锁
```

被唤醒线程仍然需要重新执行获取判断。

------

# 十九、持有 lock 时不要执行长时间操作

例如：

```java
lock.lock();

try {
    Thread.sleep(10_000);
} finally {
    lock.unlock();
}
```

`sleep()` 不会释放 `ReentrantLock`。

这十秒内，其他线程无法获得锁。

同样不建议在持锁期间执行：

```text
长时间数据库查询
远程接口调用
文件上传下载
复杂网络请求
大量无关计算
人为 sleep
```

不推荐：

```java
lock.lock();

try {
    Result result = remoteService.call();
    sharedData = result;
} finally {
    lock.unlock();
}
```

更合理：

```java
Result result = remoteService.call();

lock.lock();

try {
    sharedData = result;
} finally {
    lock.unlock();
}
```

原则：

> 只把必须保持原子性和一致性的共享资源操作放进锁内。

------

# 二十、lock() 是否能够防止死锁

不能。

`ReentrantLock` 本身只是提供锁机制，并不会自动防止多个锁之间形成循环等待。

例如：

```text
Thread-A：
先获得 lock1
再等待 lock2

Thread-B：
先获得 lock2
再等待 lock1
```

形成：

```text
Thread-A 等 Thread-B
Thread-B 等 Thread-A
```

两边都使用普通 `lock()` 时，可能永远等待。

解决方式包括：

```text
固定多把锁的获取顺序
使用 tryLock(timeout)
减少嵌套锁
缩小锁范围
重新设计共享资源结构
```

------

# 二十一、lock() 常见错误

## 错误一：忘记解锁

```java
lock.lock();

// 执行业务
```

结果：

```text
锁永远被当前线程持有
```

------

## 错误二：不在 finally 中解锁

```java
lock.lock();

doSomething();

lock.unlock();
```

业务抛异常时无法解锁。

------

## 错误三：加锁两次只解锁一次

```java
lock.lock();
lock.lock();

try {
    // 临界区
} finally {
    lock.unlock();
}
```

最终：

```text
state = 1
```

锁仍未真正释放。

------

## 错误四：其他线程调用 unlock

```text
Thread-A 获得锁
Thread-B 调用 unlock()
```

会抛出：

```text
IllegalMonitorStateException
```

------

## 错误五：认为进入队列后所有线程一起抢

假设：

```text
head → B → C
```

正常情况下：

```text
B 是队首候选线程
C 不能直接越过 B
```

非公平主要是允许队列外的新线程插队，不是允许队列中的后续节点随便越级。

------

## 错误六：认为被唤醒就获得了锁

```text
unpark
```

只表示线程可以重新运行。

它仍然要再次尝试获取锁。

------

## 错误七：认为 sleep 会释放锁

```java
lock.lock();

try {
    Thread.sleep(1000);
} finally {
    lock.unlock();
}
```

`sleep()` 期间仍然持有锁。

------

# 二十二、完整演示示例

```java
import java.util.concurrent.locks.ReentrantLock;

public class LockDemo {

    private static final ReentrantLock LOCK =
            new ReentrantLock();

    public static void main(String[] args)
            throws InterruptedException {

        Thread threadA = new Thread(
                () -> execute("Thread-A"),
                "Thread-A"
        );

        Thread threadB = new Thread(
                () -> execute("Thread-B"),
                "Thread-B"
        );

        threadA.start();

        Thread.sleep(100);

        threadB.start();
    }

    private static void execute(String threadName) {
        System.out.println(
                threadName + " 准备获取锁"
        );

        LOCK.lock();

        try {
            System.out.println(
                    threadName + " 成功获得锁"
            );

            Thread.sleep(2000);

            System.out.println(
                    threadName + " 执行完成"
            );
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            LOCK.unlock();

            System.out.println(
                    threadName + " 释放锁"
            );
        }
    }
}
```

可能输出：

```text
Thread-A 准备获取锁
Thread-A 成功获得锁
Thread-B 准备获取锁
Thread-A 执行完成
Thread-A 释放锁
Thread-B 成功获得锁
Thread-B 执行完成
Thread-B 释放锁
```

Thread-B 调用 `lock()` 后，会停在获取锁的位置。

只有 Thread-A 执行：

```java
LOCK.unlock();
```

之后，Thread-B 才有机会获得锁并让自己的 `lock()` 返回。

# 二十三、完整流程图

```text
线程调用 lock()
        ↓
当前锁是否空闲？
        │
        ├── 是
        │    ↓
        │  尝试 CAS 获取锁
        │    │
        │    ├── 成功
        │    │    ↓
        │    │  state = 1
        │    │  owner = 当前线程
        │    │    ↓
        │    │  lock() 返回
        │    │
        │    └── 失败
        │         ↓
        │       进入 AQS 获取流程
        │
        └── 否
             ↓
        owner 是否为当前线程？
             │
             ├── 是
             │    ↓
             │  state++
             │    ↓
             │  重入成功
             │    ↓
             │  lock() 返回
             │
             └── 否
                  ↓
              加入同步队列
                  ↓
              必要时 park
                  ↓
              等待被唤醒
                  ↓
              重新尝试获取
                  ↓
              成功后 lock() 返回
```

# 二十四、最终记忆

```text
lock()：
必须获得锁后才返回

锁空闲：
直接尝试获得

当前线程已经持锁：
允许重入，state++

其他线程持锁：
进入 AQS 同步等待流程

普通 lock() 等待时被中断：
不会取消获取，不抛 InterruptedException

非公平锁：
队列外新线程可以插队

公平锁：
尽量按照等待队列顺序获取

被唤醒：
只是重新获得竞争资格

成功 lock 几次：
就必须 unlock 几次
```

一句话总结：

> `lock()` 会让当前线程持续尝试获取锁；锁空闲时直接获取，当前线程已经持锁时进行重入，其他线程持锁时进入 AQS 同步队列等待，直到最终成功获得锁后才返回。

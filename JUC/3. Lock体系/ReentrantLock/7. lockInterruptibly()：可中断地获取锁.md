# `lockInterruptibly()`：可中断地获取锁

## 1. 方法定义

```java
void lockInterruptibly() throws InterruptedException;
```

使用方式：

```java
lock.lockInterruptibly();
```

它的作用是：

> 当前线程尝试获取锁。如果锁被其他线程持有，当前线程会进入等待；但在等待锁的过程中，可以通过中断取消本次锁获取。

因此，`lockInterruptibly()` 与普通 `lock()` 最大的区别是：

```text
lock()：
等待锁时，中断不会取消获取锁

lockInterruptibly()：
等待锁时，可以通过中断放弃获取锁
```

------

## 2. 基本使用模板

```java
boolean locked = false;

try {
    lock.lockInterruptibly();
    locked = true;

    // 临界区
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    if (locked) {
        lock.unlock();
    }
}
```

这里需要注意两个重点：

```text
1. lockInterruptibly() 可能抛出 InterruptedException
2. 只有真正获得锁以后，才能执行 unlock()
```

因此通常需要使用：

```java
boolean locked = false;
```

记录当前线程是否已经成功获得锁。

------

## 3. 为什么需要 `locked` 变量

假设线程 A 持有锁，线程 B 执行：

```java
lock.lockInterruptibly();
```

线程 B 还没有获得锁时，被其他线程中断：

```java
threadB.interrupt();
```

此时 `lockInterruptibly()` 会直接抛出：

```java
InterruptedException
```

线程 B 并没有获得锁。

如果这样写：

```java
try {
    lock.lockInterruptibly();

    // 临界区
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    lock.unlock();
}
```

那么即使线程没有获得锁，`finally` 仍然会执行：

```java
lock.unlock();
```

由于当前线程不是锁的持有者，会抛出：

```text
IllegalMonitorStateException
```

所以需要判断是否真正获得了锁：

```java
boolean locked = false;

try {
    lock.lockInterruptibly();
    locked = true;

    // 临界区
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    if (locked) {
        lock.unlock();
    }
}
```

执行过程可以理解为：

```text
lockInterruptibly() 成功返回
        ↓
locked = true
        ↓
finally 中可以 unlock()
```

如果在等待锁时被中断：

```text
lockInterruptibly() 抛出异常
        ↓
locked 仍然是 false
        ↓
finally 中不执行 unlock()
```

------

## 4. 锁空闲时的执行过程

假设当前锁状态为：

```text
state = 0
owner = null
```

线程 A 调用：

```java
lock.lockInterruptibly();
```

线程 A 可以直接尝试获得锁。

成功后：

```text
state = 1
owner = Thread-A
```

然后：

```java
lock.lockInterruptibly();
```

正常返回。

执行流程：

```text
Thread-A 调用 lockInterruptibly()
                ↓
发现锁空闲
                ↓
成功获得锁
                ↓
方法正常返回
                ↓
执行临界区
```

在锁空闲并且立即获取成功的情况下，它与普通 `lock()` 的效果基本相同。

------

## 5. 当前线程已经持锁时

`lockInterruptibly()` 同样支持可重入。

假设：

```text
state = 1
owner = Thread-A
```

Thread-A 再次执行：

```java
lock.lockInterruptibly();
```

因为当前线程就是持锁线程，所以会直接重入：

```text
state：1 → 2
owner：仍然是 Thread-A
```

不会进入等待，也不会阻塞。

例如：

```java
lock.lock();

try {
    System.out.println("第一次获得锁");

    lock.lockInterruptibly();

    try {
        System.out.println("第二次获得锁");
    } finally {
        lock.unlock();
    }
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    lock.unlock();
}
```

成功执行时：

```text
第一次加锁：
state = 1

第二次加锁：
state = 2

第一次解锁：
state = 1

第二次解锁：
state = 0
```

------

## 6. 锁被其他线程持有时

假设：

```text
state = 1
owner = Thread-A
```

此时 Thread-B 执行：

```java
lock.lockInterruptibly();
```

Thread-B 无法获得锁，会进入 AQS 同步等待流程：

```text
Thread-B 尝试获得锁
        ↓
发现锁被 Thread-A 持有
        ↓
获取失败
        ↓
进入 AQS 同步队列
        ↓
可能被 park 挂起
        ↓
等待锁释放或线程被中断
```

Thread-B 在等待过程中，存在两种主要结果。

### 结果一：成功获得锁

Thread-A 释放锁：

```java
lock.unlock();
```

Thread-B 被唤醒并重新尝试获取。

如果成功：

```text
state = 1
owner = Thread-B
```

随后：

```java
lock.lockInterruptibly();
```

正常返回。

------

### 结果二：等待过程中被中断

另一个线程执行：

```java
threadB.interrupt();
```

Thread-B 会取消本次锁获取，并抛出：

```java
InterruptedException
```

执行流程：

```text
Thread-B 正在等待锁
        ↓
其他线程调用 threadB.interrupt()
        ↓
Thread-B 响应中断
        ↓
取消锁等待
        ↓
从 AQS 同步队列中取消节点
        ↓
抛出 InterruptedException
```

所以：

> `lockInterruptibly()` 使线程不必无限等待一把暂时拿不到的锁。

------

## 7. 与 `lock()` 的中断区别

假设 Thread-A 长时间持有锁，Thread-B 正在等待。

### 使用 `lock()`

```java
lock.lock();
```

其他线程执行：

```java
threadB.interrupt();
```

Thread-B 不会因为这次中断放弃获取锁。

它仍然会继续等待：

```text
等待锁
    ↓
收到中断
    ↓
不抛 InterruptedException
    ↓
继续等待
    ↓
最终获得锁
```

------

### 使用 `lockInterruptibly()`

```java
lock.lockInterruptibly();
```

其他线程执行：

```java
threadB.interrupt();
```

Thread-B 会退出等待：

```text
等待锁
    ↓
收到中断
    ↓
取消锁获取
    ↓
抛出 InterruptedException
```

对比：

| 方法                  | 等待锁时能否被中断取消 | 是否抛出 `InterruptedException` |
| --------------------- | ---------------------- | ------------------------------- |
| `lock()`              | 否                     | 否                              |
| `lockInterruptibly()` | 是                     | 是                              |

可以这样记：

```text
lock()：
我一定要拿到这把锁

lockInterruptibly()：
我要拿锁，但任务被取消时可以不等了
```

------

## 8. 如果调用前线程已经被中断

假设当前线程的中断标记已经是：

```text
true
```

然后执行：

```java
lock.lockInterruptibly();
```

即使锁当前可能可以获取，`lockInterruptibly()` 也会优先检查中断状态，并抛出：

```java
InterruptedException
```

例如：

```java
Thread.currentThread().interrupt();

try {
    lock.lockInterruptibly();
} catch (InterruptedException e) {
    System.out.println("线程进入方法前已经被中断");
}
```

因此：

> `lockInterruptibly()` 不只是等待过程中响应中断，进入方法时如果已经存在中断标记，也会响应中断。

这也是它与普通 `lock()` 的重要区别。

------

## 9. 捕获异常后为什么经常重新中断

常见写法：

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}
```

原因是：

> 抛出 `InterruptedException` 时，线程的中断标记通常会被清除。

也就是说：

```text
线程被中断
    ↓
抛出 InterruptedException
    ↓
中断标记被清除
```

如果当前方法无法完整处理这次中断，通常应该重新设置：

```java
Thread.currentThread().interrupt();
```

这样上层代码还能通过：

```java
Thread.currentThread().isInterrupted()
```

知道线程曾经被要求中断。

例如：

```java
public void execute() {
    boolean locked = false;

    try {
        lock.lockInterruptibly();
        locked = true;

        doSomething();
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        return;
    } finally {
        if (locked) {
            lock.unlock();
        }
    }
}
```

不过，是否重新中断取决于当前方法的职责。

如果当前方法决定：

```text
我就在这里完整处理这次中断
```

也可以不重新设置。

但在普通业务方法、线程池任务或工具方法中，通常不应该悄悄吞掉中断。

------

## 10. 不要空着捕获中断异常

错误写法：

```java
try {
    lock.lockInterruptibly();
} catch (InterruptedException e) {
}
```

这相当于：

```text
线程已经收到取消或停止信号
        ↓
代码什么也不做
        ↓
上层也不知道发生过中断
```

这种行为通常叫：

> 吞掉中断。

更合理的方式主要有两种。

### 方式一：继续向上抛

```java
public void execute() throws InterruptedException {
    lock.lockInterruptibly();

    try {
        // 临界区
    } finally {
        lock.unlock();
    }
}
```

让调用方决定如何处理中断。

------

### 方式二：重新设置中断标记

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;
}
```

表示当前方法结束执行，但保留中断信息。

------

## 11. 最简洁的推荐模板

如果当前方法本身允许继续抛出异常，推荐写成：

```java
public void execute() throws InterruptedException {
    lock.lockInterruptibly();

    try {
        // 临界区
    } finally {
        lock.unlock();
    }
}
```

这里不需要 `locked` 变量。

原因是：

```text
lockInterruptibly() 成功：
才会进入后面的 try

lockInterruptibly() 被中断：
直接向上抛异常，不会进入 try
```

所以一旦进入 `try`，就说明当前线程已经成功获得锁。

------

## 12. 什么时候需要 `locked` 变量

当你需要在当前方法中捕获异常，并在同一个 `finally` 中判断是否解锁时，可以使用：

```java
boolean locked = false;
```

例如：

```java
public void execute() {
    boolean locked = false;

    try {
        lock.lockInterruptibly();
        locked = true;

        // 临界区
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    } finally {
        if (locked) {
            lock.unlock();
        }
    }
}
```

不过也可以通过嵌套结构，避免使用变量：

```java
public void execute() {
    try {
        lock.lockInterruptibly();

        try {
            // 临界区
        } finally {
            lock.unlock();
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}
```

这个结构表达得非常清楚：

```text
外层 try：
负责获取锁时可能发生的中断

内层 try-finally：
负责成功获得锁后的释放
```

## 13. 完整示例

```java
import java.util.concurrent.locks.ReentrantLock;

public class LockInterruptiblyDemo {

    private static final ReentrantLock LOCK =
            new ReentrantLock();

    public static void main(String[] args)
            throws InterruptedException {

        Thread threadA = new Thread(() -> {
            LOCK.lock();

            try {
                System.out.println(
                        "Thread-A 获得锁"
                );

                try {
                    Thread.sleep(10_000);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            } finally {
                LOCK.unlock();

                System.out.println(
                        "Thread-A 释放锁"
                );
            }
        }, "Thread-A");

        Thread threadB = new Thread(() -> {
            System.out.println(
                    "Thread-B 准备获取锁"
            );

            try {
                LOCK.lockInterruptibly();

                try {
                    System.out.println(
                            "Thread-B 获得锁"
                    );
                } finally {
                    LOCK.unlock();
                }
            } catch (InterruptedException e) {
                System.out.println(
                        "Thread-B 等待锁时被中断"
                );

                Thread.currentThread().interrupt();
            }
        }, "Thread-B");

        threadA.start();

        Thread.sleep(100);

        threadB.start();

        Thread.sleep(1000);

        System.out.println(
                "主线程中断 Thread-B"
        );

        threadB.interrupt();
    }
}
```

可能输出：

```text
Thread-A 获得锁
Thread-B 准备获取锁
主线程中断 Thread-B
Thread-B 等待锁时被中断
Thread-A 释放锁
```

可以看到：

```text
Thread-B 没有等到 Thread-A 释放锁
```

它在收到中断后，直接取消了锁获取。

如果 Thread-B 使用的是：

```java
LOCK.lock();
```

那么中断不会让它退出锁等待，它仍然会继续等待 Thread-A 释放锁。

## 14. 在死锁处理中有什么作用

假设两个线程分别持有不同的锁。

```text
Thread-A：
持有 lock1
等待 lock2

Thread-B：
持有 lock2
等待 lock1
```

如果双方都使用普通：

```java
lock();
```

可能会永远等待。

如果使用：

```java
lockInterruptibly();
```

管理线程可以中断其中一个等待线程：

```java
threadA.interrupt();
```

让它取消锁获取，并释放自己已经持有的其他锁，从而打破死锁。

例如：

```java
boolean firstLocked = false;
boolean secondLocked = false;

try {
    lock1.lockInterruptibly();
    firstLocked = true;

    lock2.lockInterruptibly();
    secondLocked = true;

    // 同时持有两把锁
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    if (secondLocked) {
        lock2.unlock();
    }

    if (firstLocked) {
        lock1.unlock();
    }
}
```

不过需要注意：

> `lockInterruptibly()` 只是让等待锁的线程可以被取消，并不会自动检测或自动解决死锁。

仍然需要其他代码决定：

```text
中断哪个线程
什么时候中断
中断后如何回滚业务
```

------

## 15. 公平锁与非公平锁中的行为

`lockInterruptibly()` 也会遵循当前 `ReentrantLock` 的公平策略。

### 非公平锁

```java
ReentrantLock lock =
        new ReentrantLock(false);
```

等待线程可以被中断。

同时，新来的线程仍可能插队竞争锁。

------

### 公平锁

```java
ReentrantLock lock =
        new ReentrantLock(true);
```

等待线程可以被中断。

同时，锁获取通常会遵循等待队列顺序，新来的线程不能随意插队。

所以：

```text
是否能够响应中断
```

和：

```text
是否按照公平策略获取锁
```

是两个不同维度。

```text
lockInterruptibly：
决定等待时能不能被中断

fair：
决定锁竞争是否尽量遵循排队顺序
```

------

## 16. 底层执行流程

可以把 `lockInterruptibly()` 简化理解为：

```java
public void lockInterruptibly()
        throws InterruptedException {

    if (Thread.interrupted()) {
        throw new InterruptedException();
    }

    if (尝试获得锁成功) {
        return;
    }

    加入AQS同步队列();

    while (没有获得锁) {
        if (当前线程被中断) {
            取消等待节点();
            throw new InterruptedException();
        }

        if (需要挂起) {
            LockSupport.park();
        }

        被唤醒后重新尝试获得锁();
    }
}
```

这不是完整源码，只是帮助理解。

核心流程：

```text
调用 lockInterruptibly()
        ↓
先检查中断状态
        ↓
尝试获得锁
        │
        ├── 成功
        │    ↓
        │  方法返回
        │
        └── 失败
             ↓
        加入 AQS 同步队列
             ↓
        可能执行 park()
             ↓
      ┌──────┴────────┐
      │               │
锁被释放          线程被中断
      │               │
重新尝试获取      取消等待
      │               │
成功后返回        抛出异常
```

------

## 17. 被中断后，队列中的后续线程怎么办

假设同步队列是：

```text
head → Thread-B → Thread-C
```

Thread-B 使用：

```java
lock.lockInterruptibly();
```

等待过程中被中断。

Thread-B 会取消等待：

```text
head → B（取消）→ C
```

AQS 后续会跳过或清理取消节点，使 Thread-C 有机会成为新的队首候选线程：

```text
head → Thread-C
```

所以某个等待线程被中断，不会导致整个同步队列无法继续运行。

------

## 18. `interrupt()` 不会强制终止线程

执行：

```java
threadB.interrupt();
```

并不是强制杀死 Thread-B。

它的作用更接近：

> 向 Thread-B 发出一个中断请求。

Thread-B 是否停止，取决于它正在执行什么操作以及代码如何处理中断。

在 `lockInterruptibly()` 的等待过程中：

```text
interrupt()
    ↓
lockInterruptibly() 检测到中断
    ↓
抛出 InterruptedException
```

异常抛出后，Thread-B 仍然是一个正常线程。

它可以：

```text
结束任务
执行清理
返回线程池
继续执行其他逻辑
重新设置中断标记
```

因此：

```text
中断 ≠ 强制杀死线程
```

------

## 19. 适合使用的场景

`lockInterruptibly()` 适合以下场景：

```text
任务允许被取消
线程可能长时间等待锁
需要响应系统关闭
需要响应用户取消操作
需要打破可中断的锁等待
在线程池任务中需要及时停止
```

例如：

```java
public void processTask()
        throws InterruptedException {

    lock.lockInterruptibly();

    try {
        processSharedData();
    } finally {
        lock.unlock();
    }
}
```

上层可以通过：

```java
future.cancel(true);
```

或者：

```java
thread.interrupt();
```

通知任务停止等待锁。

------

## 20. 不适合使用的场景

如果业务要求：

> 这个操作无论如何都必须最终获得锁并完成，不能因为普通中断请求而放弃。

可以使用：

```java
lock.lock();
```

不过实际项目中仍需谨慎。

无限等待本身可能意味着：

- 持锁线程异常；
- 出现死锁；
- 临界区过长；
- 锁竞争严重；
- 任务无法正常退出。

## 21. 常见错误

### 错误一：无条件执行 unlock

```java
try {
    lock.lockInterruptibly();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    lock.unlock();
}
```

线程可能尚未获得锁。

------

### 错误二：吞掉中断

```java
catch (InterruptedException e) {
}
```

会让上层无法得知任务被要求中断。

------

### 错误三：捕获后继续执行临界区

```java
try {
    lock.lockInterruptibly();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}

sharedData++;
```

如果发生中断，当前线程根本没有获得锁，却继续访问共享资源。

正确写法：

```java
try {
    lock.lockInterruptibly();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;
}

try {
    sharedData++;
} finally {
    lock.unlock();
}
```

------

### 错误四：认为中断会自动释放已经持有的其他锁

假设线程已经获得：

```text
lock1
```

然后等待：

```text
lock2
```

此时中断只能让它放弃等待 `lock2`。

已经持有的 `lock1` 不会自动释放，仍然需要：

```java
finally {
    lock1.unlock();
}
```

------

### 错误五：认为 `interrupt()` 会杀死线程

中断只是协作式取消信号。

线程收到异常后如何处理，仍然由代码决定。

------

## 22. 与四种获取锁方式对比

| 方法                     | 获取不到锁时     | 是否响应中断 | 是否支持超时 | 返回结果         |
| ------------------------ | ---------------- | ------------ | ------------ | ---------------- |
| `lock()`                 | 一直等待         | 不取消获取   | 否           | 成功后返回       |
| `lockInterruptibly()`    | 一直等待         | 是           | 否           | 成功返回或抛异常 |
| `tryLock()`              | 立即返回         | 不等待       | 否           | `boolean`        |
| `tryLock(timeout, unit)` | 最多等待指定时间 | 是           | 是           | `boolean` 或异常 |

选择方式：

```text
必须拿到锁，普通中断不取消：
lock()

必须拿到锁，但任务可以取消：
lockInterruptibly()

拿不到立即放弃：
tryLock()

最多等待一段时间：
tryLock(timeout, unit)
```

## 23. 最终记忆

```text
lockInterruptibly()：
可中断地获取锁

锁空闲：
立即获得锁

当前线程已经持锁：
允许重入

其他线程持锁：
进入 AQS 同步队列等待

等待期间被中断：
取消锁获取
抛出 InterruptedException

进入方法前已经被中断：
同样抛出 InterruptedException

没有成功获得锁：
不能执行 unlock()

捕获 InterruptedException：
通常重新设置中断标记
```

一句话总结：

> `lockInterruptibly()` 与 `lock()` 一样会等待直到成功获得锁，但它允许线程在等待过程中响应中断，取消本次锁获取并抛出 `InterruptedException`，适合需要任务取消、系统关闭或避免线程无限等待的场景。

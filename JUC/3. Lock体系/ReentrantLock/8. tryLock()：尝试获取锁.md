# `tryLock(x)`：尝试获取锁

## 1. `tryLock()` 是什么

`ReentrantLock` 提供了两个 `tryLock()` 方法：

```java
boolean tryLock();
```

以及：

```java
boolean tryLock(long time, TimeUnit unit)
        throws InterruptedException;
```

它们的共同特点是：

> 尝试获取锁，并通过返回值告诉调用者是否成功。

返回值含义：

```text
true：
当前线程成功获得锁

false：
当前线程没有获得锁
```

它和普通 `lock()` 最大的区别是：

```text
lock()：
拿不到锁就一直等待，直到获得锁

tryLock()：
拿不到锁时，可以不一直等待
```

因此，`tryLock()` 适合以下场景：

```text
拿不到锁就放弃
拿不到锁就执行其他逻辑
不希望线程无限等待
希望设置最大等待时间
需要同时获取多把锁
希望降低死锁造成的无限阻塞风险
```

------

## 2. 两种 `tryLock()` 的区别

### 无参数 `tryLock()`

```java
boolean acquired = lock.tryLock();
```

特点：

```text
立即尝试获取锁

获取成功：
返回 true

获取失败：
立即返回 false

不会进入长时间等待
不会抛出 InterruptedException
```

可以理解成：

> 我现在试一下，能拿到就拿，拿不到就算了。

------

### 带超时时间的 `tryLock()`

```java
boolean acquired =
        lock.tryLock(3, TimeUnit.SECONDS);
```

特点：

```text
先立即尝试获取锁

如果没有获取到：
最多等待指定时间

等待期间获得锁：
返回 true

等待超时仍未获得锁：
返回 false

等待期间被中断：
抛出 InterruptedException
```

可以理解成：

> 我愿意等一会儿，但最多只等三秒。

------

## 3. 无参数 `tryLock()` 的基本使用方式

标准写法：

```java
if (lock.tryLock()) {
    try {
        // 临界区
    } finally {
        lock.unlock();
    }
} else {
    // 没有获得锁
}
```

也可以写成：

```java
boolean acquired = lock.tryLock();

if (!acquired) {
    System.out.println("没有获得锁");
    return;
}

try {
    // 临界区
} finally {
    lock.unlock();
}
```

必须记住：

> 只有 `tryLock()` 返回 `true`，当前线程才有资格执行 `unlock()`。

------

## 4. 无参数 `tryLock()` 的执行情况

当前线程执行：

```java
boolean acquired = lock.tryLock();
```

大致会遇到三种情况。

### 情况一：锁当前空闲

假设：

```text
state = 0
owner = null
```

线程 A 执行：

```java
boolean acquired = lock.tryLock();
```

线程 A 会立即尝试获取锁。

成功后：

```text
state = 1
owner = Thread-A
acquired = true
```

执行过程：

```text
Thread-A 调用 tryLock()
        ↓
发现锁空闲
        ↓
CAS 获取锁成功
        ↓
返回 true
```

------

### 情况二：锁已经被当前线程持有

假设：

```text
state = 1
owner = Thread-A
```

Thread-A 再次执行：

```java
boolean acquired = lock.tryLock();
```

因为 `ReentrantLock` 支持可重入，所以会成功重入：

```text
state：1 → 2
owner：仍然是 Thread-A
acquired = true
```

因此：

> `tryLock()` 不只是尝试首次加锁，也支持当前持锁线程重入。

例如：

```java
lock.lock();

try {
    System.out.println(lock.getHoldCount());

    if (lock.tryLock()) {
        try {
            System.out.println(lock.getHoldCount());
        } finally {
            lock.unlock();
        }
    }
} finally {
    lock.unlock();
}
```

输出：

```text
1
2
```

------

### 情况三：锁被其他线程持有

假设：

```text
state = 1
owner = Thread-A
```

Thread-B 执行：

```java
boolean acquired = lock.tryLock();
```

Thread-B 会立即尝试一次。

由于锁被 Thread-A 持有，所以获取失败：

```text
acquired = false
```

然后方法立即返回。

它不会：

```text
进入长时间等待
一直阻塞
等到 Thread-A 释放锁
抛出获取锁失败异常
```

执行过程：

```text
Thread-B 调用 tryLock()
        ↓
发现锁被 Thread-A 持有
        ↓
立即获取失败
        ↓
返回 false
        ↓
Thread-B 执行其他逻辑
```

------

## 5. `tryLock()` 与 `lock()` 的区别

### 使用 `lock()`

```java
lock.lock();
```

如果锁被占用：

```text
当前线程进入等待
        ↓
直到最终获得锁
        ↓
lock() 才返回
```

------

### 使用 `tryLock()`

```java
boolean acquired = lock.tryLock();
```

如果锁被占用：

```text
立即返回 false
```

对比：

| 方法        | 锁被其他线程持有时 | 返回结果         |
| ----------- | ------------------ | ---------------- |
| `lock()`    | 一直等待           | 成功获得锁后返回 |
| `tryLock()` | 立即返回           | `false`          |

可以这样记：

```text
lock()：
这把锁我必须拿到

tryLock()：
我先试一下，拿不到就算了
```

------

## 6. 为什么必须判断返回值

错误写法：

```java
lock.tryLock();

try {
    sharedData++;
} finally {
    lock.unlock();
}
```

问题在于：

```java
lock.tryLock();
```

可能返回：

```text
false
```

此时当前线程并没有获得锁，却继续：

```java
sharedData++;
```

不但失去了线程安全，而且最终执行：

```java
lock.unlock();
```

还会抛出：

```text
IllegalMonitorStateException
```

正确写法：

```java
boolean acquired = lock.tryLock();

if (!acquired) {
    return;
}

try {
    sharedData++;
} finally {
    lock.unlock();
}
```

所以：

> `tryLock()` 的返回值绝对不能忽略。

------

## 7. 为什么不能无条件在 `finally` 中解锁

错误写法：

```java
boolean acquired = false;

try {
    acquired = lock.tryLock();

    if (!acquired) {
        return;
    }

    // 临界区
} finally {
    lock.unlock();
}
```

即使执行：

```java
return;
```

`finally` 仍然会执行。

如果 `acquired` 是 `false`，当前线程没有锁，却调用了：

```java
lock.unlock();
```

会抛出异常。

正确写法：

```java
boolean acquired = false;

try {
    acquired = lock.tryLock();

    if (!acquired) {
        return;
    }

    // 临界区
} finally {
    if (acquired) {
        lock.unlock();
    }
}
```

不过对于无参数 `tryLock()`，通常更推荐这种结构：

```java
if (!lock.tryLock()) {
    return;
}

try {
    // 临界区
} finally {
    lock.unlock();
}
```

这样代码更加清晰。

------

## 8. 无参数 `tryLock()` 会不会进入 AQS 队列

通常不会。

调用：

```java
lock.tryLock();
```

本质上是一次立即获取尝试。

如果成功：

```text
直接获得锁
```

如果失败：

```text
直接返回 false
```

它不会像普通 `lock()` 那样：

```text
获取失败
    ↓
加入 AQS 同步队列
    ↓
park 挂起
    ↓
等待被唤醒
```

因此无参数 `tryLock()` 是一种：

> 非阻塞获取锁方式。

这里的“非阻塞”是指：

```text
不会因为锁被其他线程持有而长时间等待
```

但调用线程执行方法本身仍然需要极短时间完成状态检查和 CAS。

------

## 9. 无参数 `tryLock()` 与公平锁

这是非常重要的细节。

假设创建的是公平锁：

```java
ReentrantLock lock =
        new ReentrantLock(true);
```

当前等待队列为：

```text
head → Thread-B → Thread-C
```

此时新线程 D 执行：

```java
boolean acquired = lock.tryLock();
```

如果调用瞬间锁恰好空闲，Thread-D 仍然可能直接获取锁。

也就是说：

> 无参数 `tryLock()` 不遵守公平锁的排队策略。

即使：

```java
lock.isFair() == true
```

调用：

```java
lock.tryLock();
```

仍然允许插队。

可以理解为：

```text
公平锁的 lock()：
先检查前面有没有等待线程

无参数 tryLock()：
不管队列，立即尝试抢一次
```

因此可能出现：

```text
同步队列：
B → C

新线程 D 调用 tryLock()
        ↓
锁恰好空闲
        ↓
D 插队成功
```

------

## 10. 为什么公平锁中的 `tryLock()` 仍允许插队

因为无参数 `tryLock()` 的语义重点是：

> 立即尝试。

它希望快速得出结果：

```text
现在能拿到：
返回 true

现在拿不到：
返回 false
```

如果还要严格检查公平队列，会增加额外判断，也不符合这种快速尝试的设计目标。

所以必须记住：

```text
new ReentrantLock(true)
并不意味着所有获取方法都绝对公平
```

无参数：

```java
tryLock()
```

是一个特殊情况。

------

## 11. 带超时时间的 `tryLock()`

方法定义：

```java
boolean tryLock(long time, TimeUnit unit)
        throws InterruptedException;
```

例如：

```java
boolean acquired =
        lock.tryLock(3, TimeUnit.SECONDS);
```

表示：

> 当前线程最多等待三秒来获取锁。

可能结果包括：

```text
锁立即可用：
立即获得锁，返回 true

锁暂时不可用：
进入等待

三秒内锁被释放并成功获取：
返回 true

等待三秒仍然没有获取：
返回 false

等待期间被中断：
抛出 InterruptedException
```

------

## 12. 带超时 `tryLock()` 的标准模板

### 允许向上抛异常

```java
public void execute()
        throws InterruptedException {

    boolean acquired =
            lock.tryLock(3, TimeUnit.SECONDS);

    if (!acquired) {
        System.out.println("获取锁超时");
        return;
    }

    try {
        // 临界区
    } finally {
        lock.unlock();
    }
}
```

一旦进入：

```java
try {
    // 临界区
}
```

就说明：

```text
acquired = true
```

因此可以在 `finally` 中直接解锁。

------

### 在当前方法中捕获中断

```java
public void execute() {
    boolean acquired = false;

    try {
        acquired =
                lock.tryLock(
                        3,
                        TimeUnit.SECONDS
                );

        if (!acquired) {
            System.out.println("获取锁超时");
            return;
        }

        // 临界区
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    } finally {
        if (acquired) {
            lock.unlock();
        }
    }
}
```

这里需要：

```java
boolean acquired = false;
```

因为有三种情况：

```text
获得锁：
acquired = true

超时：
acquired = false

被中断：
可能根本没有获得锁
```

只有成功获取锁，才能解锁。

------

## 13. 带超时 `tryLock()` 的执行流程

假设 Thread-A 正在持有锁。

Thread-B 执行：

```java
boolean acquired =
        lock.tryLock(3, TimeUnit.SECONDS);
```

大致流程：

```text
Thread-B 尝试立即获取锁
        ↓
获取失败
        ↓
加入 AQS 同步队列
        ↓
计算剩余等待时间
        ↓
必要时 parkNanos()
        ↓
等待锁释放、中断或超时
```

随后有三种结果。

### 结果一：等待期间获得锁

```text
Thread-A 在三秒内释放锁
        ↓
Thread-B 被唤醒
        ↓
重新尝试获取锁
        ↓
获取成功
        ↓
返回 true
```

------

### 结果二：等待超时

```text
等待时间到达三秒
        ↓
Thread-A 仍然没有释放锁
        ↓
Thread-B 取消等待
        ↓
返回 false
```

超时不会抛出异常。

超时只是正常的失败结果：

```java
if (!acquired) {
    System.out.println("锁竞争太激烈，本次放弃");
}
```

------

### 结果三：等待期间被中断

其他线程执行：

```java
threadB.interrupt();
```

则：

```text
Thread-B 响应中断
        ↓
取消同步队列中的等待
        ↓
抛出 InterruptedException
```

因此带超时的 `tryLock()` 同时具备：

```text
可等待
可超时
可中断
```

------

## 14. 超时时间小于或等于零

例如：

```java
lock.tryLock(0, TimeUnit.SECONDS);
```

或者：

```java
lock.tryLock(-1, TimeUnit.SECONDS);
```

这种情况下不会真正等待。

它会立即尝试获取锁：

```text
成功：
返回 true

失败：
返回 false
```

不过它与无参数：

```java
lock.tryLock();
```

仍有重要区别：

```text
tryLock()：
不遵守公平策略

tryLock(0, unit)：
会按照当前锁的公平策略进行尝试
```

------

## 15. 公平锁中如何立即尝试但不插队

假设：

```java
ReentrantLock lock =
        new ReentrantLock(true);
```

如果希望：

```text
不长时间等待
并且
不违反公平排队规则
```

可以使用：

```java
boolean acquired =
        lock.tryLock(0, TimeUnit.SECONDS);
```

它基本不会等待，但在公平锁中会检查：

```text
当前线程前面是否已有等待线程
```

如果前面有线程，即使锁当前处于空闲瞬间，也不会插队。

对比：

| 方法                     | 是否等待         | 公平锁中是否允许插队 |
| ------------------------ | ---------------- | -------------------- |
| `tryLock()`              | 否               | 是                   |
| `tryLock(0, unit)`       | 基本不等待       | 否                   |
| `tryLock(timeout, unit)` | 最多等待指定时间 | 否                   |

------

## 16. 带超时 `tryLock()` 与公平锁

假设：

```java
ReentrantLock lock =
        new ReentrantLock(true);
```

同步队列：

```text
head → Thread-B → Thread-C
```

Thread-D 调用：

```java
lock.tryLock(3, TimeUnit.SECONDS);
```

Thread-D 不会像无参数 `tryLock()` 那样随意插队。

它会遵循公平策略：

```text
发现前面有 B、C
        ↓
D 进入队尾
        ↓
head → B → C → D
```

如果在三秒内轮到 D，并且 D 成功获得锁：

```text
返回 true
```

如果三秒到期仍然没有轮到：

```text
取消等待
返回 false
```

------

## 17. 调用前线程已经被中断

对于无参数：

```java
lock.tryLock();
```

它不会抛出 `InterruptedException`。

即使当前线程已经有中断标记，它仍会正常尝试获取锁。

中断标记通常仍然保留。

例如：

```java
Thread.currentThread().interrupt();

boolean acquired = lock.tryLock();

System.out.println(acquired);
System.out.println(
        Thread.currentThread().isInterrupted()
);
```

------

对于带超时参数：

```java
lock.tryLock(3, TimeUnit.SECONDS);
```

它是可中断获取方式。

如果调用前线程已经被中断，通常会直接抛出：

```java
InterruptedException
```

并清除中断标记。

所以：

| 方法                     | 调用前已被中断              |
| ------------------------ | --------------------------- |
| `tryLock()`              | 仍然正常尝试，不抛异常      |
| `tryLock(timeout, unit)` | 抛出 `InterruptedException` |

------

## 18. 为什么捕获中断后通常要重新设置标记

带超时的 `tryLock()` 可能抛出：

```java
InterruptedException
```

捕获后常见写法：

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}
```

原因是：

```text
InterruptedException 被抛出时
线程中断标记通常已经被清除
```

如果当前方法没有完整处理这次中断，应重新设置：

```java
Thread.currentThread().interrupt();
```

让上层代码仍然能知道：

```text
这个线程曾被要求中断
```

不要这样吞掉中断：

```java
catch (InterruptedException e) {
}
```

## 19. `tryLock()` 的典型使用场景

### 场景一：拿不到锁就跳过

例如定时任务不允许重复执行：

```java
public void scheduledTask() {
    if (!lock.tryLock()) {
        System.out.println(
                "上一次任务还没结束，本次跳过"
        );
        return;
    }

    try {
        executeTask();
    } finally {
        lock.unlock();
    }
}
```

执行效果：

```text
第一个线程获得锁：
正常执行任务

第二个线程再次触发：
tryLock() 返回 false
本次直接跳过
```

------

### 场景二：拿不到锁执行降级逻辑

```java
if (lock.tryLock()) {
    try {
        updateSharedCache();
    } finally {
        lock.unlock();
    }
} else {
    useLocalSnapshot();
}
```

获取不到锁时，不阻塞当前请求，而是读取旧数据或执行备用逻辑。

------

### 场景三：限制最大等待时间

```java
boolean acquired =
        lock.tryLock(500, TimeUnit.MILLISECONDS);

if (!acquired) {
    throw new RuntimeException(
            "系统繁忙，请稍后重试"
    );
}

try {
    processOrder();
} finally {
    lock.unlock();
}
```

这样可以避免请求线程无限等待。

------

### 场景四：同时获取多把锁

假设需要同时获取：

```text
lock1
lock2
```

可以尝试：

```java
boolean lock1Acquired = false;
boolean lock2Acquired = false;

try {
    lock1Acquired =
            lock1.tryLock(
                    1,
                    TimeUnit.SECONDS
            );

    if (!lock1Acquired) {
        return;
    }

    lock2Acquired =
            lock2.tryLock(
                    1,
                    TimeUnit.SECONDS
            );

    if (!lock2Acquired) {
        return;
    }

    // 同时持有 lock1 和 lock2
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    if (lock2Acquired) {
        lock2.unlock();
    }

    if (lock1Acquired) {
        lock1.unlock();
    }
}
```

如果第二把锁拿不到：

```text
等待超时
    ↓
进入 finally
    ↓
释放已经获得的第一把锁
```

这样比双方永远阻塞在第二把锁上更加可控。

------

## 20. `tryLock()` 能不能彻底解决死锁

不能。

它可以避免一种情况：

```text
线程永远等待另一把锁
```

因为获取失败后可以：

```text
返回 false
释放已经持有的锁
稍后重试
```

但如果代码设计不合理，仍然可能出现：

```text
活锁
频繁重试
线程饥饿
业务状态重复回滚
锁竞争风暴
```

例如两个线程不断执行：

```text
获得第一把锁
获取第二把锁失败
释放第一把锁
立即重试
```

两个线程的动作一直同步，可能谁也无法完成，这就是活锁风险。

因此：

> `tryLock()` 能降低无限等待风险，但不能代替合理的锁顺序和并发设计。

## 21. 一个可能造成活锁的写法

```java
while (true) {
    if (lock1.tryLock()) {
        try {
            if (lock2.tryLock()) {
                try {
                    // 执行业务
                    break;
                } finally {
                    lock2.unlock();
                }
            }
        } finally {
            lock1.unlock();
        }
    }
}
```

问题是：

```text
失败后立即疯狂重试
```

可能导致：

```text
CPU 占用升高
线程互相谦让
长期无法完成
```

可以增加：

```text
随机退避
限制重试次数
固定锁顺序
超时返回
```

例如：

```java
Thread.sleep(
        ThreadLocalRandom.current()
                .nextLong(10, 50)
);
```

不过实际业务应优先通过固定加锁顺序解决。

## 22. 无参数 `tryLock()` 完整示例

```java
import java.util.concurrent.locks.ReentrantLock;

public class TryLockDemo {

    private static final ReentrantLock LOCK =
            new ReentrantLock();

    public static void main(String[] args)
            throws InterruptedException {

        Thread threadA = new Thread(() -> {
            LOCK.lock();

            try {
                System.out.println(
                        "Thread-A 获得锁"
                );

                try {
                    Thread.sleep(3000);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            } finally {
                LOCK.unlock();

                System.out.println(
                        "Thread-A 释放锁"
                );
            }
        }, "Thread-A");

        Thread threadB = new Thread(() -> {
            System.out.println(
                    "Thread-B 尝试获取锁"
            );

            boolean acquired = LOCK.tryLock();

            if (!acquired) {
                System.out.println(
                        "Thread-B 获取失败，直接离开"
                );
                return;
            }

            try {
                System.out.println(
                        "Thread-B 获得锁"
                );
            } finally {
                LOCK.unlock();
            }
        }, "Thread-B");

        threadA.start();

        Thread.sleep(100);

        threadB.start();
    }
}
```

可能输出：

```text
Thread-A 获得锁
Thread-B 尝试获取锁
Thread-B 获取失败，直接离开
Thread-A 释放锁
```

Thread-B 不会等待 Thread-A 三秒。

它会立即得到：

```text
false
```

然后离开。

## 23. 带超时 `tryLock()` 完整示例

```java
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class TimedTryLockDemo {

    private static final ReentrantLock LOCK =
            new ReentrantLock();

    public static void main(String[] args)
            throws InterruptedException {

        Thread threadA = new Thread(() -> {
            LOCK.lock();

            try {
                System.out.println(
                        "Thread-A 获得锁"
                );

                try {
                    Thread.sleep(5000);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            } finally {
                LOCK.unlock();

                System.out.println(
                        "Thread-A 释放锁"
                );
            }
        }, "Thread-A");

        Thread threadB = new Thread(() -> {
            boolean acquired = false;

            try {
                System.out.println(
                        "Thread-B 最多等待两秒"
                );

                acquired =
                        LOCK.tryLock(
                                2,
                                TimeUnit.SECONDS
                        );

                if (!acquired) {
                    System.out.println(
                            "Thread-B 等待超时"
                    );
                    return;
                }

                System.out.println(
                        "Thread-B 成功获得锁"
                );
            } catch (InterruptedException e) {
                System.out.println(
                        "Thread-B 等待时被中断"
                );

                Thread.currentThread().interrupt();
            } finally {
                if (acquired) {
                    LOCK.unlock();
                }
            }
        }, "Thread-B");

        threadA.start();

        Thread.sleep(100);

        threadB.start();
    }
}
```

可能输出：

```text
Thread-A 获得锁
Thread-B 最多等待两秒
Thread-B 等待超时
Thread-A 释放锁
```

因为 Thread-A 持锁五秒，而 Thread-B 最多只等两秒。

## 25. `tryLock()` 的简化底层逻辑

无参数 `tryLock()` 可以简化理解为：

```java
public boolean tryLock() {
    Thread current = Thread.currentThread();

    int state = getState();

    if (state == 0) {
        if (compareAndSetState(0, 1)) {
            setExclusiveOwnerThread(current);
            return true;
        }
    } else if (
            current == getExclusiveOwnerThread()
    ) {
        setState(state + 1);
        return true;
    }

    return false;
}
```

这不是完整源码，只用于理解。

核心逻辑：

```text
state = 0：
CAS 抢锁

owner 是当前线程：
执行重入，state++

其他情况：
返回 false
```

## 26. 带超时 `tryLock()` 的简化底层逻辑

```java
public boolean tryLock(
        long time,
        TimeUnit unit
) throws InterruptedException {

    long nanos =
            unit.toNanos(time);

    if (Thread.interrupted()) {
        throw new InterruptedException();
    }

    if (尝试获取锁成功) {
        return true;
    }

    if (nanos <= 0L) {
        return false;
    }

    加入AQS同步队列();

    while (没有获得锁) {
        if (当前线程被中断) {
            取消等待();
            throw new InterruptedException();
        }

        if (剩余时间 <= 0) {
            取消等待();
            return false;
        }

        LockSupport.parkNanos(剩余时间);

        被唤醒后重新尝试();
    }

    return true;
}
```

核心过程：

```text
先立即尝试
    ↓
失败后判断是否还有等待时间
    ↓
加入 AQS 同步队列
    ↓
等待锁释放、中断或者超时
```

## 27. 被唤醒不等于获得锁

带超时 `tryLock()` 等待期间可能被：

```text
unpark
中断
超时
虚假唤醒
```

从 `parkNanos()` 中恢复。

恢复以后不是直接返回 `true`，而是：

```text
重新检查剩余时间
重新检查中断状态
重新尝试获取锁
```

所以：

```text
线程被唤醒
≠
线程已经获得锁
```

只有真正修改成功：

```text
state：0 → 1
owner：当前线程
```

才能返回：

```text
true
```

## 28. `tryLock()` 与 `lockInterruptibly()` 的区别

### `lockInterruptibly()`

```java
lock.lockInterruptibly();
```

特点：

```text
没有超时上限
可以被中断
不被中断就一直等待
成功以后返回
```

------

### 带超时 `tryLock()`

```java
lock.tryLock(3, TimeUnit.SECONDS);
```

特点：

```text
最多等待指定时间
可以被中断
可能返回 true
也可能因超时返回 false
```

对比：

| 方法                     | 最长等待时间 | 可中断 | 失败方式                     |
| ------------------------ | ------------ | ------ | ---------------------------- |
| `lockInterruptibly()`    | 没有上限     | 是     | 被中断抛异常                 |
| `tryLock(timeout, unit)` | 指定时间     | 是     | 超时返回 `false`，中断抛异常 |

------

## 29. 四种获取方式完整对比

| 方法                     | 获取不到锁时     | 是否响应中断 | 是否支持超时 | 结果                   |
| ------------------------ | ---------------- | ------------ | ------------ | ---------------------- |
| `lock()`                 | 一直等待         | 不取消获取   | 否           | 最终获得锁             |
| `lockInterruptibly()`    | 一直等待         | 是           | 否           | 获得锁或抛异常         |
| `tryLock()`              | 立即返回         | 不等待       | 否           | `true` 或 `false`      |
| `tryLock(timeout, unit)` | 最多等待指定时间 | 是           | 是           | `true`、`false` 或异常 |

选择方式：

```text
无论多久都要拿到：
lock()

需要支持取消：
lockInterruptibly()

现在拿不到就放弃：
tryLock()

只愿意等待一段时间：
tryLock(timeout, unit)
```

## 30. 常见错误

### 错误一：忽略返回值

```java
lock.tryLock();

try {
    // 临界区
} finally {
    lock.unlock();
}
```

可能根本没有获得锁。

------

### 错误二：获取失败后仍访问共享数据

```java
boolean acquired = lock.tryLock();

if (!acquired) {
    System.out.println("获取失败");
}

sharedData++;
```

即使获取失败，代码仍然访问共享数据。

正确写法：

```java
if (!lock.tryLock()) {
    return;
}

try {
    sharedData++;
} finally {
    lock.unlock();
}
```

------

### 错误三：获取失败后仍解锁

```java
boolean acquired = lock.tryLock();

try {
    // 临界区
} finally {
    lock.unlock();
}
```

如果 `acquired == false`，会抛出：

```text
IllegalMonitorStateException
```

------

### 错误四：认为无参数 `tryLock()` 遵守公平性

```java
ReentrantLock lock =
        new ReentrantLock(true);

lock.tryLock();
```

仍然可能插队。

------

### 错误五：把超时当成异常

```java
boolean acquired =
        lock.tryLock(1, TimeUnit.SECONDS);
```

超时只是返回：

```text
false
```

不会抛出超时异常。

------

### 错误六：吞掉中断

```java
catch (InterruptedException e) {
}
```

应根据业务：

```java
Thread.currentThread().interrupt();
```

或者继续向上抛。

------

### 错误七：获得两把锁后释放顺序混乱

推荐：

```text
先获得 lock1
再获得 lock2

先释放 lock2
再释放 lock1
```

并且每一把锁都要单独记录是否成功获得。

------

### 错误八：失败后无限高速重试

```java
while (!lock.tryLock()) {
}
```

这会持续占用 CPU。

更合理：

```text
限制重试次数
增加等待或退避
使用带超时 tryLock
失败后直接返回
```

------

## 31. 最终记忆

```text
tryLock()：
立即尝试获取锁

成功：
返回 true

失败：
立即返回 false

不进入长时间等待
不抛 InterruptedException
不遵守公平锁排队策略
tryLock(timeout, unit)：
最多等待指定时间

等待期间获得锁：
返回 true

等待超时：
返回 false

等待期间被中断：
抛出 InterruptedException

公平锁中遵守公平策略
```

最重要的代码规则：

```java
if (!lock.tryLock()) {
    return;
}

try {
    // 临界区
} finally {
    lock.unlock();
}
```

以及：

```java
boolean acquired = false;

try {
    acquired =
            lock.tryLock(
                    3,
                    TimeUnit.SECONDS
            );

    if (!acquired) {
        return;
    }

    // 临界区
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    if (acquired) {
        lock.unlock();
    }
}
```

一句话总结：

> 无参数 `tryLock()` 会立即尝试获取锁，成功返回 `true`，失败立即返回 `false`；带超时时间的 `tryLock()` 则会在指定时间内等待锁，成功返回 `true`，超时返回 `false`，等待期间被中断会抛出 `InterruptedException`。

# `Condition`：条件等待与精确唤醒

## 1. `Condition` 是什么

`Condition` 是 Java 并发包中的一个接口：

```java
package java.util.concurrent.locks;

public interface Condition {
}
```

它通常与：

```java
ReentrantLock
```

配合使用。

创建方式：

```java
ReentrantLock lock = new ReentrantLock();

Condition condition = lock.newCondition();
```

`Condition` 主要用于解决这样的问题：

> 线程已经获得锁，但当前业务条件还不满足，所以需要暂时释放锁并等待；等其他线程修改了共享状态后，再通知它回来继续竞争锁。

例如消费者准备取食物：

```text
消费者已经获得锁
        ↓
发现没有食物
        ↓
暂时释放锁并等待
        ↓
生产者放入食物
        ↓
生产者发出通知
        ↓
消费者重新竞争锁
        ↓
消费者获得锁
        ↓
继续取食物
```

因此，`Condition` 不是用来代替锁的。

它负责的是：

```text
线程之间的条件等待和通知
```

而 `ReentrantLock` 负责的是：

```text
线程之间的互斥访问
```

两者关系可以概括为：

```text
ReentrantLock：
决定线程能不能进入临界区

Condition：
线程进入临界区后，条件不满足时应该去哪里等待
```

------

## 2. `Condition` 不是一把锁

下面代码创建了一把锁：

```java
ReentrantLock lock = new ReentrantLock();
```

又创建了一个条件对象：

```java
Condition hasFood = lock.newCondition();
```

这里：

```text
lock：
是一把互斥锁

hasFood：
是与这把锁关联的条件对象
```

调用：

```java
lock.lock();
```

表示：

> 当前线程尝试获得锁。

调用：

```java
hasFood.await();
```

表示：

> 当前线程已经获得锁，但“有食物”这个条件还不满足，所以主动释放锁并等待。

因此，下面这种理解不准确：

```text
Condition 是另一把锁
```

正确理解是：

> `Condition` 是依附于某把 `Lock` 的条件等待机制。

------

## 3. `Condition` 与线程、锁的关系

可以把三者关系画成：

```text
线程
  │
  │ 调用 lock()
  ▼
ReentrantLock
  │
  │ 获得锁以后发现条件不满足
  │ 调用 await()
  ▼
Condition 条件队列
```

完整一点：

```text
┌──────────────────────────────┐
│        ReentrantLock         │
│                              │
│  state：锁持有次数             │
│  owner：当前持锁线程           │
│                              │
│  AQS 同步队列：                │
│  等待获取锁的线程               │
└──────────────────────────────┘
              │
              │ newCondition()
              ▼
┌──────────────────────────────┐
│          Condition           │
│                              │
│  条件队列：                    │
│  调用 await() 等待条件的线程    │
└──────────────────────────────┘
```

这里存在两类等待线程：

```text
同步队列中的线程：
想获得锁，但暂时没有获得

条件队列中的线程：
曾经获得了锁，但业务条件不满足，
主动释放锁并等待通知
```

这是理解 `Condition` 最重要的区别。

------

## 4. 如何创建 `Condition`

标准写法：

```java
private final ReentrantLock lock =
        new ReentrantLock();

private final Condition condition =
        lock.newCondition();
```

也可以在同一把锁上创建多个 `Condition`：

```java
private final ReentrantLock lock =
        new ReentrantLock();

private final Condition notEmpty =
        lock.newCondition();

private final Condition notFull =
        lock.newCondition();
```

这里：

```text
notEmpty：
等待“队列不为空”的线程

notFull：
等待“队列没有满”的线程
```

每调用一次：

```java
lock.newCondition();
```

都会得到一个新的、独立的条件对象。

每个条件对象都有自己的条件等待队列。

```text
ReentrantLock
    │
    ├── Condition notEmpty
    │       └── 条件队列 1
    │
    └── Condition notFull
            └── 条件队列 2
```

------

## 5. `Condition` 的核心方法

`Condition` 主要包含以下方法：

```java
void await() throws InterruptedException;

void awaitUninterruptibly();

long awaitNanos(long nanosTimeout)
        throws InterruptedException;

boolean await(long time, TimeUnit unit)
        throws InterruptedException;

boolean awaitUntil(Date deadline)
        throws InterruptedException;

void signal();

void signalAll();
```

可以分为两类。

### 等待方法

```java
await()
awaitUninterruptibly()
awaitNanos()
await(time, unit)
awaitUntil()
```

作用：

> 当前线程释放锁，进入条件队列等待。

### 通知方法

```java
signal()
signalAll()
```

作用：

> 将条件队列中的线程转移到 AQS 同步队列，让它们重新竞争锁。

------

## 6. `await()` 的基本使用方式

标准写法：

```java
lock.lock();

try {
    while (!条件成立) {
        condition.await();
    }

    // 条件成立后的业务逻辑
} finally {
    lock.unlock();
}
```

例如：

```java
private boolean ready;

private final ReentrantLock lock =
        new ReentrantLock();

private final Condition readyCondition =
        lock.newCondition();

public void execute() throws InterruptedException {
    lock.lock();

    try {
        while (!ready) {
            readyCondition.await();
        }

        System.out.println("条件成立，开始执行");
    } finally {
        lock.unlock();
    }
}
```

这里必须满足：

```text
先获得锁
    ↓
检查业务条件
    ↓
条件不满足
    ↓
调用 await()
```

------

## 7. 调用 `await()` 前必须持有锁

错误写法：

```java
condition.await();
```

如果当前线程没有持有与该 `Condition` 关联的锁，会抛出：

```text
IllegalMonitorStateException
```

正确写法：

```java
lock.lock();

try {
    condition.await();
} finally {
    lock.unlock();
}
```

为什么必须先获得锁？

因为线程执行 `await()` 前，通常需要检查某个共享状态：

```java
while (!ready) {
    condition.await();
}
```

这里的：

```java
ready
```

是共享变量。

检查状态与进入等待必须受到同一把锁的保护，否则可能发生通知丢失。

例如：

```text
消费者检查：没有食物
        ↓
生产者放入食物并通知
        ↓
消费者才开始 await()
```

消费者会错过刚才的通知，可能永远等待。

锁可以保证：

```text
检查条件
和
进入等待
```

形成一个正确衔接的过程。

------

## 8. `await()` 会释放锁

这是 `await()` 最重要的特点之一。

线程执行：

```java
condition.await();
```

以后，会主动释放当前持有的锁。

例如：

```java
lock.lock();

try {
    System.out.println("获得锁");

    condition.await();

    System.out.println("等待结束");
} finally {
    lock.unlock();
}
```

执行到 `await()` 时：

```text
当前线程原本持有 lock
        ↓
加入 Condition 条件队列
        ↓
释放 lock
        ↓
进入等待
```

释放锁以后，其他线程才能获得锁并修改共享状态。

例如生产者需要获得锁：

```java
lock.lock();

try {
    ready = true;
    condition.signal();
} finally {
    lock.unlock();
}
```

假如 `await()` 不释放锁：

```text
消费者持有锁并等待生产者
生产者等待消费者释放锁
```

双方会永远等待。

因此：

> `await()` 必须释放锁，其他线程才能进入临界区，使条件变为成立。

------

## 9. `await()` 会完全释放所有重入层数

假设当前线程连续加锁三次：

```java
lock.lock();
lock.lock();
lock.lock();
```

此时：

```text
state = 3
owner = 当前线程
```

然后执行：

```java
condition.await();
```

`await()` 不是只释放一层锁。

它会完全释放当前线程持有的所有重入层数：

```text
state：3 → 0
owner：当前线程 → null
```

然后进入条件队列等待。

等到线程被通知，并且重新获得锁以后，原来的重入次数会恢复：

```text
state：0 → 3
owner：当前线程
```

之后 `await()` 才会返回。

所以完整过程是：

```text
调用 await() 前：
state = 3

进入等待：
state = 0

重新获得锁：
state = 3

await() 返回
```

这一点非常重要：

> `await()` 会完全释放锁，并在返回前恢复原来的锁持有次数。

------

## 10. `await()` 返回前必须重新获得锁

线程被：

```java
condition.signal();
```

通知后，并不会立即从 `await()` 返回。

它还需要重新获得与 Condition 关联的锁。

完整过程：

```text
条件队列中等待
        ↓
被 signal()
        ↓
转移到 AQS 同步队列
        ↓
等待重新获得锁
        ↓
成功获得锁
        ↓
await() 返回
```

因此，执行完：

```java
condition.await();
```

以后，当前线程仍然持有锁。

例如：

```java
lock.lock();

try {
    while (!ready) {
        condition.await();
    }

    // 这里仍然持有 lock
    useSharedData();
} finally {
    lock.unlock();
}
```

不需要在 `await()` 返回后重新执行：

```java
lock.lock();
```

因为它已经重新获得锁了。

------

## 11. `await()` 的完整执行流程

假设 Thread-A 当前持有锁：

```text
state = 1
owner = Thread-A
```

Thread-A 调用：

```java
condition.await();
```

完整过程可以分为以下步骤。

### 第一步：检查当前线程是否持有锁

如果没有持有锁：

```text
抛出 IllegalMonitorStateException
```

------

### 第二步：加入 Condition 条件队列

Thread-A 被包装为一个等待节点，加入当前 Condition 的条件队列：

```text
Condition Queue：

Thread-A
```

如果已经有线程等待：

```text
Condition Queue：

Thread-A → Thread-B → Thread-C
```

------

### 第三步：完全释放锁

假设：

```text
state = 1
owner = Thread-A
```

释放后：

```text
state = 0
owner = null
```

如果原来是重入三次：

```text
state = 3
```

则也会完全释放为：

```text
state = 0
```

------

### 第四步：线程进入等待

Thread-A 会被挂起，不再继续执行：

```text
condition.await();
        ↑
程序暂时停在这里
```

------

### 第五步：其他线程修改条件

例如 Thread-B 获得锁：

```java
lock.lock();

try {
    ready = true;
    condition.signal();
} finally {
    lock.unlock();
}
```

------

### 第六步：Thread-A 被转移到同步队列

`signal()` 会将 Thread-A 从：

```text
Condition 条件队列
```

转移到：

```text
AQS 同步队列
```

此时 Thread-A 仍然没有获得锁。

------

### 第七步：等待 Thread-B 释放锁

Thread-B 执行：

```java
lock.unlock();
```

之后，Thread-A 才有机会重新竞争锁。

------

### 第八步：Thread-A 重新获得锁

成功后：

```text
state = 原来的重入次数
owner = Thread-A
```

------

### 第九步：`await()` 返回

Thread-A 从原来的位置继续执行：

```java
condition.await();

System.out.println("继续执行");
```

------

## 12. `signal()` 是什么

方法定义：

```java
void signal();
```

作用：

> 通知当前 Condition 条件队列中的一个等待线程，让它转移到 AQS 同步队列，重新等待获取锁。

标准用法：

```java
lock.lock();

try {
    修改共享状态();

    condition.signal();
} finally {
    lock.unlock();
}
```

例如：

```java
lock.lock();

try {
    ready = true;
    readyCondition.signal();
} finally {
    lock.unlock();
}
```

调用 `signal()` 前，也必须持有对应的锁。

否则会抛出：

```text
IllegalMonitorStateException
```

------

## 13. `signal()` 不会立即释放锁

假设 Thread-B 执行：

```java
lock.lock();

try {
    ready = true;

    condition.signal();

    doSomething();
} finally {
    lock.unlock();
}
```

执行：

```java
condition.signal();
```

以后，Thread-B 仍然持有锁。

它还可以继续执行：

```java
doSomething();
```

只有执行：

```java
lock.unlock();
```

以后，被通知的线程才有机会获得锁。

执行过程：

```text
Thread-B 持有锁
        ↓
调用 signal()
        ↓
等待线程转入同步队列
        ↓
Thread-B 仍然持有锁
        ↓
Thread-B 继续执行临界区
        ↓
Thread-B 调用 unlock()
        ↓
等待线程开始竞争锁
```

因此：

```text
signal()
≠
释放锁
```

也不等于：

```text
signal()
≠
被通知线程立即执行
```

------

## 14. `signal()` 到底做了什么

假设 Condition 条件队列是：

```text
Condition Queue：

Thread-A → Thread-B → Thread-C
```

调用：

```java
condition.signal();
```

通常会选择等待时间最长的有效等待线程，例如 Thread-A。

然后把它转移到同步队列：

```text
Condition Queue：

Thread-B → Thread-C
```

同步队列可能变为：

```text
AQS Sync Queue：

Thread-D → Thread-E → Thread-A
```

Thread-A 接下来等待的是：

```text
重新获得 lock
```

而不是继续等待业务通知。

所以可以记住：

```text
await：
同步队列之外 → 条件队列

signal：
条件队列 → 同步队列
```

更准确地说，调用 `await()` 的线程原本持有锁，之后进入条件队列；被 `signal()` 后才转移到同步队列。

------

## 15. 被 `signal()` 的线程不一定马上获得锁

假设：

```text
Condition 条件队列：
Thread-A

同步队列：
Thread-C
```

Thread-B 当前持有锁，并调用：

```java
condition.signal();
```

Thread-A 被转移后：

```text
同步队列：
Thread-C → Thread-A
```

Thread-B 释放锁以后，通常是 Thread-C 先有资格获得锁。

Thread-A 还要继续等待。

即使同步队列中没有其他线程，非公平锁下也可能有新线程插队。

因此：

> `signal()` 只是让线程从“等待条件”变成“等待锁”，并不保证它下一个执行。

------

## 16. `signalAll()` 是什么

方法定义：

```java
void signalAll();
```

作用：

> 将当前 Condition 条件队列中的所有等待线程转移到 AQS 同步队列。

假设：

```text
Condition Queue：

Thread-A → Thread-B → Thread-C
```

执行：

```java
condition.signalAll();
```

以后：

```text
Condition Queue：

空
```

这些线程进入同步队列：

```text
AQS Sync Queue：

Thread-A → Thread-B → Thread-C
```

但它们不可能同时进入临界区。

因为 `ReentrantLock` 是互斥锁：

```text
同一时刻仍然只有一个线程能获得锁
```

所以它们需要依次竞争和执行。

------

## 17. `signal()` 和 `signalAll()` 的区别

| 方法          | 通知数量     | 特点                       |
| ------------- | ------------ | -------------------------- |
| `signal()`    | 一个等待线程 | 唤醒更精确，开销通常更小   |
| `signalAll()` | 所有等待线程 | 更稳妥，但会产生更多锁竞争 |

### 使用 `signal()`

```java
condition.signal();
```

适合：

- 所有等待线程等待的是同一种条件；
- 一次状态变化只允许一个线程继续；
- 可以明确保证不会唤醒错误类型的线程；
- 条件划分足够精确。

### 使用 `signalAll()`

```java
condition.signalAll();
```

适合：

- 多个线程等待的条件不完全一样；
- 状态变化可能让多个线程都可以继续；
- 无法确定应该通知哪个线程；
- 更看重正确性，而不是少量唤醒开销。

初学阶段不确定时：

> `signalAll()` 通常更安全，但配合多个精确的 Condition 后，往往可以合理使用 `signal()`。

------

## 18. 为什么 `await()` 必须放在 `while` 中

错误写法：

```java
if (!ready) {
    condition.await();
}
```

正确写法：

```java
while (!ready) {
    condition.await();
}
```

主要有三个原因。

### 原因一：可能发生虚假唤醒

线程可能在没有收到真正业务通知的情况下，从底层等待中恢复。

因此不能认为：

```text
await() 返回
=
条件一定成立
```

必须重新检查：

```java
while (!ready) {
    condition.await();
}
```

------

### 原因二：被通知后，条件可能再次失效

假设仓库中只有一个商品。

两个消费者等待：

```text
消费者 A
消费者 B
```

生产者放入一个商品，然后执行：

```java
notEmpty.signalAll();
```

A 和 B 都被转移到同步队列。

A 先获得锁并取走商品：

```text
商品数量：1 → 0
```

B 随后获得锁。

虽然 B 也被通知过，但此时仓库又空了。

如果使用：

```java
if (queue.isEmpty()) {
    notEmpty.await();
}
```

B 不会再次检查条件，可能继续执行错误逻辑。

使用：

```java
while (queue.isEmpty()) {
    notEmpty.await();
}
```

B 会发现队列仍然为空，再次进入等待。

------

### 原因三：`signal()` 只是通知状态可能变化

`signal()` 表达的不是：

```text
你的条件已经百分之百成立
```

而更接近：

```text
共享状态发生了变化，你可以醒来重新检查一下
```

所以标准模式永远是：

```java
while (!条件成立) {
    condition.await();
}
```

------

## 19. 什么是条件谓词

下面的判断：

```java
queue.isEmpty()
```

或者：

```java
!ready
```

可以称为条件谓词。

例如：

```java
while (queue.isEmpty()) {
    notEmpty.await();
}
```

这里线程等待的条件是：

```text
队列不为空
```

条件谓词必须满足几个规则：

```text
1. 在持有锁的情况下检查
2. 在 while 循环中检查
3. 修改条件相关状态时，也持有同一把锁
4. 状态改变后，再执行 signal 或 signalAll
```

完整模式：

```java
lock.lock();

try {
    while (!条件成立) {
        condition.await();
    }

    执行业务();
} finally {
    lock.unlock();
}
```

修改条件的线程：

```java
lock.lock();

try {
    修改共享状态();

    condition.signal();
} finally {
    lock.unlock();
}
```

------

## 20. 为什么应该先修改状态，再 `signal()`

推荐：

```java
lock.lock();

try {
    ready = true;
    condition.signalAll();
} finally {
    lock.unlock();
}
```

不推荐：

```java
lock.lock();

try {
    condition.signalAll();
    ready = true;
} finally {
    lock.unlock();
}
```

虽然通知线程必须重新获得锁后才能检查状态，第二种写法在严格持锁场景下通常也不一定立即出错，但逻辑表达不清晰。

更合理的顺序是：

```text
先让条件成立
    ↓
再通知等待线程
```

即：

```java
修改状态();
condition.signal();
```

这样通知的含义明确：

> 状态已经发生变化，你们可以重新检查了。

## 21. 一个 Condition 的完整示例

```java
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public class ConditionDemo {

    private final ReentrantLock lock =
            new ReentrantLock();

    private final Condition hasFood =
            lock.newCondition();

    private boolean foodAvailable;

    public void eat() throws InterruptedException {
        lock.lock();

        try {
            while (!foodAvailable) {
                System.out.println(
                        Thread.currentThread().getName()
                                + "：没有食物，进入等待"
                );

                hasFood.await();
            }

            System.out.println(
                    Thread.currentThread().getName()
                            + "：开始吃食物"
            );

            foodAvailable = false;
        } finally {
            lock.unlock();
        }
    }

    public void produce() {
        lock.lock();

        try {
            foodAvailable = true;

            System.out.println(
                    Thread.currentThread().getName()
                            + "：生产了食物"
            );

            hasFood.signal();
        } finally {
            lock.unlock();
        }
    }
}
```

执行：

```java
public static void main(String[] args)
        throws InterruptedException {

    ConditionDemo demo = new ConditionDemo();

    Thread consumer = new Thread(() -> {
        try {
            demo.eat();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }, "消费者");

    Thread producer = new Thread(
            demo::produce,
            "生产者"
    );

    consumer.start();

    Thread.sleep(1000);

    producer.start();
}
```

可能输出：

```text
消费者：没有食物，进入等待
生产者：生产了食物
消费者：开始吃食物
```

完整过程：

```text
消费者获得锁
    ↓
发现 foodAvailable = false
    ↓
调用 await()
    ↓
释放锁并进入 hasFood 条件队列
    ↓
生产者获得锁
    ↓
foodAvailable = true
    ↓
调用 signal()
    ↓
消费者转移到同步队列
    ↓
生产者释放锁
    ↓
消费者重新获得锁
    ↓
await() 返回
    ↓
重新检查 foodAvailable
    ↓
开始吃食物
```

## 22. 多个 `Condition` 的意义

假设实现一个有界队列：

```text
队列为空：
消费者不能取数据

队列已满：
生产者不能放数据
```

这里存在两种完全不同的等待原因：

```text
消费者等待：
队列不为空

生产者等待：
队列没有满
```

可以创建两个 Condition：

```java
private final Condition notEmpty =
        lock.newCondition();

private final Condition notFull =
        lock.newCondition();
```

这样：

```text
消费者只进入 notEmpty 条件队列

生产者只进入 notFull 条件队列
```

当放入一个元素后：

```java
notEmpty.signal();
```

只通知消费者。

当取走一个元素后：

```java
notFull.signal();
```

只通知生产者。

这就是多个 Condition 的最大优势：

> 可以按照不同业务条件，对等待线程进行分类和精确通知。

## 23. 有界阻塞队列完整示例

```java
import java.util.ArrayDeque;
import java.util.Queue;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public class BoundedQueue<E> {

    private final Queue<E> queue =
            new ArrayDeque<>();

    private final int capacity;

    private final ReentrantLock lock =
            new ReentrantLock();

    /**
     * 等待队列中存在可取元素。
     */
    private final Condition notEmpty =
            lock.newCondition();

    /**
     * 等待队列中存在空余位置。
     */
    private final Condition notFull =
            lock.newCondition();

    public BoundedQueue(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException(
                    "capacity 必须大于 0"
            );
        }

        this.capacity = capacity;
    }

    public void put(E element)
            throws InterruptedException {

        lock.lockInterruptibly();

        try {
            while (queue.size() == capacity) {
                notFull.await();
            }

            queue.offer(element);

            /*
             * 放入元素后，队列一定不为空。
             * 通知一个等待取数据的消费者。
             */
            notEmpty.signal();
        } finally {
            lock.unlock();
        }
    }

    public E take()
            throws InterruptedException {

        lock.lockInterruptibly();

        try {
            while (queue.isEmpty()) {
                notEmpty.await();
            }

            E element = queue.poll();

            /*
             * 取走元素后，队列一定出现了空余空间。
             * 通知一个等待放数据的生产者。
             */
            notFull.signal();

            return element;
        } finally {
            lock.unlock();
        }
    }

    public int size() {
        lock.lock();

        try {
            return queue.size();
        } finally {
            lock.unlock();
        }
    }
}
```

### 生产者流程

```text
获得锁
    ↓
队列是否已满？
    │
    ├── 是
    │    ↓
    │  notFull.await()
    │    ↓
    │  释放锁并等待
    │
    └── 否
         ↓
       放入元素
         ↓
       notEmpty.signal()
         ↓
       通知消费者
```

### 消费者流程

```text
获得锁
    ↓
队列是否为空？
    │
    ├── 是
    │    ↓
    │  notEmpty.await()
    │    ↓
    │  释放锁并等待
    │
    └── 否
         ↓
       取走元素
         ↓
       notFull.signal()
         ↓
       通知生产者
```

实际项目中，一般直接使用：

```java
ArrayBlockingQueue
LinkedBlockingQueue
```

这个例子主要用于理解 `Condition` 的工作原理。

## 24. `Condition` 与 `wait/notify` 的关系

使用 `synchronized` 时：

```java
synchronized (monitor) {
    while (!ready) {
        monitor.wait();
    }
}
```

通知：

```java
synchronized (monitor) {
    ready = true;
    monitor.notify();
}
```

使用 `ReentrantLock + Condition` 时：

```java
lock.lock();

try {
    while (!ready) {
        condition.await();
    }
} finally {
    lock.unlock();
}
```

通知：

```java
lock.lock();

try {
    ready = true;
    condition.signal();
} finally {
    lock.unlock();
}
```

方法对应关系：

| `Object` 监视器 | `Condition`         |
| --------------- | ------------------- |
| `wait()`        | `await()`           |
| `wait(timeout)` | `await(time, unit)` |
| `notify()`      | `signal()`          |
| `notifyAll()`   | `signalAll()`       |

共同点：

```text
等待前必须先持有锁

等待时都会释放锁

被通知后都必须重新获取锁

通知操作本身不会立即释放锁

都应该使用 while 检查条件
```

------

## 25. `Condition` 相比 `wait/notify` 的优势

### `synchronized` 通常只有一个等待集合

假设：

```java
synchronized (monitor) {
    monitor.wait();
}
```

所有在这个 monitor 上等待的线程，都会进入同一个等待集合。

例如：

```text
等待队列不为空的消费者
等待队列不满的生产者
等待系统启动的线程
```

如果全都在同一个监视器上等待，通知时不容易区分。

------

### 一把 `ReentrantLock` 可以创建多个 Condition

```java
Condition notEmpty = lock.newCondition();
Condition notFull = lock.newCondition();
Condition started = lock.newCondition();
```

可以形成：

```text
notEmpty 条件队列：
只放消费者

notFull 条件队列：
只放生产者

started 条件队列：
只放等待系统启动的线程
```

因此可以精确通知：

```java
notEmpty.signal();
```

只通知消费者，而不是把所有类型的线程都叫醒。

------

## 26. `await()` 的中断行为

方法定义：

```java
void await() throws InterruptedException;
```

说明 `await()` 是可中断等待。

线程正在：

```java
condition.await();
```

时，其他线程调用：

```java
waitingThread.interrupt();
```

等待线程会响应中断。

一般流程：

```text
线程在 Condition 队列中等待
        ↓
收到 interrupt()
        ↓
取消条件等待
        ↓
重新获得关联的锁
        ↓
抛出 InterruptedException
```

需要注意：

> 即使 `await()` 因中断抛出异常，在异常被当前线程处理前，它也要先重新获得锁。

例如：

```java
lock.lock();

try {
    condition.await();
} catch (InterruptedException e) {
    // 执行到这里时，当前线程仍然持有 lock
    Thread.currentThread().interrupt();
} finally {
    lock.unlock();
}
```

所以 `finally` 中可以正常释放锁。

------

## 27. 调用 `await()` 前已经被中断

假设当前线程已经有中断标记：

```java
Thread.currentThread().interrupt();
```

然后执行：

```java
condition.await();
```

`await()` 会检查中断状态，并抛出：

```text
InterruptedException
```

一般不会正式进入长期条件等待。

因此：

```text
await()：
进入前已中断，也会响应中断

等待过程中被中断，也会响应中断
```

## 28. 捕获 `InterruptedException` 后如何处理

常见写法：

```java
try {
    condition.await();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;
}
```

原因是：

```text
抛出 InterruptedException 后，
线程中断标记通常会被清除
```

如果当前方法没有完整处理这次中断，应重新设置：

```java
Thread.currentThread().interrupt();
```

不要这样吞掉中断：

```java
catch (InterruptedException e) {
}
```

更推荐让上层处理：

```java
public void awaitReady()
        throws InterruptedException {

    lock.lockInterruptibly();

    try {
        while (!ready) {
            condition.await();
        }
    } finally {
        lock.unlock();
    }
}
```

## 29. `awaitUninterruptibly()`

方法定义：

```java
void awaitUninterruptibly();
```

它表示：

> 不可中断地等待条件。

使用方式：

```java
lock.lock();

try {
    while (!ready) {
        condition.awaitUninterruptibly();
    }
} finally {
    lock.unlock();
}
```

如果等待过程中收到：

```java
thread.interrupt();
```

线程不会抛出 `InterruptedException`，也不会取消等待。

它仍然继续等待，直到：

```text
被 signal 或 signalAll 通知
并重新获得锁
```

如果等待期间发生过中断，方法最终正常返回后，中断状态通常会被保留。

对比：

| 方法                     | 等待期间被中断              |
| ------------------------ | --------------------------- |
| `await()`                | 抛出 `InterruptedException` |
| `awaitUninterruptibly()` | 继续等待，不抛异常          |

使用 `awaitUninterruptibly()` 时要谨慎，因为它会让任务更难取消。

## 30. `await(long, TimeUnit)`

方法定义：

```java
boolean await(long time, TimeUnit unit)
        throws InterruptedException;
```

例如：

```java
boolean signalled =
        condition.await(
                3,
                TimeUnit.SECONDS
        );
```

表示：

> 最多等待三秒。

返回值通常可以理解为：

```text
true：
在超时前被通知

false：
等待超时
```

但是即使返回 `true`，也不能直接认为业务条件一定成立。

仍然必须使用 while：

```java
long timeout = 3;

while (!ready) {
    boolean signalled =
            condition.await(
                    timeout,
                    TimeUnit.SECONDS
            );

    if (!signalled && !ready) {
        return;
    }
}
```

实际编写超时条件等待时，通常更适合使用 `awaitNanos()` 计算剩余时间。

## 31. `awaitNanos()`

方法定义：

```java
long awaitNanos(long nanosTimeout)
        throws InterruptedException;
```

它接收纳秒等待时间，并返回：

```text
剩余等待时间
```

标准写法：

```java
long nanos =
        TimeUnit.SECONDS.toNanos(3);

lock.lockInterruptibly();

try {
    while (!ready) {
        if (nanos <= 0L) {
            System.out.println("等待超时");
            return;
        }

        nanos = condition.awaitNanos(nanos);
    }

    System.out.println("条件成立");
} finally {
    lock.unlock();
}
```

为什么要保存剩余时间？

假设：

```text
总超时时间：3 秒
```

线程等待一秒后发生虚假唤醒。

如果重新调用：

```java
condition.awaitNanos(
        TimeUnit.SECONDS.toNanos(3)
);
```

又会重新等待三秒，总等待时间可能超过原计划。

正确做法：

```text
第一次等待后返回剩余时间
        ↓
下一次只等待剩余时间
```

## 33. 多个 Condition 的队列结构

假设：

```java
Condition notEmpty =
        lock.newCondition();

Condition notFull =
        lock.newCondition();
```

可能形成：

```text
AQS 同步队列：
Thread-A → Thread-B

notEmpty 条件队列：
Consumer-1 → Consumer-2

notFull 条件队列：
Producer-1 → Producer-2
```

这些队列的含义分别是：

```text
AQS 同步队列：
线程想获得 lock，但暂时拿不到

notEmpty 条件队列：
消费者等待队列中出现元素

notFull 条件队列：
生产者等待队列出现空余空间
```

执行：

```java
notEmpty.signal();
```

只会影响：

```text
notEmpty 条件队列
```

不会影响：

```text
notFull 条件队列
```

也不会直接唤醒所有同步队列线程。

## 34. `signal()` 与公平锁

假设使用公平锁：

```java
ReentrantLock lock =
        new ReentrantLock(true);
```

一个线程从 Condition 条件队列被转移到同步队列后，会按照公平锁的同步队列策略等待获取锁。

假设：

```text
同步队列：
Thread-B → Thread-C
```

Condition 中的 Thread-A 被 `signal()`：

```text
同步队列：
Thread-B → Thread-C → Thread-A
```

Thread-A 通常不会越过已经排队的 B、C。

如果是非公平锁，新来的队外线程仍可能插队，但条件队列转移过来的线程本身仍要按照 AQS 同步队列规则等待。

## 35. `signal()` 是否会丢失

`Condition` 不会保存“通知次数”。

假设当前 Condition 中没有任何等待线程：

```text
Condition Queue：
空
```

此时执行：

```java
condition.signal();
```

这个通知不会被保存。

之后新线程再调用：

```java
condition.await();
```

它不会因为之前调用过 `signal()` 而直接返回。

因此：

```text
signal 不是许可证
signal 也不是消息存储
```

正确设计依赖的是共享状态：

```java
ready = true;
condition.signal();
```

等待线程先检查：

```java
while (!ready) {
    condition.await();
}
```

如果 `ready` 已经是 `true`，线程根本不需要进入等待。

所以真正可靠的是：

```text
共享状态
+
锁
+
while 检查
```

而不是单独依赖 signal 的次数。

## 36. 为什么通知必须和共享状态配合

错误设计：

```java
public void waitForSignal()
        throws InterruptedException {

    lock.lock();

    try {
        condition.await();
    } finally {
        lock.unlock();
    }
}
```

这里没有任何条件判断。

线程只是盲目等待一个通知。

如果通知在线程进入等待前已经发生，就可能永远等不到。

正确设计：

```java
private boolean ready;

public void waitForReady()
        throws InterruptedException {

    lock.lock();

    try {
        while (!ready) {
            condition.await();
        }
    } finally {
        lock.unlock();
    }
}
```

通知方：

```java
public void makeReady() {
    lock.lock();

    try {
        ready = true;
        condition.signalAll();
    } finally {
        lock.unlock();
    }
}
```

即使通知先发生：

```text
ready 已经变成 true
```

等待线程进入后检查到条件成立，不会调用 `await()`。

## 42. 常见错误五：认为 `await()` 返回时没有锁


```text

```

如果后面只解锁一次，就可能导致锁无法完全释放。

## 43. 常见错误六：用错 Condition

等待在 `notEmpty` 中的线程不会收到通知。

## 44. 常见错误七：把 Condition 当成共享状态

## 45. 常见错误八：只调用 `signal()`，不改变状态


发现：

于是再次进入等待。

正确：

```java
lock.lock();

try {
    ready = true;
    condition.signal();
} finally {
    lock.unlock();
}
```

------

## 46. 常见错误九：吞掉 `InterruptedException`

错误：

```java
try {
    condition.await();
} catch (InterruptedException e) {
}
```

更合理：

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;
}
```

或者继续向上抛出。

------

## 47. 常见错误十：暴露 Lock 和 Condition

不推荐：

```java
public final ReentrantLock lock =
        new ReentrantLock();

public final Condition condition =
        lock.newCondition();
```

外部代码可以随意调用：

```java
lock.lock();
condition.await();
condition.signalAll();
```

破坏类内部的同步规则。

推荐：

```java
private final ReentrantLock lock =
        new ReentrantLock();

private final Condition condition =
        lock.newCondition();
```

只通过类自身的方法操作共享状态。

## 48. `Condition` 的底层整体流程

### `await()` 流程

```text
线程已经持有锁
        ↓
检查中断状态
        ↓
加入 Condition 条件队列
        ↓
保存当前重入次数
        ↓
完全释放 ReentrantLock
        ↓
线程 park 等待
        ↓
收到 signal / signalAll
        ↓
转移到 AQS 同步队列
        ↓
重新竞争 ReentrantLock
        ↓
恢复原来的重入次数
        ↓
await() 返回
```

### `signal()` 流程

```text
当前线程持有锁
        ↓
调用 signal()
        ↓
选择 Condition 队列中的一个有效节点
        ↓
把节点转移到 AQS 同步队列
        ↓
当前线程仍然继续持有锁
        ↓
当前线程执行 unlock()
        ↓
被通知线程重新竞争锁
```

### `signalAll()` 流程

```text
当前线程持有锁
        ↓
调用 signalAll()
        ↓
Condition 队列中的全部有效节点
转移到 AQS 同步队列
        ↓
等待线程逐个竞争锁
```

## 49. 面试常见问题

### Condition 是什么

`Condition` 是与 `Lock` 关联的条件等待机制，用于让持锁线程在业务条件不满足时释放锁并等待通知。

------

### Condition 是队列吗

`Condition` 本身是一个接口对象。

它的具体实现内部维护着条件等待队列。

可以简单说：

> 一个 Condition 对应一个条件等待队列。

但更准确地说：

```text
Condition 不是队列本身
Condition 内部管理条件队列
```

------

### 一把锁可以有几个 Condition

可以创建多个：

```java
Condition condition1 =
        lock.newCondition();

Condition condition2 =
        lock.newCondition();
```

每个 Condition 都有独立的条件等待队列。

------

### `await()` 会释放锁吗

会。

而且会完全释放当前线程持有的所有重入层数。

返回之前会重新获得锁，并恢复原来的持有次数。

------

### `signal()` 会释放锁吗

不会。

调用 `signal()` 的线程仍然持有锁，必须等它调用 `unlock()` 后，等待线程才有机会获得锁。

------

### `signal()` 会让线程立即执行吗

不会。

它只把一个等待线程从条件队列转移到同步队列。

线程还要重新竞争锁。

------

### 为什么 `await()` 要写在 while 中

因为：

```text
可能虚假唤醒
条件可能再次被其他线程改变
被通知不代表条件一定成立
```

------

### `await()` 与 `wait()` 有什么区别

作用类似，但使用体系不同：

```text
wait/notify：
配合 synchronized 和对象 Monitor

await/signal：
配合 Lock 和 Condition
```

`Condition` 的主要优势是同一把锁可以创建多个条件队列。

------

### Condition 条件队列和 AQS 同步队列有什么区别

```text
条件队列：
线程曾经获得锁，
因为业务条件不满足而主动等待

同步队列：
线程想获得锁，
但是锁被其他线程持有
```

------

### 被 `signal()` 的线程去了哪里

从：

```text
Condition 条件队列
```

转移到：

```text
AQS 同步队列
```

然后重新等待获取锁。

------

### `signal()` 会保存通知吗

不会。

Condition 中没有等待线程时调用 `signal()`，通知不会被保存供未来线程使用。

因此必须依赖共享状态配合 while 检查。

------

## 50. 最终记忆口诀

```text
Lock 管互斥
Condition 管条件
await：
持锁进入
加入条件队列
完全释放锁
被通知后进入同步队列
重新抢到锁后才返回
signal：
必须持锁
条件队列转同步队列
不立即释放锁
不保证对方立即执行
signalAll：
全部转入同步队列
但仍然逐个竞争锁

while (!条件成立) {
    condition.await();
}
先改变共享状态
再 signal 或 signalAll

管理独立的条件等待队列
```

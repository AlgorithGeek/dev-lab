## 为什么废弃简述

这三个已经废弃的方法：

- `stop()`
- `suspend()`
- `resume()`

它们都属于 `Thread` 类，但现在都 **不推荐使用**，因为它们太危险

核心结论先放前面：

- stop()：强行杀死线程，可能导致数据写一半，状态混乱。
- suspend()：强行暂停线程，但不释放锁，容易死锁。
- resume()：恢复 suspend 的线程，但和 suspend 配合很容易出问题。



## `stop()` 方法

### `stop()` 为什么废弃？

`stop()` 的作用是：`t.stop();`

强制停止线程。

听起来很爽：我不想让你跑了，你立刻停。

但问题是：**它停得太粗暴了**



### `stop()` 会强制结束线程

假设线程正在执行：

```java
synchronized (lock) {
    user.setName("张三");
    user.setAge(18);
}
```

如果执行到一半时，外部调用：

```java
t.stop();
```

可能发生这种情况：

- name 已经改成了 张三

  age 还没来得及改

  线程突然死了

于是对象处于一种“半更新”的状态



### `stop()` 会释放锁，但数据可能坏了

这个点很重要。

`stop()` 不只是让线程停，它还可能让线程释放它持有的锁。

假设线程 A 正在同步代码块里修改共享数据：

```java
synchronized (lock) {
    account.balance -= 100;
    account.log = "扣款成功";
}
```

如果刚执行完：

```
account.balance -= 100;
```

还没执行：

```
account.log = "扣款成功";
```

线程被 `stop()` 强杀了。

然后锁被释放，其他线程进来看到的就是一个不完整状态：

```
钱扣了
日志没写
业务状态乱了
```

所以 `stop()` 的危险不是“停线程”本身，而是：

```
它可能在任意位置把线程杀掉，让共享对象处于不一致状态。
```



### `stop()` 的本质问题

正常停止线程应该是：

- 线程自己检查到该停了
- 然后收尾资源
- 然后安全退出

而 `stop()` 是：

- 外部强行把你干掉
- 不管你正在干什么
- 不管你数据有没有改完
- 不管你资源有没有释放好

所以它被废弃了



### 应该用什么代替 `stop()`？

用 `interrupt()`

比如：

```java
Thread t = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        System.out.println("线程正在执行任务");
    }

    System.out.println("线程安全退出");
});

t.start();

Thread.sleep(1000);

t.interrupt();
```

这种方式的意思是：

- 外部通知线程：你该停了。
- 线程自己检查中断标记，然后自己决定安全退出。

这就比 `stop()` 安全很多



### 如果线程里有 `sleep()`

```java
Thread t = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        try {
            Thread.sleep(1000);
            System.out.println("执行任务");
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    System.out.println("线程安全退出");
});
```

这里 catch 里重新：

```java
Thread.currentThread().interrupt();
```

是为了恢复中断标记，让外层 while 能检测到线程应该退出。



## `suspend()` 方法

### `suspend()` 是干嘛的？

`suspend()` 的作用是：`t.suspend();`

暂停线程。

听起来也很正常：我先让这个线程暂停一下。

但它最大的问题是：`suspend()` 暂停线程时，不会释放锁。

这就非常危险。



### `suspend()` 为什么容易死锁？

看这个例子：

```java
public class SuspendDemo {
    private static final Object lock = new Object();

    public static void main(String[] args) throws InterruptedException {
        Thread t = new Thread(() -> {
            synchronized (lock) {
                System.out.println("子线程拿到锁");

                while (true) {
                    // 模拟一直执行
                }
            }
        });

        t.start();

        Thread.sleep(1000);

        t.suspend();

        synchronized (lock) {
            System.out.println("main 拿到锁");
        }
    }
}
```

过程是：

```
子线程拿到 lock
main 调用 t.suspend()
子线程被暂停
但是子线程没有释放 lock

main 想进入 synchronized(lock)
main 拿不到 lock
main 等锁

子线程被暂停着，不继续执行，也不释放锁
main 又卡住了
```

结果：死锁



### 重点

`suspend()` 最危险的地方就是：

- 它可以在目标线程持有锁的时候，把目标线程暂停。

  而暂停之后，锁还在目标线程手里

其他线程如果需要这把锁，就可能永远等不到



## `resume()` 方法

### `resume()` 是干嘛的？

`resume()` 是用来恢复被 `suspend()` 暂停的线程

```
t.resume();
```

它和 `suspend()` 是一对：

```
t.suspend(); // 暂停
t.resume();  // 恢复
```

但是因为 `suspend()` 本身危险，所以 `resume()` 也跟着废弃了





### `resume()` 还有一个问题：可能错过恢复时机

假设线程 A 要等别人恢复它

线程 B 负责调用：

```
t.resume();
```

如果调用顺序错了，比如：

```
线程B 先调用 resume()
线程A 后调用 suspend()
```

那就尴尬了。

因为 `resume()` 不是一个“持久信号”。

它不会说：我先记着，等你以后 suspend 了我再恢复你。

它只是当场恢复。

如果当场线程还没暂停，这个 `resume()` 就相当于白调用了。

后面线程再 `suspend()`，就可能没人恢复它了。



## `suspend()` / `resume()` 联合

### 应该用什么代替？

一般用更安全的协作方式

比如用一个标志位配合 `wait()` / `notify()`

```java
public class PauseDemo {
    private static final Object lock = new Object();
    private static boolean paused = false;
    private static boolean stopped = false;

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            while (!stopped) {
                synchronized (lock) {
                    while (paused && !stopped) {
                        try {
                            lock.wait();
                        } catch (InterruptedException e) {
                            Thread.currentThread().interrupt();
                            return;
                        }
                    }
                }

                System.out.println("线程正在工作");

                try {
                    Thread.sleep(500);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    return;
                }
            }

            System.out.println("线程结束");
        });

        worker.start();

        Thread.sleep(1000);

        synchronized (lock) {
            paused = true;
            System.out.println("暂停线程");
        }

        Thread.sleep(2000);

        synchronized (lock) {
            paused = false;
            lock.notifyAll();
            System.out.println("恢复线程");
        }

        Thread.sleep(1000);

        stopped = true;
        worker.interrupt();
    }
}
```

这个思路是：

```
不是外部强行暂停线程，
而是线程自己在合适的位置检查 paused，
如果需要暂停，就自己 wait()。
```

这样线程会在安全的位置暂停，而且 `wait()` 会释放锁

比 `suspend()` 安全很多





## 三个方法对比

| 方法        | 原本作用     | 为什么危险                                          |
| ----------- | ------------ | --------------------------------------------------- |
| `stop()`    | 强制停止线程 | 可能在线程修改数据一半时杀死它，导致状态不一致      |
| `suspend()` | 强制暂停线程 | 暂停时不释放锁，容易死锁                            |
| `resume()`  | 恢复暂停线程 | 和 `suspend()` 配合容易错过恢复时机，也依赖危险机制 |



## 正确思想

Java 现在更推荐的线程控制思想是：

- 不要强行控制线程。
- 要通知线程，让线程自己在安全位置退出、暂停、恢复。

也就是：

- 粗暴控制：stop / suspend / resume
- 协作控制：interrupt / 标志位 / wait-notify / Lock-Condition / 并发工具类

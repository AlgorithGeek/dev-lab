## `notify()` / `notifyAll()`

它们俩都是配合 `wait()` 用的，核心作用是：唤醒正在某个锁对象上 wait 的线程

> `notify()` / `notifyAll()` 唤醒的只是一类线程：
>
> **在同一个锁对象上调用过 `wait()`，并因此进入等待队列的线程**



### 它们是谁的方法？

和 `wait()` 一样，`notify()`、`notifyAll()` 都是 `Object` 的方法，不是 `Thread` 的方法

也就是说，任何对象都有这几个方法：

```java
lock.wait();
lock.notify();
lock.notifyAll();
```

因为它们都是围绕“锁对象”工作的



### `notify()` 是干嘛的？

`lock.notify();`

意思是：从正在 `lock` 这个对象上 `wait()` 的线程里，随机/任意唤醒一个正在 `lock` 这个对象上 `wait()` 的线程

注意是：唤醒一个. 不是全部

比如：

```java
synchronized (lock) {
    lock.notify();
}
```

它唤醒的是：

```java
synchronized (lock) {
    lock.wait();
}
```

这种在同一个 `lock` 上等待的线程



### `notifyAll()` 是干嘛的？

`lock.notifyAll();`

意思是：唤醒所有正在 `lock` 这个对象上 `wait()` 的线程

比如有 5 个线程都在：

```java
synchronized (lock) {
    lock.wait();
}
```

这时候另一个线程调用：

```java
synchronized (lock) {
    lock.notifyAll();
}
```

这 5 个等待线程都会被唤醒

但是注意：

> 被唤醒，不等于一起执行。

它们还要重新抢 `lock` 锁

同一时间仍然只有一个线程能进入 `synchronized(lock)` 继续执行



### `notify()` 和 `notifyAll()` 必须在 synchronized 里面调用

错误写法：`lock.notify();`

这样会报：`IllegalMonitorStateException`

正确写法：

```java
synchronized (lock) {
    lock.notify();
}
```

或者：

```java
synchronized (lock) {
    lock.notifyAll();
}
```

原因是：你必须先持有 `lock` 这把锁，才能在 `lock` 上 `notify / notifyAll`

也就是：拿哪把锁，才能通知哪把锁上的等待线程



### `notify()` 不会立刻释放锁

这个你前面已经问过了，这里再巩固一下

```java
synchronized (lock) {
    lock.notify();

    System.out.println("我还在同步代码块里");
}
```

执行完：`lock.notify();`

之后，当前线程还持有 `lock`

它不会因为调用了 `notify()` 就立刻释放锁

真正释放锁的时机是：`}`

也就是退出 `synchronized` 代码块的时候

所以流程是：

- 线程A：`lock.wait()`，释放 `lock`，挂起等待



- 线程B：进入 `synchronized(lock)`，拿到 `lock`

- 线程B：`lock.notify()`，唤醒线程A
- 线程B：继续执行同步代码块
- 线程B：退出 `synchronized`，释放 `lock`



- 线程A：重新竞争 `lock`
- 线程A：抢到 `lock` 后，`wait()` 返回
- 线程A：继续执行 `wait` 后面的代码



### 被 notify 唤醒后，线程去哪了？

假设线程 A 正在：

```java
synchronized (lock) {
    lock.wait();
}
```

这时线程 A 在 `lock` 的等待队列里

线程 B 调用：

```java
synchronized (lock) {
    lock.notify();
}
```

线程 A 会被唤醒

但是它不是马上继续执行，而是：从 wait 等待队列出来，去重新竞争 lock。

如果线程 B 还没退出同步代码块，线程 A 抢不到锁，就只能等

等线程 B 退出同步代码块释放锁后，线程 A 才有机会重新拿到锁

拿到锁以后：`lock.wait();`

这个方法才真正返回。

然后线程 A 才继续执行后面的代码



### `notify()` 和 `notifyAll()` 的区别

| 方法          | 作用             |
| ------------- | ---------------- |
| `notify()`    | 唤醒一个等待线程 |
| `notifyAll()` | 唤醒所有等待线程 |

但是这句话还不够完整。

更准确是：

- notify() 从当前锁对象的 wait 等待队列中随机/任意唤醒一个线程
- notifyAll() 唤醒当前锁对象 wait 等待队列中的所有线程

注意是“当前锁对象”

比如：`lock1.wait();`

只能被：`lock1.notify();`

或者：`lock1.notifyAll();`

唤醒。



不能被：`lock2.notify();`

唤醒。



因为它们不是同一个锁对象



### `notify()` 唤醒的是哪个线程？

这个很重要：notify() 唤醒哪个线程，不由你控制

比如现在有三个线程都在 `lock.wait()`：

```
线程A 等待中
线程B 等待中
线程C 等待中
```

你调用：`lock.notify();`

可能唤醒 A，也可能唤醒 B，也可能唤醒 C

你不能指定：我要唤醒线程B

`notify()` 没有这个能力

所以如果你业务里有不同类型的等待线程，用 `notify()` 就容易叫错人





### 为什么很多时候推荐 `notifyAll()`？

因为 `notify()` 可能唤醒“条件不满足”的线程

举个例子：生产者消费者

桌子上只能放一个食物：

```
消费者：没有食物就 wait
生产者：有食物就 wait
```

如果你有多个生产者、多个消费者，用 `notify()` 可能出现问题

比如：

```
桌子上没有食物
消费者1 在等
消费者2 在等
生产者1 生产了食物
生产者1 调用 notify()
```

这时候如果唤醒的是消费者，那很好

但在更复杂的场景里，如果唤醒了一个不该执行的线程，它醒来以后发现条件不满足，又继续 `wait()`，可能导致真正该醒的线程没醒

所以很多实际代码更推荐：`lock.notifyAll();`

然后让所有线程醒来后重新判断条件：

```java
while (!condition) {
    lock.wait();
}
```

条件满足的线程继续执行

条件不满足的线程继续等待



### 为什么 wait 要配 while？

因为 `notifyAll()` 会唤醒很多线程，但不是每个线程醒来后都能干活。

标准写法是：

```java
synchronized (lock) {
    while (!条件满足) {
        lock.wait();
    }

    // 条件满足，执行逻辑
}
```

不要写成：

```java
synchronized (lock) {
    if (!条件满足) {
        lock.wait();
    }

    // 执行逻辑
}
```

因为醒来以后，条件可能还是不满足

所以要用 `while` 重新检查



### notify 会不会唤醒 BLOCKED 线程？

不会

这个要强调一下: `notify / notifyAll` **只唤醒因为 `wait()` 进入等待的线程**

如果一个线程是因为进不了：

```java
synchronized (lock) {
}
```

而处于 `BLOCKED` 状态，`notify()` 不负责唤醒它。

`BLOCKED` 线程只需要等当前持锁线程释放锁。

所以：

- wait 的线程靠 notify / notifyAll 唤醒。

  `BLOCKED` 的线程靠锁释放后重新竞争。

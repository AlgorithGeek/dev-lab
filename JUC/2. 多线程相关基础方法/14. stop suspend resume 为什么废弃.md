## 了解 `stop` / `suspend` / `resume` 为什么废弃

这几个方法现在都不推荐使用，属于应该了解但不要在新代码里使用的方法。

它们的问题不是“不能用”，而是“太危险”。



### `stop()` 为什么危险？

`stop()` 会强制停止线程。

听起来很方便，但问题是：它可能在线程执行到一半的时候，直接把线程干掉。

更危险的是：它会让线程突然释放已经持有的锁。

比如一个线程正在修改共享对象：

```java
synchronized (lock) {
    user.setName("张三");
    user.setAge(18);
}
```

如果线程刚执行完 `setName()`，还没来得及执行 `setAge()`，就被 `stop()` 强行停止了。

这时候对象可能处于一种“只改了一半”的状态。

锁还被释放了，其他线程就可能读到这个不完整的数据。

所以 `stop()` 的核心问题是：破坏数据一致性。



### `suspend()` 为什么危险？

`suspend()` 会把线程挂起。

问题是：如果线程是在拿着锁的时候被挂起，它不会释放锁。

```java
synchronized (lock) {
    Thread.currentThread().suspend();
}
```

这个线程挂起了，但 `lock` 还在它手里。

其他线程如果也需要这把锁，就会一直等。

如果负责调用 `resume()` 的线程也刚好需要这把锁，那就可能死锁。

所以 `suspend()` 的核心问题是：容易带着锁一起挂起，造成死锁。



### `resume()` 为什么也不安全？

`resume()` 是用来恢复 `suspend()` 挂起的线程。

但它和 `suspend()` 配合时有一个经典问题：信号可能丢失。

比如 `resume()` 先执行了，而目标线程还没来得及 `suspend()`。

后面目标线程再 `suspend()`，就可能再也没人唤醒它。

所以 `resume()` 的核心问题是：和 `suspend()` 配合时很容易出现时序问题。



### 那应该怎么停止线程？

更推荐用：`interrupt()` + 线程自己检查状态。

```java
Thread t = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        // 正常工作
    }

    System.out.println("线程自己正常结束");
});

t.start();
t.interrupt();
```

这种方式不是强制把线程砍掉，而是通知线程：你该结束了。

然后线程在合适的位置自己退出。



### 一句话总结

- `stop()`：强制停止，容易破坏数据一致性
- `suspend()`：挂起但不释放锁，容易死锁
- `resume()`：唤醒时机容易丢，容易造成线程永远挂起
- 新代码里优先用 `interrupt()`、条件变量、JUC 工具类来控制线程协作

## `yield()`

这个方法比 `sleep()` 更“虚”，因为它不是强制控制线程，而是给线程调度器一个 **建议** , 它也是 `Thread` 的静态方法

### 作用

`yield()` 的作用是：**当前执行这个代码的线程** 主动让出一下 CPU，告诉线程调度器：我愿意先暂停一下，让其他线程有机会执行

`yield()` 只是“让一下”，不是“必须让成功”



### 例子

```java
public class YieldDemo {
    public static void main(String[] args) {
        Runnable task = () -> {
            for (int i = 1; i <= 5; i++) {
                System.out.println(Thread.currentThread().getName() + "：" + i);

                Thread.yield();
            }
        };

        Thread t1 = new Thread(task, "线程A");
        Thread t2 = new Thread(task, "线程B");

        t1.start();
        t2.start();
    }
}
```

> 可能输出：
>
> 线程A：1
>
> 线程B：1
>
> 线程A：2
>
> 线程B：2
>
> 线程A：3
>
> 线程B：3
>
> 线程A：4
>
> 线程B：4
>
> 线程A：5
>
> 线程B：5

> 但也可能输出：
>
> 线程A：1
>
> 线程A：2
>
> 线程A：3
>
> 线程B：1
>
> 线程A：4
>
> 线程B：2
>
> 线程B：3
>
> 线程A：5
>
> 线程B：4
>
> 线程B：5

为什么？因为 `yield()` 不保证一定切换线程



### `yield()` 不会让线程进入阻塞状态

这是它和 `sleep()` 的一个重要区别。

调用：`Thread.sleep(1000);`

当前线程会进入：`TIMED_WAITING`, 也就是限时等待状态



但是调用：`Thread.yield();`

当前线程还是：`RUNNABLE`

它只是从“正在运行”变成“愿意重新参与 CPU 竞争”



### `yield()` 不会释放锁

和 `sleep()` 一样，`yield()` 也不会释放锁

比如：

```java
public class YieldLockDemo {
    private static final Object lock = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (lock) {
                System.out.println("线程A拿到锁");

                Thread.yield();

                System.out.println("线程A执行结束");
            }
        }, "线程A");

        Thread t2 = new Thread(() -> {
            synchronized (lock) {
                System.out.println("线程B拿到锁");
            }
        }, "线程B");

        t1.start();
        t2.start();
    }
}
```

即使线程 A 调用了：`Thread.yield();`

它也还在：`synchronized (lock)`

里面，所以它不会释放 `lock` 这把锁

所以线程 B 仍然要等线程 A 退出同步代码块后，才能拿到锁

> 这里我提出了一个很有意思的问题：
>
> 如果操作系统真的听从了这个“建议”，切换了过去，那么是不是就卡死了？
>
> - 答：
>
>   即使 `yield()` 真的让 CPU 切换到了线程 B，线程 B 也拿不到锁。
>
>   线程 B 会进入 `BLOCKED` 状态，然后 CPU 还会再切回线程 A，让线程 A 继续执行并释放锁。
>
>   > 当线程 A 执行到：`Thread.yield();`
>   >
>   > 此时线程 A 的状态可以理解为：持有 lock 锁，但愿意让出 CPU
>   >
>   > 线程 B 开始执行：
>   >
>   > ```java
>   > synchronized (lock) {
>   >     System.out.println("线程B拿到锁");
>   > }
>   > ```
>   >
>   > 它想进入 `synchronized (lock)`
>   >
>   > 但是问题是：
>   >
>   > ```
>   > lock 还在线程 A 手里
>   > ```
>   >
>   > 所以线程 B 进不去。
>   >
>   > 于是线程 B 会变成：`BLOCKED`
>   >
>   > 它不是一直占着 CPU 傻等，而是进入阻塞状态，等线程 A 释放锁
>   >
>   > 然后 CPU 怎么办？
>   >
>   > 既然线程 B 拿不到锁，进入 `BLOCKED` 了，那么它暂时不能继续执行。
>   >
>   > 这时候 CPU 会继续找可以运行的线程。
>   >
>   > 线程 A 虽然刚才调用了 `yield()`，但它并没有睡眠，也没有阻塞，它仍然是：`RUNNABLE`
>   >
>   > 所以调度器很可能又切回线程 A
>   >
>   > 然后线程 A 继续执行：
>   >
>   > ```java
>   > System.out.println("线程A执行结束");
>   > ```
>   >
>   > 接着退出 `synchronized` 代码块
>   >
>   > 一退出这里：
>   >
>   > ```java
>   > synchronized (lock) {
>   >     ...
>   > }
>   > ```
>   >
>   > 线程 A 就释放了 `lock`
>   >
>   > 然后线程 B 才有机会拿到锁，打印：
>   >
>   > ```java
>   > 线程B拿到锁
>   > ```



### `yield()` 和 `sleep()` 的区别

| 对比点       | `sleep()`                 | `yield()`            |
| ------------ | ------------------------- | -------------------- |
| 作用         | 当前线程睡一段时间        | 当前线程让出一下 CPU |
| 是否指定时间 | 可以指定时间              | 不能指定时间         |
| 状态         | `TIMED_WAITING`           | 仍然是 `RUNNABLE`    |
| 是否释放锁   | 不释放                    | 不释放               |
| 是否一定暂停 | 是，至少暂停一段时间      | 不一定               |
| 是否抛异常   | 抛 `InterruptedException` | 不抛异常             |



### 为什么 `yield()` 不抛异常？

因为 `yield()` 不会让线程进入真正的等待、睡眠、阻塞状态

它只是告诉调度器：我愿意重新排队，让别人有机会执行。

所以它不像 `sleep()` 那样存在“睡到一半被打断”的问题。

因此它不抛：`InterruptedException`



### `yield()` 和线程优先级的关系

一般来说，`yield()` 更倾向于让给 **同优先级或更高优先级** 的线程

比如当前线程优先级是 5，它调用 `yield()`，调度器可能更愿意让优先级 5 或更高的线程执行

但是这个行为也不绝对

因为 Java 线程调度最终依赖 JVM 和操作系统

所以不能写出这种逻辑：

```java
Thread.yield();
// 我认为这里之后一定轮到线程B执行
```

这是错误的



### `yield()` 的实际开发使用多吗？

很少。实际项目里很少直接用 `Thread.yield()`



原因是：

1. 它不稳定，不保证效果。

2. 它依赖操作系统调度。

3. 它不适合控制业务流程。

4. 代码可读性一般。



它更多是学习线程调度时用来理解：

- 线程不是你想让谁执行，谁就一定执行
- 最终还是看 CPU 调度

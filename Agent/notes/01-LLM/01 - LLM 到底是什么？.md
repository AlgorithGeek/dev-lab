# 01 - LLM 到底是什么？

> AI Agent 学习笔记 · LLM 基础
>
> 这一篇不讨论具体框架，也不讨论 Tool Calling、RAG、MCP。
>
> 目标只有一个：
>
> **真正搞清楚我们以后每天调用的那个“大模型”，到底是个什么东西。**

------

# 一、先给 LLM 一个最简单的定义

LLM 的全称是：

**Large Language Model**

中文一般叫：

**大语言模型 / 大型语言模型**

拆开来看：

```text
Large
+
Language
+
Model
```

分别代表：

- `Large`：模型规模非常大，通常拥有大量参数，并使用海量数据进行训练。
- `Language`：主要处理语言，也就是文本、代码、自然语言等符号序列。
- `Model`：它本质上是一个数学模型。

所以可以先得到一个简单定义：

> **LLM 是一种通过大量文本数据训练出来、能够理解和生成语言的大规模机器学习模型。**

例如：

- GPT
- DeepSeek
- Claude
- Gemini
- Qwen

本质上都属于这一类东西。

------

# 二、但这个定义还是太抽象

如果站在程序员角度，我们真正关心的问题应该是：

> 我给 LLM 一句话，它内部到底干了什么？

比如你输入：

```text
Java 中 HashMap 为什么线程不安全？
```

模型可能回答：

```text
HashMap 本身没有提供并发访问时的同步机制，
多个线程同时进行 put、resize 等操作时可能产生数据竞争……
```

看起来非常像：

```text
你问了一个问题
↓
AI 理解问题
↓
AI 在脑子里找知识
↓
AI 想了一下
↓
AI 回答
```

但从底层工作方式来看，并不是这么简单。

LLM 最核心的工作实际上可以概括成：

> **根据已经看到的内容，预测接下来最可能出现什么 Token。**

也就是说，LLM 最底层做的事情，其实是：

```text
已有内容
↓
计算概率
↓
预测下一个 Token
```

然后：

```text
已有内容 + 新 Token
↓
再次计算
↓
预测下一个 Token
```

不断重复。

------

# 三、什么叫“预测下一个 Token”？

先暂时把 Token 理解成：

> 模型处理文本时使用的基本单位。

后面会有专门一篇讲 Token。

现在只需要理解一个大概。

比如：

```text
我喜欢吃苹果
```

模型内部并不一定直接按照：

```text
我
喜
欢
吃
苹
果
```

处理。

也不一定按照：

```text
我 / 喜欢 / 吃 / 苹果
```

处理。

它会经过专门的 Tokenizer，把文字转换成 Token。

暂时可以把它抽象成：

```text
[我]
[喜欢]
[吃]
[苹果]
```

然后假设你输入：

```text
我今天早上吃了一个
```

模型开始计算：

```text
下一个 Token 是什么？
```

可能得到：

```text
苹果      30%
鸡蛋      20%
面包      15%
包子      10%
香蕉       5%
……
```

然后模型从这些可能性中选出一个。

假设选中了：

```text
苹果
```

此时文本变成：

```text
我今天早上吃了一个苹果
```

模型继续预测：

```text
下一个 Token 是什么？
```

可能：

```text
。        50%
，然后     15%
，因为     5%
和         3%
……
```

于是继续生成。

整个过程不断重复：

```text
输入
↓
预测 Token
↓
加入上下文
↓
预测 Token
↓
加入上下文
↓
预测 Token
↓
……
```

最终就形成了一整段回答。

------

# 四、那问题来了：预测下一个词，怎么能变得这么聪明？

这是理解 LLM 最大的一个坎。

很多人第一次听到：

> “LLM 本质上就是预测下一个 Token。”

会产生一种感觉：

> 就这？？？

因为“预测下一个词”听起来实在太简单了。

甚至像手机输入法。

比如：

```text
今天晚上我们一起
```

输入法可能预测：

```text
吃饭
```

那为什么 ChatGPT、DeepSeek 却能够：

- 写代码
- 解释 JVM
- 分析 Bug
- 写文章
- 翻译
- 数学推理
- 分析需求
- 制定计划
- 调用工具
- 辅助编程

关键在于：

> **为了准确预测下一个 Token，模型必须学习非常复杂的语言规律以及隐藏在语言背后的知识结构。**

举个例子。

如果训练数据里经常出现：

```text
北京是中国的首都。
```

模型慢慢就会学到：

```text
北京
中国
首都
```

这些概念之间存在非常强的关系。

再比如大量 Java 代码里出现：

```java
Map<String, Object> map = new HashMap<>();
```

以及：

```java
ConcurrentHashMap
```

以及大量文章讨论：

```text
HashMap 不是线程安全的。
```

模型训练久了以后，就会逐渐形成：

```text
HashMap
Map
线程安全
ConcurrentHashMap
Java
并发
```

这些概念之间的内部关联。

所以真正发生的是：

```text
为了预测语言
↓
被迫学习语言规律
↓
为了理解语言规律
↓
被迫学习大量世界知识
↓
学习概念之间的关系
↓
形成复杂内部表示
```

于是最终产生了非常强的通用能力。

------

# 五、一个非常关键的理解

可以把这个过程类比成人。

假设让你完成下面这句话：

```text
Java 中用于创建对象的关键字是 ______。
```

你会填：

```text
new
```

为什么？

因为你掌握了 Java。

再比如：

```text
HashMap 在多线程情况下不是 ______ 的。
```

你大概率填写：

```text
线程安全
```

这时候表面上：

> 你也只是在预测下一个词。

但是为了预测正确，你必须拥有：

```text
Java知识
+
HashMap知识
+
并发知识
```

所以：

> **“预测下一个 Token”描述的是模型的输出机制，并不意味着模型内部只做了一件简单的事情。**

这是非常重要的一点。

------

# 六、LLM 可以看成一个巨大的概率模型

传统 Java 代码通常更接近：

```java
if (score >= 60) {
    return "及格";
} else {
    return "不及格";
}
```

只要：

```text
score = 80
```

无论执行：

```text
1 次
100 次
10000 次
```

结果基本都是：

```text
及格
```

它是：

> **确定性的。**

------

而 LLM 不一样。

比如：

```text
给我取一个 Java 项目的名字。
```

第一次可能回答：

```text
CodeNest
```

第二次：

```text
JavaForge
```

第三次：

```text
DevSpring
```

这是因为模型内部存在：

```text
Token → 概率分布
```

例如：

```text
Code      20%
Dev       15%
Java      13%
Smart      8%
Spring     7%
……
```

然后根据：

- 模型本身
- Context
- Temperature
- Sampling 策略
- 其他参数

选择接下来生成什么。

所以 LLM 的一个非常重要的特点就是：

> **概率性。**

这也是为什么以后做 AI 工程时：

```text
“运行成功一次”
```

并不能证明系统可靠。

------

# 七、传统程序和 LLM 最大的区别

这一点非常重要。

## 传统 Java 程序

程序员提前写规则：

```java
if (age < 18) {
    return "未成年";
}

if (age >= 18 && age < 60) {
    return "成年人";
}

return "老年人";
```

流程：

```text
程序员定义规则
↓
程序执行规则
↓
得到结果
```

所以：

```text
输入相同
+
程序相同
=
结果基本相同
```

------

## LLM

你不会写：

```java
if (question.contains("HashMap")) {
    ...
}

if (question.contains("Spring")) {
    ...
}

if (question.contains("Redis")) {
    ...
}
```

而是：

```text
用户问题
↓
训练好的模型
↓
模型根据内部学习到的规律推理
↓
生成结果
```

这里的规则不是程序员一条一条写进去的。

而是：

> **通过训练从大量数据中学习出来的。**

------

# 八、可以这样理解两者

传统程序更像：

```text
规则
+
数据
=
结果
```

LLM 更像：

```text
训练得到的复杂模型
+
当前 Context
=
概率性输出
```

或者：

```text
传统程序：

人写规则
↓
机器执行
```

而：

```text
机器学习模型：

人提供训练机制和数据
↓
机器学习规律
↓
利用规律完成任务
```

------

# 九、为什么 LLM 不像数据库？

这是以后做 Agent 特别重要的认知。

假设数据库里：

```sql
SELECT salary
FROM employee
WHERE id = 1001;
```

数据库返回：

```text
12000
```

只要数据没变：

```text
查 100 次
```

结果都是：

```text
12000
```

因为数据库的职责是：

> **存储和准确读取数据。**

------

LLM 完全不是这种东西。

比如问：

```text
我们公司的用户 1001 工资是多少？
```

如果模型没有连接你的数据库：

它根本不知道。

它可能：

```text
拒绝回答
```

也可能：

```text
猜
```

甚至可能非常自信地：

```text
胡说一个数字。
```

因为 LLM 的工作不是：

```text
从某个精确位置读取事实
```

而是：

```text
根据上下文和训练规律生成最合理的语言
```

所以：

> **LLM 不是数据库。**

这是以后理解：

```text
RAG
Tool Calling
Agent
```

的地基。

------

# 十、LLM 为什么会“知道”很多知识？

这里需要区分两种知识。

## 第一种：训练时学到的知识

模型训练的时候看过大量：

```text
书籍
网页
代码
文章
文档
对话
公开资料
……
```

训练过程中，很多规律被压进模型参数里。

所以它能够回答：

```text
Java 是什么？
HashMap 是什么？
北京是哪个国家的首都？
```

这些知识可以粗略称为：

> **参数知识 / Parametric Knowledge**

------

## 第二种：当前 Context 提供的知识

比如你告诉模型：

```text
我们公司内部规定：
所有广告预算超过 10000 元的修改必须经过主管审核。
```

模型原本不知道这条规定。

但是这一轮 Context 里有。

于是问：

```text
我想把预算改成 20000，需要审核吗？
```

模型就可以回答：

```text
需要。
```

这不是因为：

> 模型突然永久学会了公司制度。

而是：

```text
你把规则放进了 Context
↓
模型基于 Context 推理
```

这就是以后 RAG 非常重要的基础。

------

# 十一、模型参数到底是什么？

现在不用理解数学细节。

先建立概念。

LLM 内部存在大量：

```text
Parameters
```

也就是：

> 参数。

可以粗略想象成：

```text
无数个数字
```

模型训练的过程，本质上就是不断调整这些数字。

例如：

```text
0.12784
-0.93211
1.33721
0.00381
……
```

这些数字单独看毫无意义。

但是数十亿、数百亿甚至更多参数组合起来，就形成了一个极其复杂的数学系统。

训练可以粗略理解：

```text
给模型文本
↓
让模型预测
↓
预测错了
↓
计算误差
↓
调整参数
↓
再预测
↓
再调整
↓
……
```

经过海量数据和海量计算以后：

```text
参数逐渐包含大量语言规律和知识关系
```

最终得到：

```text
训练完成的模型
```

------

# 十二、训练好的 LLM 是什么状态？

可以把它想象成：

```text
一个已经训练完成的巨大数学函数
```

非常粗略地表示：

```text
Output = LLM(Input)
```

但实际输入还包括：

```text
System Prompt
User Message
Conversation History
Tool Result
RAG Context
Memory
……
```

所以以后 Agent 中实际更像：

```text
Output =
LLM(
    System Prompt,
    User Message,
    History,
    RAG,
    Tool Results,
    State
)
```

这也是为什么以后会学习：

> **Context Engineering**

因为你给模型什么信息，会极大影响它生成什么结果。

------

# 十三、LLM 到底有没有“记忆”？

默认情况下：

> **模型本身并不会像人一样自动记住你之前所有事情。**

比如程序第一次调用：

```text
User:
我叫张三。
```

模型回答：

```text
你好，张三。
```

请求结束。

下一次你重新发一个完全独立的 API 请求：

```text
我叫什么？
```

如果没有重新把：

```text
我叫张三
```

发给模型，

模型通常是不知道的。

为什么？

因为模型 API 一般更接近：

```text
Request
↓
Inference
↓
Response
↓
结束
```

下一次：

```text
新的 Request
↓
新的 Inference
```

所以所谓：

```text
Chat Memory
```

很多时候其实是你的程序在做：

```text
第一次：

User: 我叫张三
Assistant: 你好
```

保存起来。

下一次请求：

```text
History:
User: 我叫张三
Assistant: 你好

Current User:
我叫什么？
```

再一起发给模型。

于是模型：

```text
你叫张三。
```

看起来：

> AI 有记忆。

实际上可能是：

> **应用程序重新把历史信息提供给模型了。**

这就是以后学习：

```text
Memory
Context
State
```

的基础。

------

# 十四、LLM 和搜索引擎有什么区别？

搜索引擎：

```text
用户问题
↓
搜索互联网索引
↓
找到网页
↓
返回相关内容
```

核心能力：

> **Retrieval / 检索**

比如搜索：

```text
Spring Boot 4 最新版本
```

搜索引擎会寻找真实网页。

------

LLM：

```text
用户问题
↓
根据模型参数 + Context
↓
生成回答
```

核心能力：

> **Generation / 生成**

------

所以可以粗略区分：

```text
搜索引擎：
帮你找东西

LLM：
帮你生成东西
```

当然现在很多 AI 产品会：

```text
Search
+
LLM
```

组合起来。

流程：

```text
先搜索
↓
拿到真实资料
↓
交给 LLM
↓
LLM 整理和回答
```

这已经非常接近 RAG 的思想。

------

# 十五、LLM 和传统搜索最大的差异

比如问：

```text
Java synchronized 有什么作用？
```

搜索引擎可能返回：

```text
Oracle 文档
博客
Stack Overflow
教程
```

然后：

> 你自己阅读。

LLM 可以：

```text
综合已有知识
↓
重新组织
↓
根据你的水平解释
```

甚至你继续说：

```text
还是没懂，举个库存扣减的例子。
```

它可以重新解释。

这就是生成式模型非常强的地方。

------

# 十六、为什么 LLM 会产生幻觉？

现在只讲核心，后面会有单独一篇。

因为模型的目标并不是：

```text
保证每句话都是真实事实
```

它更接近：

```text
根据当前上下文
生成最合理的下一段内容
```

所以如果你问：

```text
请介绍一本根本不存在的书。
```

某些情况下模型可能生成：

```text
作者
出版日期
内容简介
章节
```

甚至看起来非常真实。

原因在于：

> **语言合理 ≠ 事实真实。**

例如：

```text
张三教授于 2018 年出版《Java并发宇宙》……
```

从语言模式上：

```text
人名
+
年份
+
书名
+
出版
```

完全符合真实世界文章的写法。

但：

```text
事实可能根本不存在。
```

所以以后做 Agent 时绝对不能：

```text
“LLM 说数据库里有这条数据，
那肯定就有。”
```

必须：

```text
LLM
↓
Tool
↓
数据库
↓
真实结果
```

------

# 十七、这就是 Agent 为什么需要 Tool

现在你应该已经能看到一点后面的路线了。

假设用户问：

```text
帮我看看 campaign 123 今天花了多少钱。
```

LLM 自己只有：

```text
语言能力
+
训练知识
```

它根本不知道：

```text
你们数据库今天的真实广告数据。
```

怎么办？

让它调用 Tool：

```text
用户
↓
LLM
↓
“我需要 queryCampaignMetrics”
↓
Java
↓
数据库
↓
真实数据：¥5321
↓
LLM
↓
“今天已经消耗 5321 元。”
```

于是：

```text
LLM
+
Tool
```

就突破了：

> 模型只能依靠自身参数知识的限制。

这就是 Agent 的第一个核心。

------

# 十八、这也是为什么需要 RAG

如果用户问：

```text
按照我们公司广告规范，这种情况应该怎么处理？
```

模型不知道公司内部文档。

于是：

```text
用户问题
↓
搜索内部知识库
↓
找到相关文档
↓
把文档提供给 LLM
↓
LLM 根据资料回答
```

也就是：

```text
LLM
+
Retrieval
```

这就是后面的 RAG。

------

# 十九、那 LLM 到底算不算“理解”？

这是一个容易陷入哲学争论的问题。

工程学习阶段没有必要钻进：

```text
AI 到底有没有意识？
AI 是否真正理解？
AI 是否拥有思想？
```

我们更关心：

> **它表现出了什么能力，以及这些能力是否足以解决任务。**

例如模型可以：

```text
读 Java 代码
↓
发现空指针风险
↓
解释为什么
↓
给修改方案
```

从工程角度：

```text
这个能力可以使用。
```

至于：

```text
它是不是和人类一样“真正理解”？
```

并不是当前 Agent 工程首先要解决的问题。

------

# 二十、那 LLM 到底有没有“思考”？

同样需要分开看。

从最底层输出机制：

```text
LLM 不断预测 Token。
```

但是在产生 Token 之前，模型内部会执行大量复杂计算。

一些现代模型还会：

```text
分解问题
推理
规划
检查
重新计算
```

因此现实中经常会使用：

```text
Reasoning Model
推理模型
```

这样的概念。

但从工程角度，不要陷入：

```text
“它到底算不算真的思考？”
```

这种语言争论。

更实用的理解是：

> **LLM 是一个能够基于输入进行复杂概率推理并生成结果的模型。**

------

# 二十一、为什么同一个模型有时候聪明，有时候很蠢？

因为最终表现取决于很多东西。

不只是：

```text
模型本身
```

而是：

```text
模型能力
+
Prompt
+
Context
+
问题表达
+
提供的数据
+
Tool
+
采样参数
+
任务难度
```

例如：

```text
帮我看看代码。
```

和：

```text
你是一名 Java 后端 Code Reviewer。

请重点检查：
1. 空指针
2. 并发问题
3. SQL 风险
4. 异常处理

请逐项输出。
```

即使模型相同，结果也可能差很多。

所以以后 AI 工程并不是：

> 找到最聪明的模型，然后全部结束。

还需要设计：

```text
Prompt
Context
Tools
RAG
Workflow
Evaluation
```

------

# 二十二、LLM 是不是知道整个互联网？

不是。

这是一个常见误区。

模型：

```text
不是 Google
```

也不是：

```text
互联网数据库镜像
```

训练过程中模型虽然可能使用过大量互联网文本，但最终留下来的主要是：

```text
参数
```

而不是：

```text
一个可以随时准确查询全部原始网页的数据库。
```

所以：

```text
模型可能知道某件事
```

不代表：

```text
模型能够给你精确恢复原始资料
```

更不代表：

```text
知识一定最新
```

因此最新信息通常需要：

```text
Web Search
RAG
API
Tool
```

来提供。

------

# 二十三、LLM 是否知道最新信息？

不一定。

假设一个模型训练数据截止：

```text
某个时间点
```

之后发生：

```text
新版本发布
公司政策变化
今天的股票价格
今天的天气
新的新闻
```

模型参数本身不可能凭空知道。

所以：

```text
“今天北京天气怎么样？”
```

严格来说不应该只依赖模型参数。

应该：

```text
LLM
↓
Weather API
↓
真实天气
```

这也是 Agent 的意义。

------

# 二十四、LLM 和 API 是两回事

这个概念要提前区分。

LLM 是：

```text
模型
```

例如：

```text
DeepSeek 某模型
GPT 某模型
Qwen 某模型
```

API 是：

> **你的程序访问模型的一种方式。**

例如：

```text
Java程序
↓
HTTP Request
↓
DeepSeek API
↓
LLM
↓
Response
```

所以：

```text
LLM ≠ API
```

就像：

```text
MySQL ≠ JDBC
```

JDBC 是你访问数据库的一种方式。

同样：

```text
模型 ≠ 模型 API
```

以后我们真正写 Java 时，操作的大多数其实是：

```text
模型提供商提供的 API
```

------

# 二十五、站在 Java 程序员角度理解 LLM

这个类比很重要。

你以前写：

```text
Spring Boot
↓
Google Ads API
↓
Google服务器
↓
JSON
↓
Java DTO
```

未来写：

```text
Spring Boot
↓
DeepSeek API
↓
DeepSeek服务器
↓
模型推理
↓
JSON
↓
Java对象
```

从调用层面看：

> **LLM API 首先就是一个第三方 HTTP 服务。**

这意味着你已经会很多东西了：

```text
HTTP
JSON
Request
Response
Authentication
Timeout
Retry
Error Handling
DTO
Logging
```

这些全部还能继续用。

真正新增的是：

```text
模型具有概率性
模型理解自然语言
模型可以生成内容
模型可以选择 Tool
模型需要 Context
模型可能幻觉
```

------

# 二十六、一个非常重要的认知：模型不是程序的主人

以后写 Agent 时容易产生一种错觉：

```text
AI 控制整个系统。
```

实际上更合理的架构应该是：

```text
你的应用程序
       │
       ├── 调用 LLM
       │
       ├── 管理 Tool
       │
       ├── 管理权限
       │
       ├── 管理 State
       │
       ├── 管理数据库
       │
       └── 决定什么行为真正允许执行
```

LLM 更像：

> **系统中的一个智能决策组件。**

而不是：

> 系统真正拥有最终执行权的人。

例如模型说：

```text
删除用户 123。
```

不能：

```text
模型说删除
↓
直接 DELETE
```

而应该经过：

```text
模型提出操作
↓
程序校验
↓
权限检查
↓
风险检查
↓
必要时人工确认
↓
真正执行
```

这个思想会贯穿整个 Agent 学习路线。

------

# 二十七、LLM 的优势到底是什么？

LLM 最大的优势不是：

```text
计算 1 + 1
```

传统代码干这个更可靠。

LLM 真正强的是处理：

> **非结构化、模糊、开放性的语言任务。**

例如：

```text
理解自然语言
总结文章
提取信息
分类文本
写代码
解释代码
分析需求
制定计划
根据自然语言决定调用哪个 Tool
```

这最后一条就是 Agent 极其重要的能力。

------

# 二十八、传统代码擅长什么？

传统代码擅长：

```text
精确
确定
可重复
规则明确
高速执行
```

比如：

```java
balance = balance - amount;
SELECT * FROM users WHERE id = 1;
if (permission == ADMIN) {
    ...
}
```

这些事情：

> **千万不要因为有了 LLM 就让 LLM 接管。**

------

# 二十九、LLM + 传统代码才是真正强大的地方

最佳情况往往不是：

```text
LLM 替代所有 Java
```

而是：

```text
              用户自然语言
                    │
                    ▼
                  LLM
                    │
           理解用户想干什么
                    │
                    ▼
              Java业务系统
                    │
          执行精确业务逻辑
                    │
                    ▼
                  数据
                    │
                    ▼
                  LLM
                    │
              整理成答案
```

也就是说：

```text
LLM
负责：
理解
判断
生成
推理

Java
负责：
执行
校验
权限
事务
数据
可靠性
```

这就是为什么：

> **Java 后端 + Agent**

其实是非常自然的组合。

现在终于可以把它们连起来。

只有 LLM：

```text

```

能力有限。

加入 Tool：

```text

 ↓

 ↓

 ↓

 ↓

```

加入 Memory：

```text

 ↓

```

加入 RAG：


# 三十二、理解 LLM 后，再看一个完整例子

用户：

```text
帮我分析一下 campaign 123 今天为什么 CPA 突然涨了。
```

仅靠 LLM：

```text
LLM：
可能是竞争加剧、素材疲劳、受众变化……
```

听起来合理。

但是：

> 全是猜测。

真正 Agent：

```text

↓

↓

↓

↓

↓

↓

↓

↓

```

这个案例特别重要。

你以后学 Agent，实际上就是不断解决：

> **LLM 自己做不到的事情，怎么通过软件工程给它补上。**


所以 LLM：

# 三十六、这一篇最核心的 10 句话

如果以后忘了整篇，只记住下面这些。

### 1

> **LLM 是通过大量数据训练得到的大规模语言模型。**

### 2

> **LLM 最底层的生成机制，可以理解为不断预测下一个 Token。**

### 3

> **“预测下一个 Token”并不意味着它很简单，因为为了预测准确，模型必须学习大量复杂语言规律和知识关系。**

### 4

> **LLM 是概率模型，因此输出天然具有一定不确定性。**

### 5

> **传统 Java 程序主要执行程序员明确编写的规则；LLM 的大量行为来自训练中学习到的规律。**

### 6

> **LLM 不是数据库，不能把它说出的内容天然当成真实数据。**

### 7

> **LLM 不是搜索引擎，最新和私有信息通常需要通过 Search、RAG、API 或 Tool 获得。**

### 8

> **LLM 默认并没有无限、永久的用户记忆，Memory 往往需要应用程序自己管理。**

### 9

> **LLM 擅长理解、推理和生成；Java 等传统程序擅长精确执行、校验、事务、权限和可靠性。**

### 10

> **Agent 的核心思想之一，就是让 LLM 的智能能力与真实软件系统的执行能力结合起来。**

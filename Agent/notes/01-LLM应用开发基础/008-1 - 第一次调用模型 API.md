# 一、从这里开始，我们终于真正“调用模型”了

Phase 0 的 Node 001～007，我们主要在建立认知：

```
LLM 是什么
↓
Training / Inference
↓
Hallucination
↓
Token
↓
Context Window
↓
Agent
↓
Workflow 与 Agent
```

到目前为止，我们一直在讨论：

> **模型究竟是什么，以及围绕模型的 Agent 系统为什么会出现。**

但是我们还缺少一个非常基础的东西：

> **程序到底是怎么和模型说上话的？**

平时使用 ChatGPT、Qwen、Claude 时，我们只看到：

```
输入框
↓
输入问题
↓
点击发送
↓
看到回答
```

产品已经把底层调用过程全部藏起来了。

但是作为 LLM Application Engineer，我们不能只知道：

```
“我输入一句话，模型就回答了。”
```

必须继续往下追：

```
这句话到底以什么形式离开我的电脑？

发送到了哪里？

谁接收了它？

怎么知道我要调用哪个模型？

模型回答以后又以什么格式返回？

为什么 Java、Python、Apifox、curl 都可以调用同一个模型？

API Key 到底在其中做什么？
```

Node 008 就是正式解决这些问题。

# 二、先看最完整的一条链路

第一次调用模型 API，可以先建立这样一张图：

```
你的程序 / Apifox / curl
          │
          │
          │ HTTP Request
          ▼
     Model Provider
          │
          │
          ▼
        Model
          │
          │ Inference
          ▼
     Model Provider
          │
          │ HTTP Response
          ▼
你的程序 / Apifox / curl
```

如果当前使用：

```
Provider：
阿里云百炼

Model：
Qwen
```

那么可以理解成：

```
你的程序
   │
   │ HTTP Request
   ▼
阿里云百炼
   │
   ▼
Qwen
   │
   │ Inference
   ▼
阿里云百炼
   │
   │ HTTP Response
   ▼
你的程序
```

这一整条链路以后非常重要。

因为未来你使用：

```
OpenAI
Claude
DeepSeek
Qwen
Gemini
其他 Provider
```

虽然：

```
URL
参数
SDK
能力
```

可能不同，

但是最核心的结构仍然非常相似：

```
Client
↓
Request
↓
Provider
↓
Model
↓
Response
```

# 三、Node 002 的 Inference 终于落地了

Node 002 学过：

```
Training
≠
Inference
```

当时我们说：

```
Training
↓
更新模型参数
```

而：

```
Inference
↓
使用已经训练好的模型进行推理
```

现在真正调用模型 API：

```
POST ...
```

本质就是在请求：

> **请 Provider 使用某个已经部署好的模型，为我执行一次 Inference。**

所以：

```
调用 API
≠
训练模型
```

你发：

```
请解释 HashMap
```

模型不会因为看到这句话：

```
重新训练一次 Qwen
```

也不会：

```
永久修改模型参数
```

而是：

```
已有模型参数
+
当前 Context
↓
Inference
↓
生成结果
```

这就是前面抽象概念第一次和工程实践连上。

# 四、先分清四个最容易混的词

从现在开始，经常会同时看到：

```
Provider
Model
API
SDK
```

这四个词一定不要混。

# 五、什么是 Provider？

Provider 可以理解成：

> **向你提供模型调用服务的平台或服务提供方。**

它负责很多模型以外的工程工作，例如：

```
模型部署
服务器
GPU
推理服务
网络
鉴权
限流
计费
日志
API Endpoint
```

比如你不需要自己：

```
买 GPU
下载模型权重
部署推理服务器
做负载均衡
维护模型 Serving
```

Provider 已经帮你完成。

你只需要：

```
发送 Request
↓
拿到 Response
```

所以可以把 Provider 理解成：

```
模型服务平台
```

# 六、什么是 Model？

Model 是：

> **真正完成语言理解和生成的模型本身。**

例如：

```
Qwen
GPT
Claude
DeepSeek
```

再具体一点：

```
某一个具体模型版本 / 型号
```

Provider 和 Model 是两层东西。

可以这样类比：

```
阿里云百炼
=
电影院

Qwen 模型
=
电影院里上映的一部电影
```

当然这只是帮助理解。

更工程一点：

```
Provider
=
提供运行环境和 API

Model
=
真正执行 Inference 的模型
```

所以：

```
Provider
≠
Model
```

# 七、为什么一次请求需要指定 model？

一个 Provider 可能同时提供很多模型。

例如可能存在：

```
大模型
小模型
推理模型
代码模型
视觉模型
Embedding 模型
```

所以请求中需要告诉 Provider：

```
“这一次我要用哪个。”
```

于是经常会看到：

```
{
  "model": "xxx"
}
```

这里：

```
model
```

就是：

> **本次请求的模型选择。**

# 八、什么是 API？

API：

```
Application Programming Interface
```

可以简单理解成：

> **两个程序之间约定好的调用方式。**

例如以前写后端：

```
GET /users/123
```

可能返回：

```
{
  "id": 123,
  "name": "张三"
}
```

前端知道：

```
访问哪个 URL
用什么 Method
传什么参数
返回什么 JSON
```

就可以调用你的后端。

LLM API 没有脱离这个世界。

比如：

```
POST /chat/completions
```

只是这个接口的业务含义变成：

> **让模型生成一次结果。**

所以：

```
LLM API
```

首先仍然是：

```
API
```

而不是一种神秘的新通信方式。

# 九、什么是 SDK？

SDK 可以理解成：

> **别人为了方便你调用 API，而提供的一套客户端代码。**

例如原始 HTTP 调用可能需要你自己做：

```
构造 URL
↓
设置 Header
↓
拼 JSON
↓
发送 HTTP
↓
解析 JSON Response
```

SDK 可能把它包装成：

```
client.chat(...)
```

你写一行代码，

SDK 在底层替你完成：

```
HTTP Request
```

所以：

```
SDK
≠
API
```

SDK 只是：

```
调用 API 的一种工具
```

# 十、这四个东西放在一起

可以画成：

```
你的 Java 程序
        │
        │ 使用 SDK（可选）
        ▼
       API
        │
        ▼
    Provider
        │
        ▼
      Model
```

或者：

```
Java
↓
HTTP API
↓
百炼
↓
Qwen
```

SDK 可以有，也可以没有。

这也是为什么：

```
Apifox
curl
Java
Python
```

都能调用同一个模型。

因为它们最终都能够：

```
发送符合 API 协议的 HTTP Request
```

# 十一、什么是 HTTP？

HTTP：

```
HyperText Transfer Protocol
```

Node 008 不需要把 HTTP 全部重新学一遍。

作为 Java 后端开发，你本来就已经接触大量 HTTP。

这里只需要把它映射到 LLM 调用。

模型 API 本质上仍然使用：

```
HTTP Request
↓
HTTP Response
```

所以：

> **你以前调用普通 REST API 的很多知识，在这里仍然成立。**

# 十二、HTTP Request 是什么？

Request：

```
请求
```

就是：

> **客户端向服务端发送的一次请求。**

最基本可以拆成：

```
Method
URL
Headers
Body
```

以后看到任何 LLM API 请求，

先不要觉得复杂。

先拆成这四部分。

# 十三、Method 是什么？

常见 HTTP Method：

```
GET
POST
PUT
DELETE
PATCH
```

模型生成类 API 通常大量使用：

```
POST
```

因为我们需要向服务端提交一份复杂数据：

```
Model
Messages
Parameters
Tools
Schema
...
```

这些东西适合放在：

```
Request Body
```

中。

所以：

```
POST
```

不是因为：

```
“AI API 必须 POST”
```

而是因为：

```
它非常适合提交复杂请求数据
```

# 十四、URL 是什么？

URL 告诉客户端：

> **我要把 Request 发到哪个服务。**

例如一个普通 API：

```
https://api.example.com/users
```

模型 API 也类似。

可能是：

```
https://某个域名/.../chat/completions
```

客户端必须知道：

```
Request 到底发到哪里
```

否则根本无法调用 Provider。

# 十五、Base URL 是什么？

以后 SDK 中经常看到：

```
base_url
```

假设完整接口是：

```
https://api.example.com/v1/chat/completions
```

可以把：

```
https://api.example.com/v1
```

看成：

```
Base URL
```

后面的：

```
/chat/completions
```

是具体 API Path。

# 十六、Endpoint 是什么？

Endpoint 可以理解成：

> **一个具体可以调用的 API 地址。**

例如：

```
POST
https://api.example.com/v1/chat/completions
```

这个完整组合就是：

```
一个具体 Chat Completions Endpoint
```

所以：

```
Base URL
```

和：

```
Endpoint
```

不要完全当成同义词。

# 十七、Headers 是什么？

Headers 可以先理解成：

> **Request 携带的一些元信息。**

例如：

```
我是谁
我发送的 Body 是什么格式
我希望得到什么格式
```

模型 API 中常见：

```
Authorization
Content-Type
```

# 十八、Authorization 是什么？

Provider 不可能允许：

```
世界上任何人
```

无限免费调用模型。

它需要知道：

```
你是谁
你有没有权限
费用算谁的
```

所以需要：

```
Authentication / Authorization
```

在模型 API 中最常见的方式之一就是：

```
API Key
```

# 十九、API Key 可以怎么理解？

可以把 API Key 粗略理解成：

> **调用 Provider API 时使用的一种身份凭证。**

它告诉 Provider：

```
这个 Request 属于哪个调用方
```

Provider 根据 Key 判断：

```
是否允许调用
账户是谁
配额是多少
费用记在哪里
能调用哪些模型
```

# 二十、为什么 API Key 绝对不能随便写进 Git？

假设：

```
String apiKey = "真实Key";
```

然后：

```
git add .
git commit
git push
```

Key 就可能进入：

```
GitHub
Git History
```

如果仓库公开：

别人可能直接使用你的 Key。

结果：

```
额度被消耗
费用增加
账号风险
```

即使之后删除：

```
这个字符串
```

它也可能仍然存在于：

```
旧 Commit
```

中。

所以从第一次 API 调用开始就要形成习惯：

```
Secret
≠
源码
```

# 二十一、环境变量为什么适合放 API Key？

例如：

```
DASHSCOPE_API_KEY
```

程序运行时：

```
从操作系统环境读取
```

而不是：

```
从源码读取
```

于是：

```
Git
```

只保存：

```
变量名
```

不保存：

```
真正 Secret
```

例如 Java 代码未来可能是：

```
System.getenv("DASHSCOPE_API_KEY");
```

代码里只有：

```
DASHSCOPE_API_KEY
```

没有真实 Key。

# 二十二、Content-Type 是什么？

如果 Request Body 是：

```
{
  "model": "...",
  "messages": []
}
```

那么它是：

```
JSON
```

所以通常需要告诉服务端：

```
Content-Type: application/json
```

意思就是：

> **我发送给你的 Body 是 JSON 格式。**

# 二十三、Body 是什么？

Body 可以理解成：

> **这次请求真正携带的主要业务数据。**

例如模型调用：

```
{
  "model": "xxx",
  "messages": [
    {
      "role": "user",
      "content": "你好"
    }
  ]
}
```

这里真正：

```
要调用哪个模型
给模型看什么内容
```

主要都在 Body 中。

# 二十四、为什么模型 API 特别喜欢 JSON？

因为请求往往不是：

```
只有一句字符串
```

而是一个结构化对象。

例如以后可能出现：

```
model
messages
temperature
max_tokens
tools
response_format
stream
```

所以非常适合：

```
{
  "model": "...",
  "messages": [],
  "stream": false
}
```

JSON。

# 二十五、JSON 在这里不是“模型输出格式”

注意别和 Structured Output 混。

现在 Request Body 使用 JSON：

```
只是 HTTP API 数据格式
```

后面的 Structured Output：

```
让模型生成符合 JSON Schema 的业务结果
```

是另一层问题。

所以：

```
Request 是 JSON
```

不等于：

```
模型一定输出 JSON
```

# 二十六、Chat Completions 是什么？

Node 008 第一阶段我们准备学习：

```
Chat Completions API
```

可以简单理解：

> **以“消息列表”的方式给模型提供上下文，然后让模型生成下一条 Assistant 消息。**

典型 Request：

```
{
  "model": "xxx",
  "messages": [
    {
      "role": "user",
      "content": "你好"
    }
  ]
}
```

Provider：

```
拿到 messages
↓
交给模型
↓
模型生成回复
```

# 二十七、为什么叫 Chat Completions？

可以粗略拆成：

```
Chat
=
对话

Completion
=
续写 / 补全 / 生成
```

模型根据：

```
已有 Message
```

生成：

```
下一段 Assistant 内容
```

# 二十八、messages 是什么？

这是 Node 009 会重点讲的。

当前先建立最简单认知：

```
messages
=
当前请求中提供给模型的聊天消息列表
```

例如：

```
[
  {
    "role": "user",
    "content": "Java 是什么？"
  }
]
```

以后可能变成：

```
System
User
Assistant
User
Assistant
Tool
...
```

# 二十九、messages 和 Context 有什么关系？

Node 005 已经学过：

```
Context
=
模型当前这一次推理真正看到的信息
```

在 Chat Completions 中：

```
messages
```

就是 Context 的一个非常主要来源。

例如：

```
System Message
历史 User Message
历史 Assistant Message
当前 User Message
```

都可以进入：

```
messages
```

于是：

```
messages
↓
Tokenizer
↓
Input Token
↓
Model Context
```

这就是 Node 005 开始落地。

# 三十、model + messages 就能完成最简单调用

最简单模型请求可以只有：

```
{
  "model": "某个模型",
  "messages": [
    {
      "role": "user",
      "content": "你好"
    }
  ]
}
```

之后才会慢慢加入：

```
System Prompt
Parameters
Structured Output
Tools
Streaming
```

所以 Node 008 一开始故意：

```
越简单越好
```

# 三十一、什么是 OpenAI-compatible？

这是我们当前路线中一个很重要的概念。

很多 Provider 提供：

```
OpenAI-compatible API
```

它并不是说：

```
这些 Provider 属于 OpenAI
```

而是：

> **它们让自己的 API 尽量兼容 OpenAI API 的请求 / 响应风格。**

# 三十二、为什么 Provider 要做兼容？

假设一个 Java 项目原来调用：

```
Provider A
```

请求结构是：

```
{
  "model": "...",
  "messages": [...]
}
```

后来想换：

```
Provider B
```

如果 Provider B 也兼容相同接口风格，

可能只需要改：

```
Base URL
API Key
Model
少量参数
```

而不用：

```
整个项目全部重写
```

这会明显降低迁移成本。

# 三十三、OpenAI-compatible 不代表什么？

非常重要：

```
Compatible
≠
Identical
```

它不代表：

```
所有 Provider 参数完全一样

所有模型能力完全一样

所有错误码完全一样

所有 Tool Calling 行为完全一样

所有 Structured Output 能力完全一样

所有 Reasoning 参数完全一样
```

所以以后：

```
兼容接口
```

只能减少差异，

不能让差异彻底消失。

# 三十四、为什么我们的学习路线选择 OpenAI-compatible？

因为我们真正想学的是：

```
LLM Application Engineering
```

而不是：

```
只会某个 Provider SDK
```

通过兼容接口可以先理解：

```
HTTP
Message
Structured Output
Tool Calling
Streaming
Agent Loop
```

这些相对通用的概念。

以后切换 Provider：

```
更容易理解哪些是通用机制
哪些是 Provider-specific
```

# 三十五、为什么 Node 008 暂时不使用高级 Framework？

例如：

```
Spring AI
LangChain4j
```

都可以大幅简化代码。

但第一轮如果直接：

```
chatClient.prompt()
        .user("你好")
        .call();
```

你可能完全不知道底层发生了什么。

Framework 已经替你隐藏：

```
URL
Headers
JSON
HTTP Request
Response Parsing
```

所以学习第一轮必须先看：

```
原始 Request / Response
```

以后再使用 Framework，

你才能知道：

> **它替我省掉了什么。**

# 三十六、HTTP Response 是什么？

Request：

```
Client
→
Server
```

Response：

```
Server
→
Client
```

Provider 完成模型推理以后，

会返回：

```
HTTP Response
```

Response 也可以拆：

```
Status
Headers
Body
```

# 三十七、HTTP Status 是什么？

HTTP Status 是：

```
本次 HTTP 调用的状态
```

例如：

```
200
400
401
403
404
429
500
```

它们首先描述的是：

```
HTTP / API 请求层
```

而不是：

```
模型答案质量
```

# 三十八、HTTP 200 表示什么？

大致代表：

```
HTTP 请求成功处理
```

例如：

```
请求格式正确
鉴权成功
服务正常处理
```

但是：

```
HTTP 200
```

绝对不代表：

```
模型回答一定正确
```

# 三十九、这和 Hallucination 有什么关系？

例如：

```
HTTP 200
```

模型回答：

```
一个完全错误的事实
```

那么：

```
API
=
成功
```

但：

```
Answer
=
错误
```

所以：

```
Transport Success
≠
Semantic Correctness
```

可以理解成：

```
接口成功
≠
业务内容正确
```

# 四十、这对 Agent 为什么特别重要？

以后 Agent Tool 调用时：

```
HTTP 200
```

也可能返回：

```
错误理解
错误 Tool Selection
错误分析
```

所以生产 AI 系统不能只监控：

```
接口成功率
```

还要监控：

```
任务成功率
准确性
质量
```

这就是后面 Eval 为什么会出现。

# 四十一、Response Body 大概是什么？

Chat Completions 非流式 Response 常见结构类似：

```
{
  "id": "...",
  "model": "...",
  "choices": [
    {
      "message": {
        "role": "assistant",
        "content": "..."
      },
      "finish_reason": "stop"

  ],
  "usage": {
    "prompt_tokens": 0,
    "completion_tokens": 0,
    "total_tokens": 0

现在先看结构，

不要背字段。

# 四十二、为什么 Response 不只是一个 String？

很多初学者只关心：

```
content
```

于是会产生：

```
Model API
=
传一个 String
返回一个 String
```

这种过度简化。

真实 Response 往往还有：

```
Request ID
Model
Finish Reason
Usage
Metadata
```

以后 Tool Calling：

```
甚至可能根本不是普通 content
```

所以一定要建立：

> **模型 API Response 是结构化数据，不只是模型回答文本。**

# 四十三、choices 是什么？

Chat Completions 中常见：

```
choices
```

可以理解成：

```
模型生成结果集合
```

最普通调用一般主要关注：

```

```

里面可能有：

```
message
finish_reason
```

# 四十四、message 是什么？

Response 里的：

```
message
```

通常表示：

```
模型生成的一条 Assistant Message
```

例如：

```
{
  "role": "assistant",
  "content": "Java 是一种..."
}
```

这就是 Chat Completions：

```
根据已有 Messages
↓
生成新的 Assistant Message
```

# 四十五、content 是什么？

```
content
```

就是：

```
模型生成的主要文本内容
```

普通聊天里用户最终看到的文字：

通常主要来自这里。

# 四十六、finish_reason 是什么？

这是一个从第一天就值得注意的字段。

它回答：

> **这次模型生成为什么结束？**

例如常见：

```
stop
```

表示：

```
正常停止
```

还有可能：

```
length
```

表示：

```
达到长度限制
```

以后 Tool Calling：

也可能出现工具调用相关情况。

# 四十七、为什么 finish_reason 不能忽略？

假设模型返回：

```
Java 中 HashMap 的实现主要包括……
```

然后突然中断。

如果：

```
finish_reason = length
```

说明可能：

```
不是模型突然不会了
```

而是：

```
输出长度上限到了
```

所以 Debug LLM API：

不要只看：

```
content
```

# 四十八、usage 是什么？

Node 004 终于正式回来。

```

```

通常用于描述：

```

常见：

```

completion_tokens
total_tokens
```

# 四十九、prompt_tokens 是什么？

可以理解成：

```

```

也就是：

```

其中可能包含：

```

User
History

...

具体取决于请求。

# 五十、completion_tokens 是什么？

可以理解成：

```

```

模型生成：

```

```

所使用的 Token 数。

# 五十一、total_tokens

通常近似：

```

+

```

得到：

```

```

具体以后以 Provider 实际 Usage 定义为准。

# 五十二、Token 为什么突然变成一个工程指标？

Node 004 时它只是概念。

# 五十三、为什么一句很短的 User Message，prompt_tokens 也可能比想象多？

还可能存在：

所以：

```

↓

↓

# 一百零四、这一篇最核心的 15 句话

### 1

> **模型 API 本质上仍然是一种远程 API。**

### 2

> **Provider 负责提供模型服务，Model 负责真正执行推理。**

### 3

> **API 是调用协议，SDK 是调用 API 的客户端工具。**

### 4

> **一次最基本的 HTTP Request 可以拆成 Method、URL、Headers 和 Body。**

### 5

> **API Key 是访问 Provider 服务的重要凭证，不应该写入 Git。**

### 6

> **Request Body 经常使用 JSON，因为模型请求本身是结构化数据。**

### 7

> **Chat Completions 通过 messages 向模型提供对话 Context。**

### 8

> **model 字段告诉 Provider 本次使用哪个模型。**

### 9

> **OpenAI-compatible 代表接口风格兼容，不代表 Provider 完全相同。**

### 10

> **模型调用属于 Inference，不是 Training。**

### 11

> **Response 不只有模型回答，还包含状态、结束原因、Usage 等信息。**

### 12

> **HTTP 200 代表调用成功，不代表模型答案一定正确。**

### 13

> **Usage 把 Node 004 的 Token 概念变成真实工程数据。**

### 14

> **Apifox、curl 和 Java 调模型，本质上都在构造 HTTP Request。**

### 15

> **Node 008 的目标不是写漂亮架构，而是彻底理解最基础的模型调用链。**

# 一百零七、口述测试

如果有人问你：

> “Java 到底是怎么调用大模型的？”

你现在应该能够不用任何 AI 专有术语堆砌，解释成：

```
Java 程序本质上是向模型 Provider 的 HTTP API
发送一个 Request。

Request 中会包含：
请求地址、
鉴权信息、
要调用的模型、
以及要给模型看的消息。

Provider 收到 Request 后完成鉴权和参数检查，
再调用对应模型执行一次 Inference。

模型生成结果后，
Provider 把结果封装成 HTTP Response。

Java 再解析 Response，
取出模型生成内容、结束原因和 Token Usage。

所以最基础的模型调用，
本质上仍然是一次远程 HTTP API 调用。
```

如果这段逻辑已经真正清楚，

就说明 `008-1` 的核心基本掌握。

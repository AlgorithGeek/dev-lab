- 不加入 `system` 来调教模型的回答风格：这是 Node 010；

我们的目的不是做出“一个聊天产品”，而是亲手验证下面这句话：

> **在当前使用的 Chat Completions 调用方式中，模型本轮能依据什么回答，取决于本次 Request 中实际提供了什么消息；应用程序必须自己组织需要重传的历史。**

注意这个结论有边界：它描述的是**我们目前使用的 Chat Completions 路径**。其他支持服务端历史引用的 API（例如部分 Responses API 用法）可能有不同的状态管理机制，不能由此推断“所有模型 API 都必须手工完整重传历史”。

# Checkpoint 1：先用肉眼设计“有历史 vs 无历史”

这一部分先看懂设计，**暂时不要打开 Codex**。

## 1.1 第一轮：先告诉模型一个只有本次实验才知道的信息

我们使用一个固定、无敏感含义的实验代号：

```text
青柠47
```

第一轮问题：

> 本次对话的实验代号是青柠47。请只回复“收到”。

第一轮 Request 的核心 JSON：

```json
{
  "model": "qwen3.8-max",
  "messages": [
    {
      "role": "user",
      "content": "本次对话的实验代号是青柠47。请只回复“收到”。"
    }
  ],
  "reasoning_effort": "none"
}
```

发出请求后，模型可能回复：

```text
收到
```

**这只是示例。**真实 Assistant `content` 以百炼本次返回的值为准，比如它实际返回“收到。”，Java 就应该保存“收到。”，而不是偷偷替换成我们提前写好的“收到”。

## 1.2 第二轮的共同问题

两种实验使用完全相同的第二轮 User Message：

> 刚才我告诉你的实验代号是什么？如果当前对话信息不足，请回答“无法确定”。

区别只在：**本次 Request 有没有携带第一轮历史。**

## 1.3 A 组：不携带历史

第二轮只发送：

```json
{
  "model": "qwen3.8-max",
  "messages": [
    {
      "role": "user",
      "content": "刚才我告诉你的实验代号是什么？如果当前对话信息不足，请回答“无法确定”。"
    }
  ],
  "reasoning_effort": "none"
}
```

请仔细看：这份请求里**根本没有“青柠47”这几个字**。

在当前使用的 Chat Completions 方式下，单凭这份 Request，模型不能可靠得知上一轮的实验代号。它有可能回答“无法确定”，也可能猜错或编造。这正是实验要观察的现象，而不是要保证某个固定文本出现。

## 1.4 B 组：携带历史

第二轮发送：

```json
{
  "model": "qwen3.8-max",
  "messages": [
    {
      "role": "user",
      "content": "本次对话的实验代号是青柠47。请只回复“收到”。"
    },
    {
      "role": "assistant",
      "content": "这里放第一轮模型真实返回的 assistant.content"
    },
    {
      "role": "user",
      "content": "刚才我告诉你的实验代号是什么？如果当前对话信息不足，请回答“无法确定”。"
    }
  ],
  "reasoning_effort": "none"
}
```

上面的占位文字**不是要真实发送的内容**。实验代码应该将第一轮 Response 中实际得到的 `choices[0].message.content` 放入此处。

模型本轮看到完整有序历史，因此可以从之前的 User Message 中定位代号。

## 1.5 重要：什么才算有效的 A/B 对比？

| 维度 | A 组 | B 组 |
|---|---|---|
| Model | `qwen3.8-max` | 同一个模型 |
| Endpoint | 同一地域、同一 Workspace | 同一个 Endpoint |
| Reasoning | `none` | `none` |
| 第二轮 User 问题 | 完全相同 | 完全相同 |
| 第一轮 User 历史 | **没有** | **有** |
| 第一轮 Assistant 历史 | **没有** | **有，使用真实返回** |
| 需要记录 | Request、答案、Usage | Request、答案、Usage |

本实验不是为了证明“两个回答一定不同”，而是为了证明：

> **应用发出的两份 `messages` 确实不同；B 的本次上下文包含 A 没有提供的历史。**

如果 A 偶然猜对，也不能据此得出模型在服务端保存了历史；如果 B 偶然答错，也不代表本次没有传入历史。要联合检查 **Request Body、响应内容、角色顺序与 Usage**。

### Checkpoint 1 理解检验

先在脑中回答三个问题：

1. A 第二轮为什么不能直接知道“青柠47”？
2. B 第二轮为什么要包含第一轮的 **Assistant Message**，而不是只传两条 User Message？
3. 为什么 B 里的 Assistant 内容必须取自真实 Response，不能手写一个假历史？

第三问的答案是：这个实验既要证明历史重传，也要培养正确的消息管理习惯。手写消息在协议上未必被禁止，但**伪装成实际历史**会污染我们的实验结论。

## 3.1 找到构造 `messages` 的地方

你应该能指出：

```text
seed 消息从哪里创建？
A 组消息在哪里构造？
B 组消息在哪里构造？
```

尤其注意：

```text
JSONArray / List
    ↓
包含多个 JSONObject
    ↓
每个 JSONObject 都有 role / content
    ↓
JSON 序列化到 Request Body
```

如果使用 FastJSON2，典型思想是：

```java
// 结构示意，不是让你在当前类里直接复制的完整实现。
JSONArray messages = new JSONArray();

JSONObject userMessage = new JSONObject();
userMessage.put("role", "user");
userMessage.put("content", "你好");

messages.add(userMessage);

JSONObject body = new JSONObject();
body.put("model", "qwen3.8-max");
body.put("messages", messages);
body.put("reasoning_effort", "none");

String requestJson = JSON.toJSONString(body);
```

这里最值得理解的不是 `put()` 语法，而是：

> **我们终于不再固定发送一条 Message，而是动态组装一个有序消息数组。**

## 3.2 为什么选择 JSON 构造而不是字符串拼接？

假设用户输入：

```text
他说：“你好”，然后换行。
```

如果直接通过字符串拼接来写：

```text
{"role":"user","content":"..."}
```

你还得自己处理引号、换行和反斜杠，稍不小心就会生成非法 JSON。

FastJSON2 的结构化对象与序列化可以处理这些 JSON 转义问题。但它不会替你解决所有业务安全问题，也不能据此认为任何用户输入都可被信任。

## 3.3 Request 中的 Assistant Message 是哪里来的？

第一轮返回：

```text
choices[0].message.content
```

应用读取：

```text
String assistantText
```

构造 B 请求时：

```text
role = assistant
content = assistantText
```

这是一个关键转换：

```text
上一轮 Response 的 assistant 内容
               ↓
下一轮 Request 的历史 assistant Message
```

**模型不会自动替我们的当前 Java 客户端完成这个保存步骤。**

## 3.4 有一个容易混淆的事实

B 组如果回答出“青柠47”，它直接读取的其实是 **B 的历史 User Message**，不是说 Assistant Message 中必然保存了那个代号。为什么我们仍要带 Assistant？因为一段真实多轮对话通常需要连续保留助手已经说过什么，让后续模型理解对话过程。

如果你只想验证“代号能不能找回来”，只带旧 User Message 也可能够用；但如果下一轮问的是“你上一轮自己说了什么？”，Assistant 历史就会变得非常重要。

下一阶段会专门让 Java 按顺序自动保存二者。

## 4.1 第一轮与第二轮的本质区别

第一轮我们人为构造一组有限的对照用消息：

```text

B
```

第二轮要让程序真正建立如下规律：

```text
聊天开始：history = []
        │
        ▼
追加 User 1
        │
        ▼
发送 history → 收到 Assistant 1
        │
        ▼
追加 Assistant 1
        │
        ▼
追加 User 2
        │
        ▼
发送 history → 收到 Assistant 2
        │
        ▼
追加 Assistant 2
        │
        ▼
追加 User 3
        │
        ▼
发送 history → 收到 Assistant 3
        │
        ▼
追加 Assistant 3
```

核心不在于列表名字是否叫 `history`，而在于：

> **每一轮发送的 `messages` 都应该按照真实对话顺序，包含这一轮需要的上下文；返回后再保存 Assistant，供下一轮使用。**

## 4.2 我们使用什么 Java 结构保存？

当前推荐最简单的：

```text
ArrayList / JSONArray
```

存放按顺序排列的：

```text
JSONObject{role:"user", content:"..."}
JSONObject{role:"assistant", content:"..."}
```

比如：

```json
[
  {"role":"user","content":"本次实验的变量名是 alpha-21。请回复收到。"},
  {"role":"assistant","content":"收到。"},
  {"role":"user","content":"刚才告诉你的变量名是什么？"},
  {"role":"assistant","content":"alpha-21"}
]
```

上面是**结构示意**，不是我们现在已经得到的真实 Assistant 回复。

暂时不设计：

```text
ConversationRepository
ChatHistoryService
RedisChatMemory
MySqlConversationTable
SessionManager
```

## 4.3 实验三轮问题怎么设计？

为了避免混入复杂 Prompt Engineering，这次继续使用简单且可检查的文本。

| 轮次 | User 输入 | 核心验证点 |
|---|---|---|
| 1 | `本次实验的变量名是 alpha-21。请回复“收到”。` | 只有 User 1 进入模型 |
| 2 | `刚才我告诉你的变量名是什么？` | 本轮包含 User 1 + Assistant 1 + User 2 |
| 3 | `你上一轮回答了什么？请复述原话。` | 本轮还包含上一轮实际的 Assistant 2 |

为什么第三轮重要？因为它比“继续问变量名”更直接地考察 **Assistant 历史内容**。

再次强调，模型的自然语言回复不保证 100% 逐字复现。我们主要检查它是否看到了真实历史，并观察实际效果。

## 4.4 为什么不能在发请求前就把 Assistant 写入历史？

因为 Assistant Message 必须来自：

```text
真实收到并成功解析的本次模型 Response
```

正确顺序：

```text
追加/构造本轮 User
        ↓
发送当前 messages
        ↓
确认 HTTP 2xx 且 Response 合法
        ↓
读取实际 assistant.content
        ↓
把这条 Assistant 追加到历史
```

如果请求失败，不应该编造“收到”并把它当作 Assistant 历史。

对于待发送 User Message 是否暂存进历史，有不同实现方式。本实验建议选择**构造候选列表 → 调用成功后再正式提交 User + Assistant**，避免失败时主列表留下一条没有对应 Assistant 的半成品消息。这个建议是当前实验的简化约定，不是所有生产系统唯一的会话存储策略。

# Checkpoint 5：Token、异常和正确性验证

## 5.1 从 Node 004 回到实际 `prompt_tokens`

我们已经在 `008-2` 观察过：

```text
Prompt 变长
  ↓
Input Token 通常增加
```

这一次不同：**Prompt 未必变得更长，但历史消息越来越多。**

模型每轮输入可理解成：

```text
第 1 轮：User 1

第 2 轮：User 1 + Assistant 1 + User 2

第 3 轮：User 1 + Assistant 1 + User 2 + Assistant 2 + User 3
```

因此，随着历史增加，本实验中的 `prompt_tokens` 通常会上升。

注意三个重要区别：

1. **`prompt_tokens` 与 `completion_tokens` 不同。**多轮输入增加不意味着模型每轮输出一定更长。
2. **`prompt_tokens` 与账单金额不是同一个数字。**价格可能因模型、缓存、输入输出定价而不同。
3. **程序内存里保存了多少历史，与本轮请求到底发送了多少历史不是同一件事。**我们要检查真实 Request。

## 5.2 不要把 Chat History 和 Memory 混淆

现在做的是：

```text
进程内保存上一轮 User / Assistant 消息
               ↓
下一轮重新传进 messages
```

这属于最基础的**对话历史管理**。

它还不是后续 Agent 工程里的完整 Memory 系统：

```text
跨重启保存
跨会话召回
按用户权限隔离
长期摘要
知识检索
```

也不是运行状态 `State` 的全部含义。这个边界在 `009-1` 已经讲过，实践时要继续保持清晰。

## 5.3 故障情况下绝对不能伪造历史

设想第二轮 HTTP 失败：

```text
User 1 → Assistant 1 ✅
User 2 → HTTP 500    ❌
```

错误做法：

```text
User 2
Assistant 2 = “收到，已完成”   ← 并没有真实模型成功回复
```

正确做法：

- 打印 HTTP Status 与错误信息；
- 不再把不存在的 Assistant 2 当成有效历史；
- 对尚未成功的 User 2，按照当前实验约定保持主历史一致；
- 如果终止实验，就明确显示“中止于第 2 轮”，而不是继续当作成功。

这不要求我们现在就实现重试、幂等、事务、历史持久化。这些是后面的工程化问题。

## 八、四个常见误区

### 误区 1：“我拿同一个 API Key 连续调了两次，所以服务端应该记得上一次。”

对我们当前的 Chat Completions 使用方式来说，这个推断不成立。关键看下一次 Request 的 `messages`，而不是同一个 Key、同一个 `HttpClient` 或同一个 Java 进程。

### 误区 2：“只有历史 User Message 有用，Assistant 可以不保存。”

如果只问先前 User 明确给出的代号，可能仅带 User 历史就能回答。但真实多轮对话也需要知道助手曾经回答、承诺或选择过什么，所以通常应保存 Assistant 历史。

### 误区 3：“Chat History 就是把所有东西永久、完整地传给模型。”

历史可以保存在应用侧，真正发送的 `messages` 可以经过筛选、截断、摘要等处理。Node 009 先学习最简单的全量短历史，长期 Context 管理以后再深入。

### 误区 4：“只要模型 B 回答了‘青柠47’，就说明代码完全正确。”

不够。必须再检查 Request 中旧 User、真实 Assistant 和当前 User 是否按顺序出现，且失败路径没有污染历史。

# 一、先说结论

模型选择最容易犯的错误是：

```text
哪个模型最强？
↓
那就永远用哪个
```

真实工程不是这么选。

模型选择真正是在做：

> **能力、成本、速度、上下文、稳定性、工具能力、结构化输出能力和业务要求之间的权衡。**

所以：

```text
模型选择
≠
模型排行榜
```

而是：

```text
任务需求
↓
约束条件
↓
候选模型
↓
综合权衡
↓
选择最合适的模型
```

---

# 二、为什么“最强模型”不等于“最适合的模型”？

假设有两个模型：

```text
Model A
能力：95
价格：高
速度：慢

Model B
能力：85
价格：低
速度：快
```

如果任务是：

```text
判断一条广告是否属于：
正常 / 风险 / 拒绝
```

Model B 已经可以：

```text
稳定做到业务要求
```

那继续使用 Model A：

```text
可能没有明显业务收益
```

却会带来：

```text
更高成本
更高延迟
```

所以模型选择不是：

```text
能力最大化
```

而是：

```text
在满足业务要求以后
再优化成本、速度和稳定性
```

---

# 三、模型选择本质上是工程决策

可以把它理解成普通 Java 工程中的技术选型。

例如你不会说：

```text
服务器 CPU 越贵越好
数据库机器越大越好
线程池越大越好
```

而是看：

```text
实际负载
成本预算
性能目标
可靠性要求
```

模型也一样。

---

# 四、模型选择最核心的几个维度

当前阶段重点记：

```text
1. 能力
2. 稳定性
3. 速度
4. 成本
5. Context Window
6. 最大输出长度
7. Structured Output
8. Tool Calling
9. 推理能力
10. Provider / API 特性
```

以后做真实 Agent 时：

```text
几乎都绕不开这些维度
```

---

# 五、第一维：能力

能力可以包括：

```text
理解能力
推理能力
代码能力
数学能力
长文本理解
指令遵循
多语言
```

但要注意：

```text
“模型总体能力很强”
```

不等于：

```text
“它在你的任务上一定最好”
```

---

# 六、不要只看综合 Benchmark

排行榜可能告诉你：

```text
Model A 总分高
Model B 总分低
```

但你的业务可能只是：

```text
把广告优化建议整理成 JSON
```

那你真正需要测的是：

```text
这个具体任务做得怎么样
```

而不是：

```text
它高考数学能考多少
```

所以：

> **通用 Benchmark 可以帮助筛选候选模型，但不能替代业务 Evaluation。**

---

# 七、能力应该围绕任务定义

例如 Java Agent 项目可能有这些任务：

```text
A. 简单分类
B. 提取字段
C. Structured Output
D. Java 代码解释
E. 复杂 Bug 分析
F. Agent 多步规划
G. Tool Calling
```

模型在这些任务上的表现：

```text
可能完全不同
```

所以：

```text
不要问：
哪个模型最好？

应该问：
哪个模型最适合这个任务？
```

---

# 八、第二维：稳定性

稳定性是什么意思？

例如同一个任务连续请求：

```text
第一次
格式正确

第二次
字段少一个

第三次
开始胡乱解释

第四次
又正常
```

这种模型即使：

```text
偶尔表现非常惊艳
```

在生产业务中也可能不好用。

---

# 九、为什么稳定性非常重要？

真实后端往往不追求：

```text
偶尔 100 分
```

而更喜欢：

```text
长期稳定地达到要求
```

尤其是：

```text
分类
数据提取
Structured Output
Tool Calling
自动化 Agent
```

这些场景中：

```text
可预测
```

非常重要。

---

# 十、稳定性不只是“答案一样”

稳定性可能包括：

```text
格式稳定
字段稳定
指令遵循稳定
Tool Calling 稳定
错误率稳定
延迟稳定
```

所以：

```text
seed
```

只是“可复现性”的一个工具。

它不等于：

```text
业务稳定性
```

---

# 十一、第三维：速度

模型响应速度会直接影响：

```text
用户体验
```

我们刚学过 Streaming，所以现在可以把速度拆成：

```text
TTFT
首个内容延迟

+

Tokens/s
生成速度

+

Total Latency
总耗时
```

---

# 十二、什么任务特别关注速度？

例如：

```text
聊天
搜索问答
IDE 代码补全
实时客服
交互式 Agent
```

用户会明显感受到：

```text
1 秒开始回答
```

和：

```text
8 秒才开始回答
```

的差异。

---

# 十三、什么任务没那么在意速度？

例如：

```text
夜间批处理
日报生成
离线数据分析
后台批量分类
```

这种任务可能更关心：

```text
成本
准确率
```

而不是：

```text
TTFT
```

所以：

> **速度的重要程度取决于产品形态。**

---

# 十四、第四维：成本

模型 API 一般会按照：

```text
输入 Token
+
输出 Token
```

计费。

不同模型：

```text
价格可能差很多
```

如果每天只有：

```text
100 次请求
```

可能无所谓。

如果每天：

```text
1000 万次请求
```

哪怕每次只差一点钱：

```text
最终都是很大的成本差异
```

---

# 十五、成本不能只看“单次调用价格”

真实成本还可能受到：

```text
输入长度
输出长度
思考 Token
缓存
Batch
失败重试
Agent 多轮调用
```

影响。

例如一个 Agent：

```text
一次用户请求
```

内部可能调用：

```text
模型 8 次
```

那么：

```text
单次模型价格
```

会被放大。

---

# 十六、一个 Agent 为什么更需要关心成本？

例如：

```text
用户问一次
↓
Planner 调一次
↓
Tool Selector 调一次
↓
工具结果总结调一次
↓
再规划调一次
↓
最终回答调一次
```

用户只感觉：

```text
问了一次
```

但后端可能：

```text
调用模型 5 次
```

所以：

```text
Agent 成本
```

经常比普通聊天更容易膨胀。

---

# 十七、第五维：Context Window

Context Window：

```text
模型一次最多能看到多少 Token
```

我们之前已经学过。

不同模型：

```text
Context Window 可能不同
```

例如：

```text
32K
128K
200K
1M
```

---

# 十八、Context Window 越大越好吗？

不一定。

更大的 Context Window 给你：

```text
更多容量
```

但不代表：

```text
把所有东西全部塞进去
```

就是最佳方案。

因为还有：

```text
Token 成本
Context Noise
Lost in the Middle
注意力分散
延迟
```

问题。

所以：

> **大 Context 是能力上限，不是让你无限塞垃圾信息的理由。**

---

# 十九、什么时候特别需要大 Context？

例如：

```text
阅读大型代码仓库
分析长合同
处理大量文档
长会话
大型 Agent Context
```

这时 Context Window 会成为：

```text
硬性能力约束
```

---

# 二十、当前 qwen3.8-max 的例子

当前阿里云百炼官方信息显示：

```text
qwen3.8-max
Context Window：
1,000,000 Token

最大输出：
131,072 Token
```

这是非常大的上下文能力。

但这并不意味着：

```text
我们的每次请求都应该塞几十万 Token
```

仍然要做：

```text
Context Engineering
```

这也是下一 Node 会学的重点。

---

# 二十一、第六维：最大输出长度

除了：

```text
能看多少输入
```

还要看：

```text
最多能生成多少输出
```

这两个不是一回事。

例如：

```text
Context Window = 128K
```

不代表：

```text
模型能输出 128K
```

---

# 二十二、什么任务需要较长输出？

例如：

```text
长篇报告
大型代码生成
完整技术文档
长小说
复杂分析
```

但普通 Agent 步骤：

```text
工具选择
分类
JSON 参数生成
```

通常根本不需要：

```text
超大输出
```

---

# 二十三、第七维：Structured Output 能力

我们刚刚学完：

```text
JSON Schema
Structured Output
DTO
```

所以模型选择时必须问：

```text
这个模型支不支持真正的 Structured Output？
```

不是所有模型都一样。

---

# 二十四、Structured Output 为什么影响模型选型？

假设业务要求：

```json
{
  "campaignId": 10001,
  "riskLevel": "HIGH",
  "reason": "..."
}
```

而某个模型：

```text
文本能力很好
```

但经常：

```text
JSON 格式错
字段漏
enum 不遵守
```

那么对于：

```text
自动化后端流程
```

它可能不如一个：

```text
文本能力稍弱
但 Schema 遵循更稳定
```

的模型。

---

# 二十五、这就是“业务能力”比排行榜更重要

例如：

```text
Model A
文学写作：顶级
Structured Output：一般

Model B
文学写作：普通
Structured Output：非常稳定
```

如果你做：

```text
广告投放自动化 Agent
```

Model B 可能反而更适合。

---

# 二十六、第八维：Tool Calling

Agent 以后会非常依赖：

```text
Tool Calling
```

模型要能够：

```text
判断什么时候调用工具
选择哪个工具
生成正确参数
读取工具结果
继续后续步骤
```

所以 Tool Calling 是 Agent 模型选型非常重要的一项。

---

# 二十七、不是“支持 Tool Calling”就够了

有些模型：

```text
API 支持 tools
```

但实际效果可能：

```text
经常乱调用
参数错误
重复调用
不该调用时调用
应该调用时不调用
```

所以真正需要评估的是：

```text
Tool Calling 质量
```

而不是：

```text
文档里有没有 tools 参数
```

---

# 二十八、第九维：推理能力

复杂 Agent 经常需要：

```text
规划
分析
判断
多步骤推理
```

这时模型的 reasoning 能力很重要。

例如：

```text
任务：
分析广告效果下降原因
↓
读取数据
↓
找异常
↓
决定调用哪个工具
↓
综合多个结果
↓
给出策略
```

这比：

```text
把一句话分类
```

复杂很多。

---

# 二十九、推理模型是不是所有任务都应该用？

不是。

例如：

```text
把 JSON 字段改个名字
```

如果还让模型：

```text
深度思考
```

可能只是：

```text
更慢
更贵
```

所以还是那句话：

> **任务难度和模型能力要匹配。**

---

# 三十、第十维：Provider / API 特性

模型并不是孤立存在的。

你实际接入的是：

```text
Model
+
Provider
+
API
```

例如 Provider 还会影响：

```text
接口格式
限流
地域
价格
稳定性
SLA
日志
缓存
Batch
错误码
Structured Output 实现
Tool Calling 实现
```

---

# 三十一、模型和 Provider 要分开理解

例如：

```text
Qwen
```

是：

```text
模型家族
```

而：

```text
阿里云百炼
```

是：

```text
Provider / 服务平台
```

调用体验并不只由模型决定。

---

# 三十二、为什么这一点对 Java 后端重要？

因为代码最终接的是：

```text
API
```

不是：

```text
“抽象的模型能力”
```

你要处理：

```text
请求格式
鉴权
错误码
Streaming
Structured Output
Tool Calling
限流
超时
```

这些都是：

```text
Provider 层问题
```

---

# 三十三、OpenAI-compatible 是不是代表完全一样？

不是。

`OpenAI-compatible` 通常表示：

```text
接口结构高度类似
```

例如：

```text
/chat/completions
messages
choices
```

但不同 Provider 仍可能在：

```text
支持参数
参数范围
错误码
Streaming 细节
Structured Output
Tool Calling
reasoning
```

方面有差异。

所以：

> **兼容 ≠ 完全一致。**

---

# 三十四、这就是为什么以后需要 Provider Adapter

未来如果真的接：

```text
Provider A
Provider B
```

你可能会发现：

```text
共同部分很多
```

但：

```text
特殊差异也真实存在
```

这时再抽象：

```text
ModelClient
ProviderAdapter
```

才有意义。

---

# 三十五、为什么现在不要提前做 Provider 抽象？

因为现在我们的项目实际上主要只有：

```text
百炼
+
qwen3.8-max
```

如果此时直接设计：

```java
interface ModelClient
```

再创建：

```text
QwenModelClient
OpenAIModelClient
ClaudeModelClient
GeminiModelClient
```

但后面三个根本没真实接过：

```text
你是在猜差异
```

---

# 三十六、过早抽象会发生什么？

你可能设计：

```java
interface ModelClient {
    String chat(String prompt);
}
```

然后真实接第二家 Provider 时发现：

```text
Streaming 不一样
Tool Calling 不一样
Reasoning 不一样
Structured Output 不一样
Usage 不一样
Error 不一样
```

最后：

```text
接口全部重写
```

所以路线里强调：

> **先有两个真实 Provider 的差异，再抽象。**

---

# 三十七、模型选择还有一个容易忽略的维度：可用性

一个模型再强：

```text
如果经常不可用
```

就很难用于生产。

可用性可能包括：

```text
服务稳定性
地域可用性
API 限流
并发限制
配额
模型是否下线
版本生命周期
```

---

# 三十八、模型版本为什么重要？

模型可能有：

```text
滚动别名
```

也可能有：

```text
带日期 / 版本号的固定版本
```

两者的意义可能不同。

滚动版本：

```text
可能自动升级
```

固定版本：

```text
行为更容易固定
```

---

# 三十九、为什么生产系统关心模型升级？

因为模型升级后可能：

```text
总体能力提高
```

但你的业务：

```text
格式
措辞
Tool Calling
分类边界
```

也可能发生变化。

所以以后模型升级也应该：

```text
做 Evaluation
```

而不是：

```text
“新版本更强，所以直接全量切换”
```

---

# 四十、模型选择还需要考虑地域和合规吗？

真实企业环境：

```text
需要
```

可能涉及：

```text
数据存储地域
数据跨境
企业政策
API 可用区域
隐私要求
合同 / SLA
```

这些不是模型智力问题。

但可能直接决定：

```text
某个模型能不能用
```

---

# 四十一、现在需要深入合规吗？

当前 Agent 学习路线：

```text
不需要
```

只建立意识：

```text
生产选型不只是模型能力
```

以后进入真实公司架构时：

```text
再按业务要求处理
```

---

# 四十二、模型选择还有多模态能力

模型可能只支持：

```text
文本
```

也可能支持：

```text
图片
音频
视频
文件
```

如果产品需要：

```text
图片理解
```

那么纯文本模型再强：

```text
也不符合需求
```

---

# 四十三、当前我们为什么先不展开多模态？

因为现在学习主线是：

```text
Java 后端
+
LLM Agent
+
文本模型 API
```

多模态后面有真实需求再扩展。

当前只要知道：

```text
输入模态
```

也是模型选型条件之一。

---

# 四十四、模型选择其实有“硬条件”和“软条件”

这是一个很好用的分类。

## 硬条件

不满足就不能选：

```text
必须支持 Tool Calling
必须支持 Structured Output
Context 至少 100K
必须在指定地域可用
```

## 软条件

可以权衡：

```text
能力更强一点
速度快一点
价格便宜一点
```

---

# 四十五、为什么先筛硬条件？

例如业务要求：

```text
必须支持 JSON Schema
```

Model A：

```text
能力 100
不支持 JSON Schema
```

Model B：

```text
能力 90
支持 JSON Schema
```

那么：

```text
Model A
直接淘汰
```

根本不用继续比较。

---

# 四十六、一个简单的模型选择流程

可以按：

```text
第一步：
明确任务

第二步：
列硬条件

第三步：
筛掉不满足的模型

第四步：
比较剩余模型：
能力 / 成本 / 延迟 / 稳定性

第五步：
用真实 Case Evaluation

第六步：
上线后继续监控
```

---

# 四十七、不要一上来做“全模型 Benchmark”

网上很容易产生一种冲动：

```text
把 20 个模型全部测一遍
```

很多时候没有意义。

因为你的实际候选可能只有：

```text
2～3 个
```

真正相关的模型。

所以：

```text
先筛选
再评测
```

而不是：

```text
先测全世界
```

---

# 四十八、真实 Evaluation 应该测什么？

例如广告分析 Agent：

```text
100 条真实 Case
```

可以测：

```text
结论准确率
JSON Schema 成功率
Tool Calling 成功率
平均 Token
平均延迟
成本
人工评分
```

这比：

```text
看排行榜
```

更有意义。

---

# 四十九、为什么“感觉这个模型回答更好”不够？

因为人的印象容易受到：

```text
某一次特别惊艳回答
语气
文风
篇幅
```

影响。

但真实业务要看：

```text
100 次
1000 次
```

是不是都稳定。

所以最终：

```text
模型选择
```

仍然会走向：

```text
Evaluation
```

---

# 五十、不同任务可以使用不同模型吗？

当然可以。

真实系统可能：

```text
简单分类
→ 小模型

复杂规划
→ 强模型

最终文案
→ 另一个模型
```

这叫：

```text
Model Routing
模型路由
```

---

# 五十一、为什么 Model Routing 有价值？

因为你不需要：

```text
每一步都调用最贵模型
```

例如：

```text
1000 个请求
```

其中：

```text
800 个非常简单
200 个复杂
```

可以：

```text
简单请求 → 快 / 便宜模型
复杂请求 → 强模型
```

从而优化：

```text
成本
+
速度
```

---

# 五十二、现在要学 Model Routing 吗？

不用。

当前只建立意识：

```text
以后不一定全系统一个模型
```

真正什么时候需要路由：

```text
出现真实任务差异以后
```

再做。

---

# 五十三、“小模型”是不是一定差？

不是。

“小”通常意味着：

```text
参数规模 / 能力层级较低
```

但对于简单任务：

```text
可能完全够用
```

而且可能有：

```text
速度更快
价格更低
部署更容易
```

的优势。

---

# 五十四、“大模型”是不是一定慢？

不一定绝对如此。

实际速度还和：

```text
Provider 推理基础设施
模型架构
负载
缓存
地域
```

有关。

所以：

```text
模型大小
```

不能简单等于：

```text
API 延迟
```

最终还是：

```text
实际测
```

---

# 五十五、模型选择不要只看价格

有时便宜模型：

```text
错误率更高
```

导致：

```text
重试更多
人工审核更多
业务损失更大
```

那么它表面：

```text
Token 单价便宜
```

实际：

```text
总成本更高
```

---

# 五十六、也不要只看能力

如果强模型：

```text
比次一级模型贵很多
```

但你的任务：

```text
质量只提升一点点
```

是否值得：

```text
要看业务价值
```

没有统一答案。

---

# 五十七、这就是“边际收益”

例如：

```text
模型 B：
成本 1
准确率 97%

模型 A：
成本 5
准确率 98%

模型 S：
成本 15
准确率 98.2%
```

你要问：

```text
多花的成本
换来的提升
值不值？
```

这就是工程选型。

---

# 五十八、对于 Agent，Tool Calling 可能比普通聊天能力更重要

例如模型：

```text
聊天非常自然
```

但：

```text
Tool Calling 成功率一般
```

另一个：

```text
聊天稍微普通
Tool Calling 非常稳定
```

如果做自动化 Agent：

```text
第二个可能更好
```

因为 Agent 的核心是：

```text
正确行动
```

而不只是：

```text
说得漂亮
```

---

# 五十九、Structured Output 也是同样道理

一个模型写文章特别好：

```text
不代表它适合后端自动化
```

后端可能更在意：

```text
Schema 遵循率
```

所以：

```text
“模型能力”
```

应该拆成：

```text
和任务相关的能力
```

# 六十一、模型选择和 Node 019 Context Engineering 有什么关系？

# 七十九、口述验收

如果有人问：

> 模型选择到底在选什么？

你应该能够解释：

> 模型选择不是简单地选排行榜最高或能力最强的模型，而是在真实任务下权衡能力、稳定性、速度、成本、上下文长度、Structured Output、Tool Calling、推理能力和 Provider 特性。
>
> 一个模型只要已经满足业务质量要求，更强但更贵、更慢的模型不一定更合适。真正的选型应该先明确任务和硬条件，筛掉不满足条件的模型，然后用真实业务 Case 做 Evaluation，比较质量、延迟、成本和稳定性。
>
> 对 Agent 来说尤其要关注 Tool Calling、Structured Output 和多轮稳定性，而不只是普通聊天效果。Provider 也不能忽略，因为 API、限流、地域、价格和功能实现都会影响最终工程体验。

如果能自然解释：

```text
不是选最强
而是选最合适
```

并能说出原因，

Node 018 的核心就完成了。

# 本篇一句话总结

> **模型选择不是选“世界上最强的模型”，而是为一个具体任务选择在能力、稳定性、速度、成本、上下文、Tool Calling、Structured Output 和 Provider 条件之间最合适的模型。**

最核心的流程：

```text
明确任务
↓
列出硬条件
↓
筛选候选模型
↓
比较能力 / 稳定性 / 速度 / 成本
↓
真实业务 Evaluation
↓
选择
↓
上线后持续监控
```

真正要记住：

```text
最强
≠
最适合

排行榜
≠
业务效果

模型能力
≠
整个工程体验
```

**Node 018：先建立选型判断力，不为了形式强行做模型 Benchmark。**

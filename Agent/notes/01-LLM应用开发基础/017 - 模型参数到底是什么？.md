# 一、先说结论

前面我们已经学过：

```text
Prompt
Context
Structured Output
Streaming
```

这些内容主要解决：

```text
给模型什么
要求模型返回什么
模型结果怎么传回来
```

而模型参数解决的是：

> **同一个模型、同一个 Prompt，在生成答案时，应该采用什么生成策略和资源边界。**

这一节重点理解：

```text
temperature
top_p
max_completion_tokens
seed
reasoning_effort
stop
```

不要把它们理解成：

```text
“让模型突然变聪明的按钮”
```

它们主要控制：

```text
多样性
输出长度
可复现性
推理投入
停止条件
```

---

# 二、为什么要学模型参数？

一个最简单的请求可能只有：

```json
{
  "model": "qwen3.8-max",
  "messages": [...]
}
```

这完全可以工作。

但我们还可以增加：

```json
{
  "temperature": 0.3,
  "max_completion_tokens": 1000,
  "seed": 1234,
  "reasoning_effort": "low"
}
```

这些参数会影响：

```text
回答有多随机
最多输出多少
相同请求是否更容易复现
模型愿意投入多少推理
什么时候停止
```

这一 Node 最重要的原则是：

> **不要死记参数表，要理解每个参数控制哪一层。**

---

# 三、参数不是越多越专业

刚接触模型 API 时很容易觉得：

```text
参数越多
=
配置越专业
```

其实很多时候：

```text
使用 Provider 默认值
```

就是很合理的起点。

只有出现明确问题时，再针对性调整：

```text
输出太随机
→ 看 temperature / top_p

回答太长
→ 看 max_completion_tokens

实验难复现
→ 看 seed

复杂任务推理不够
→ 看 reasoning_effort
```

所以：

> **参数应该解决问题，而不是为了“有参数”而设置参数。**

---

# 四、先理解模型生成时发生了什么

假设模型已经生成：

```text
Java 是一门
```

接下来可能有很多候选 Token：

```text
语言      0.55
编程      0.20
非常      0.08
面向      0.06
常用      0.04
...
```

可以把这些数字理解成：

```text
模型认为每个候选 Token
接下来出现的可能性
```

接下来需要：

```text
从候选 Token 中选一个
```

这个过程会受到：

```text
temperature
top_p
```

影响。

---

# 五、什么是 Sampling？

Sampling：

```text
采样
```

可以先理解成：

```text
模型得到多个候选 Token
↓
候选有不同概率
↓
按照某种策略
选出下一个 Token
```

如果总是极度偏向：

```text
最高概率 Token
```

输出往往：

```text
更稳定
更保守
```

如果允许更多候选参与：

```text
输出通常更多样
```

---

# 六、temperature 是什么？

`temperature`：

```text
采样温度
```

主要控制：

```text
生成的随机性 / 多样性
```

先记最简单的方向：

```text
temperature 较低
→ 更稳定
→ 更确定
→ 更保守

temperature 较高
→ 更多样
→ 更随机
→ 更有变化
```

---

# 七、temperature 不是“智商”

这是非常重要的一点。

```text
temperature 低
≠
模型变笨

temperature 高
≠
模型变聪明
```

它主要影响：

```text
Token 的采样方式
```

而不是：

```text
模型训练出来的知识
推理能力上限
```

---

# 八、低 temperature 适合什么？

通常更偏向：

```text
代码生成
分类
信息抽取
固定格式
技术回答
需要稳定输出的业务
```

例如：

```text
把用户反馈分成：
BUG / FEATURE / QUESTION
```

你通常希望：

```text
同一个输入
不要一会儿 BUG
一会儿 FEATURE
```

所以更关注：

```text
稳定性
```

---

# 九、高 temperature 适合什么？

通常更偏向：

```text
创意写作
头脑风暴
命名
故事
营销文案
多个候选方案
```

例如：

```text
帮我想 20 个科幻城市名字
```

你可能反而希望：

```text
结果更多样
```

---

# 十、temperature 越低是不是越准确？

不是。

低 temperature 只是：

```text
更倾向高概率候选
```

不能保证：

```text
事实正确
逻辑正确
知识正确
```

如果模型最倾向的答案本身就是错的：

```text
低 temperature
```

可能只是：

```text
更稳定地答错
```

所以：

> **稳定性 ≠ 正确性。**

---

# 十一、temperature 越高是不是越好？

也不是。

太高可能导致：

```text
跑题
逻辑松散
结构不稳定
措辞奇怪
```

所以正确问题不是：

```text
temperature 多高最好？
```

而是：

```text
这个任务需要多稳定，还是需要多样？
```

---

# 十二、当前百炼 temperature

当前 OpenAI-compatible Chat API 中：

```text
temperature
```

范围是：

```text
[0, 2)
```

但这类：

```text
具体范围
默认值
```

属于：

```text
Provider / 模型实现细节
```

以后可能变化。

真正长期记住：

```text
低 → 稳定
高 → 多样
```

即可。

---

# 十三、什么是 top_p？

`top_p`：

```text
核采样
Nucleus Sampling
```

它也控制：

```text
生成多样性
```

但方式和 temperature 不一样。

---

# 十四、top_p 怎么工作？

假设候选 Token：

```text
A  0.50
B  0.25
C  0.10
D  0.08
E  0.04
F  0.03
```

如果：

```text
top_p = 0.8
```

从最高概率开始累加：

```text
A = 0.50
A+B = 0.75
A+B+C = 0.85
```

达到：

```text
0.8
```

以后，候选集合大致就确定为：

```text
A
B
C
```

模型再从这些候选中采样。

---

# 十五、top_p 高低怎么理解？

```text
top_p 较低
→ 候选范围小
→ 更集中
→ 更稳定

top_p 较高
→ 候选范围大
→ 更多候选能参与
→ 更多样
```

---

# 十六、temperature 和 top_p 有什么区别？

粗略理解：

```text
temperature
=
改变整个概率分布有多“平”

top_p
=
决定哪些高概率候选有资格进入采样池
```

两者最终都可以影响：

```text
输出多样性
```

---

# 十七、temperature 和 top_p 要一起调吗？

通常：

```text
不建议
```

百炼当前官方文档也建议：

```text
通常只设置其中一个
```

原因很简单：

```text
两者都改变采样行为
```

如果同时改：

```text
temperature
+
top_p
```

结果变化以后，你很难知道：

```text
究竟是谁造成的
```

所以学习和实验都遵循：

> **一次只改变一个主要变量。**

---

# 十八、我们现在优先理解哪个？

我建议：

```text
temperature
```

先建立直觉。

`top_p` 当前做到：

```text
知道原理
知道它也控制多样性
知道别和 temperature 一起乱调
```

就够了。

---

# 十九、什么是 max output？

模型不能：

```text
无限输出
```

所以 API 会提供：

```text
输出 Token 上限
```

以前经常看到：

```text
max_tokens
```

但当前百炼 OpenAI-compatible Chat API 已经把：

```text
max_tokens
```

标记为：

```text
即将废弃
```

新接入优先理解：

```text
max_completion_tokens
```

---

# 二十、max_completion_tokens 是什么？

它控制：

```text
模型完整输出允许使用的最大 Token 数
```

对于支持思考的模型：

```text
完整输出
```

可能包括：

```text
推理 Token
+
最终回答 Token
```

所以可以理解成：

> **这次模型最多允许使用多少输出 Token。**

---

# 二十一、为什么需要输出上限？

可能为了：

```text
控制成本
控制延迟
防止回答过长
限制接口输出范围
避免任务失控
```

例如业务只需要：

```text
一个简短分类
```

就没必要给它：

```text
巨大的输出空间
```

---

# 二十二、达到上限会发生什么？

如果模型还没自然结束：

```text
但输出 Token 已达到上限
```

生成会提前停止。

这时：

```text
finish_reason
```

可能是：

```text
length
```

而不是：

```text
stop
```

---

# 二十三、为什么 finish_reason=length 很重要？

例如模型输出：

```text
这段代码有三个问题：

1. 空指针……
2. 并发问题……
3.
```

突然结束。

这可能不是：

```text
模型觉得回答完成
```

而是：

```text
输出预算被截断
```

所以：

```text
finish_reason = length
```

应该让你想到：

```text
输出上限
```

---

# 二十四、max_completion_tokens 越大越好吗？

不是。

它只是：

```text
最大允许值
```

不是：

```text
质量参数
```

把它调得很大：

```text
不会自动让回答更聪明
```

只是允许：

```text
模型最多输出更多内容
```

---

# 二十五、当前 qwen3.8-max 最大输出

当前官方模型信息显示：

```text
最大输出长度：
131072 Token
```

但是：

```text
模型最大能力
≠
每个业务都应该用满
```

真实设置应该根据：

```text
任务需要
```

决定。

---

# 二十六、max_tokens 和 max_completion_tokens 怎么记？

当前学习路线直接记：

```text
max_tokens
→ 旧参数方向
→ 百炼当前已标记即将废弃

max_completion_tokens
→ 新接入优先使用
```

后面的代码如果需要：

```text
限制输出
```

优先考虑：

```text
max_completion_tokens
```

---

# 二十七、什么是 seed？

`seed`：

```text
随机数种子
```

主要用于：

```text
提高相同请求的可复现性
```

例如：

```json
{
  "seed": 1234
}
```

它的意思不是：

```text
输出编号 1234
```

而是：

```text
给随机采样过程指定一个种子
```

---

# 二十八、seed 怎么理解？

同一个：

```text
Prompt
Model
Parameters
```

如果随机因素存在：

```text
每次结果可能变化
```

固定 seed：

```text
希望每次随机过程更接近
```

因此结果：

```text
更容易复现
```

---

# 二十九、seed 能保证 100% 一样吗？

不能。

当前官方描述是：

```text
尽可能返回相同结果
```

而不是：

```text
绝对一致
```

因为仍可能受到：

```text
模型版本
服务端实现
推理环境
Provider 更新
```

等因素影响。

所以：

> **seed 提高可复现性，但不提供绝对确定性保证。**

---

# 三十、seed 最适合什么场景？

例如：

```text
Prompt A/B
参数实验
回归测试
调试
减少随机干扰
```

比如你比较：

```text
Prompt A
vs
Prompt B
```

如果每次随机性都很大：

```text
很难判断变化来自 Prompt
还是随机采样
```

固定 seed 可以尽量减少一个变量。

---

# 三十一、seed 会提高正确率吗？

不会。

seed 解决：

```text
复现
```

不是：

```text
正确
```

它可能：

```text
让一个好答案更容易重复
```

也可能：

```text
让一个坏答案更容易重复
```

---

# 三十二、什么是 reasoning_effort？

`reasoning_effort`：

```text
推理力度
```

可以理解成：

> **这次任务，模型应该投入多少推理资源。**

它和：

```text
temperature
```

完全不是同一种参数。

---

# 三十三、temperature 和 reasoning_effort 的区别

```text
temperature
→ 控制采样多样性

reasoning_effort
→ 控制推理投入
```

例如：

```text
创意故事
```

更可能关心：

```text
temperature
```

而：

```text
复杂 Java 并发 Bug 分析
```

更可能关心：

```text
reasoning_effort
```

---

# 三十四、当前 qwen3.8-max 的 reasoning_effort

当前百炼 Chat Completions 中：

```text
qwen3.8-max
```

主要直接支持：

```text
low
medium
xhigh
```

默认：

```text
xhigh
```

还有兼容映射：

```text
minimal → low
high → xhigh
max → xhigh
```

而：

```text
none
```

表示：

```text
关闭思考模式
```

---

# 三十五、为什么我们之前一直使用 none？

之前很多实验研究的是：

```text
Message
System Prompt
Prompt
Structured Output
Streaming
```

我们希望：

```text
减少额外变量
减少推理 Token
减少等待
```

所以显式使用：

```json
"reasoning_effort": "none"
```

不是因为：

```text
none 永远最好
```

而是：

```text
那些实验根本不需要复杂推理
```

---

# 三十六、low / medium / xhigh 怎么理解？

不要先背具体 Token。

先记：

```text
low
→ 轻量推理

medium
→ 中等推理

xhigh
→ 更高推理投入
```

提高推理投入可能带来：

```text
更好的复杂问题处理能力
```

同时通常意味着：

```text
更多 Token
更高延迟
更高成本
```

---

# 三十七、什么任务更值得高 reasoning effort？

例如：

```text
复杂代码分析
多约束规划
数学问题
难 Bug 定位
复杂逻辑推理
需要综合很多条件的判断
```

---

# 三十八、什么任务没必要一直高 reasoning effort？

例如：

```text
简单分类
字段抽取
格式转换
固定模板
改写一句话
简单摘要
```

如果任务很简单：

```text
更高推理
```

可能只是：

```text
更慢
更贵
```

而提升不明显。

---

# 三十九、reasoning_effort 越高越好吗？

不一定。

核心原则：

> **推理资源应该和任务难度匹配。**

简单任务：

```text
不需要烧很多推理 Token
```

复杂任务：

```text
才值得给更多推理空间
```

---

# 四十、reasoning_effort 和 thinking_budget

百炼当前 qwen3.8-max 还支持：

```text
thinking_budget
```

可以理解为：

```text
更直接地控制思考 Token Budget
```

而：

```text
reasoning_effort
```

是：

```text
档位式控制
```

当前两者会互相映射。

---

# 四十一、这两个一起设置吗？

不要。

当前官方明确：

```text
qwen3.8-max
不支持 reasoning_effort
和 thinking_budget
同时设置
```

同时传：

```text
会报错
```

所以当前学习阶段：

```text
先使用 reasoning_effort
```

就够了。

---

# 四十二、为什么不深入 thinking_budget？

因为：

```text
low / medium / xhigh
```

已经足够表达：

```text
任务需要多少推理力度
```

具体 Token Budget 属于：

```text
更精细的性能 / 成本调优
```

现在没必要。

---

# 四十三、什么是 stop？

`stop`：

```text
停止序列
```

它表示：

> **如果模型生成到指定内容，就停止继续生成。**

例如：

```json
{
  "stop": ["### END"]
}
```

模型遇到：

```text
### END
```

就会终止生成。

---

# 四十四、stop 和 max_completion_tokens 的区别

```text
stop
→ 遇到指定内容停止

max_completion_tokens
→ 达到 Token 上限停止
```

一个属于：

```text
内容条件
```

一个属于：

```text
资源上限
```

---

# 四十五、这几个参数到底各管什么？

把它们压缩成一张图：

```text
temperature
→ 随机性 / 多样性

top_p
→ 候选 Token 范围 / 多样性

max_completion_tokens
→ 最大输出资源

seed
→ 可复现性

reasoning_effort
→ 推理投入

stop
→ 停止条件
```

这张图比：

```text
背几十个具体数字
```

重要得多。

---

# 四十六、几个典型错误理解

错误：

```text
temperature 低
→ 更聪明
```

实际：

```text
更稳定
```

错误：

```text
reasoning_effort 高
→ 更有创意
```

实际：

```text
投入更多推理
```

错误：

```text
seed 固定
→ 更正确
```

实际：

```text
更容易复现
```

错误：

```text
max_completion_tokens 大
→ 质量更高
```

实际：

```text
只是允许输出更多
```

---

# 四十七、参数不能代替 Prompt

如果 Prompt 写：

```text
帮我分析一下
```

需求本身很模糊。

即使：

```text
temperature = 0.1
```

也不能自动让：

```text
任务要求变清楚
```

很多时候：

```text
先写清 Prompt / Context
```

比：

```text
乱调参数
```

更重要。

---

# 四十八、参数不能代替 JSON Schema

如果你需要：

```text
必须返回：
riskLevel
reason
suggestion
```

应该使用：

```text
JSON Schema
```

而不是：

```text
把 temperature 调低
```

因为：

```text
稳定
≠
结构契约
```

---

# 四十九、参数和 Structured Output 的关系

Structured Output：

```text
规定结果结构
```

参数：

```text
影响生成过程
```

例如：

```text
riskLevel 只能 HIGH / MEDIUM / LOW
```

应该通过：

```text
Schema enum
```

控制。

不是通过：

```text
temperature
```

控制。

---

# 五十、参数和 Evaluation 的关系

真正调参数时：

```text
不能只凭感觉
```

例如：

```text
0.2 好像不错
0.5 好像也可以
```

如果没有：

```text
固定 Case
指标
评估方法
```

很难判断哪个真的更好。

以后 Evaluation 会做：

# 七十九、口述验收

如果有人问：

> LLM 模型参数到底在控制什么？

你应该能解释：

> 模型参数主要控制生成过程，而不是直接改变模型知识或智商。temperature 和 top_p 控制采样多样性；max_completion_tokens 控制输出预算；seed 用于提高可复现性；reasoning_effort 控制模型投入多少推理资源；stop 则定义内容停止条件。
>
> 参数没有统一的“越大越好”。低 temperature 往往更稳定，但不代表更正确；高 reasoning effort 可能帮助复杂任务，但也可能带来更多延迟和 Token。真实工程应该先使用合理默认值，只有遇到明确业务问题时再调整，而且一次尽量只改一个变量，最后通过真实 Case 和 Evaluation 判断效果。

如果能讲清：

```text

输出预算
可复现性
推理投入
停止条件
```

这一节核心理论就建立好了。

# 03 - LLM 幻觉到底是什么？

> AI Agent 学习笔记 · LLM 基础
>
> 前两篇解决了：
>
> ```text
> 01：LLM 到底是什么？
> 02：模型训练与推理到底是什么？
> ```
>
> 现在已经知道：
>
> ```text
> 用户输入
>     ↓
> 已经训练好的模型
>     ↓
> Inference
>     ↓
> 生成 Token
>     ↓
> 最终回答
> ```
>
> 这一篇要解决一个非常重要的问题：
>
> > **模型生成出来的东西，看起来那么像真的，它就一定是真的吗？**
>
> 答案：
>
> **不一定。**
>
> 而这正是所有生产级 AI 系统都必须面对的问题之一：
>
> ```text
> Hallucination
> ```
>
> 中文通常叫：
>
> **LLM 幻觉。**

------

# 一、什么是 LLM 幻觉？

最简单的理解：

> **模型生成了看起来合理、甚至非常自信，但实际上错误、虚构或没有依据的内容。**

例如你问：

```text
《Java并发编程艺术》第 19 章主要讲什么？
```

假设这本书根本没有第 19 章。

模型却回答：

```text
第19章主要介绍分布式并发控制，
其中重点讨论了 RedLock、Raft 和……
```

甚至：

```text
19.3.2 节中作者进一步指出……
```

听起来特别像真的。

但：

```text
根本不存在。
```

这就是非常典型的：

> **Hallucination**

------

# 二、幻觉最危险的地方是什么？

不是：

```text
“模型回答错了。”
```

单纯答错其实没那么可怕。

最危险的是：

> **它可能用非常自然、流畅、专业、自信的语言回答错。**

例如：

```text
错误答案 A：

我不知道。
```

其实很好处理。

而：

```text
错误答案 B：

根据 Java Language Specification 第 18.7.4 节，
volatile 可以保证复合操作的原子性……
```

看起来：

```text
有官方文档
有章节号
有专业术语
有明确结论
```

但是：

> 内容是假的。

这种才最危险。

因为人的直觉非常容易：

```text
语言专业
+
表达流畅
+
语气自信
=
应该是真的
```

但对于 LLM 来说：

```text
说得像真的
```

和：

```text
真的是真的
```

完全是两件事。

------

# 三、最重要的一句话

必须记住：

> **Language Plausibility ≠ Factual Truth**

可以理解成：

```text
语言上合理
≠
事实为真
```

LLM 非常擅长第一件事：

```text
生成符合语言规律的内容
```

但是：

```text
事实真实性
```

并不是仅靠语言生成就天然能够保证的。

------

# 四、为什么会这样？

回到第一篇。

LLM 的核心生成过程可以简化为：

```text
已有 Context
      ↓
模型计算
      ↓
预测下一个 Token
      ↓
继续预测
      ↓
形成回答
```

模型真正擅长的是：

> 根据当前上下文和已经学习到的模式，生成一个合理的后续。

注意关键词：

```text
合理
```

不是：

```text
经过数据库验证为真实
```

也不是：

```text
经过互联网实时核验
```

更不是：

```text
经过业务系统确认
```

------

# 五、举一个特别简单的例子

假设训练数据中有大量句子：

```text
《Effective Java》的作者是 Joshua Bloch。
```

那么问：

```text
《Effective Java》的作者是谁？
```

模型大概率可以回答：

```text
Joshua Bloch
```

因为这个关系在训练过程中被模型学得非常稳定。

------

但是突然问：

```text
《Effective Java》第四版第 127 条讲什么？
```

假设当前实际上并不存在这样一个对应内容。

模型面对这个问题有几种可能：

```text
① 说不知道

② 指出问题前提有误

③ 猜一个很像 Effective Java 的内容

④ 虚构一个条目
```

如果模型选择了：

```text
④
```

你就看到了幻觉。

------

# 六、为什么模型不直接说“我不知道”？

这是非常关键的问题。

人类会想：

> 不知道为什么不说不知道？

但模型和人不完全一样。

模型首先在完成的任务是：

```text
根据当前 Context
生成接下来最合适的内容
```

如果上下文强烈暗示：

```text
“这里应该有一个答案”
```

模型就可能继续生成一个：

```text
像答案的东西。
```

尤其当用户问：

```text
请详细解释……
```

模型更容易倾向于：

```text
生成解释
```

而不是：

```text
沉默
```

------

# 七、模型并没有一个绝对可靠的“事实数据库”

这是前面为什么一直强调：

> **LLM ≠ Database**

数据库：

```text
Key / Row / Record
        ↓
精确查询
        ↓
真实存储的数据
```

例如：

```sql
SELECT budget
FROM campaign
WHERE id = 123;
```

数据库里是：

```text
5000
```

那么返回：

```text
5000
```

------

LLM 不是：

```text
SELECT fact
FROM model
WHERE question = ?
```

模型知识更像：

```text
大量概念
大量关系
大量模式
↓
分布式编码在 Parameters 中
```

所以：

> **模型“知道一件事”并不像数据库“保存一条记录”。**

------

# 八、Knowledge ≠ Truth 是什么意思？

这是这一篇非常重要的一句话：

> **Knowledge ≠ Truth**

可以翻译成：

```text
模型拥有某种知识
≠
模型说出来的每句话都是真理
```

比如模型确实学过：

```text
Java
JVM
HashMap
ThreadLocal
```

不代表它每次回答：

```text
Java 问题
```

都会百分之百正确。

------

为什么？

因为最终回答还受到：

```text
Prompt
Context
问题表达
模型能力
采样
推理过程
知识是否完整
知识是否过时
```

等因素影响。

所以：

```text
模型具有相关知识
```

只能说明：

> 它有机会答对。

不等于：

> 它一定答对。

------

# 九、一个特别重要的区别：Knowledge 和 Retrieval

假设模型“知道”：

```text
HashMap 线程不安全
```

这个知识可能存在于：

```text
Parameters
```

但是当用户提出复杂问题时：

```text
模型是否能在当前推理中正确利用这个知识？
```

又是另一个问题。

因此可能出现：

```text
模型其实学过
↓
但这一轮没有正确调用相关知识
↓
答错
```

这也是为什么不能简单理解为：

```text
“模型训练数据里有，所以一定会答对。”
```

------

# 十、幻觉不只是“凭空编故事”

很多人以为 Hallucination 只有一种：

```text
模型编造一个不存在的事实
```

其实范围更广。

至少可以分成几类。

------

# 十一、第一类：事实幻觉

最容易理解。

模型说：

```text
Java 由微软在 1998 年发布。
```

这是：

```text
事实错误
```

模型把：

```text
错误事实
```

当成：

```text
真实事实
```

输出。

------

# 十二、第二类：虚构实体

例如：

```text
Spring Boot 提供了 @AutoRedisLock 注解，
可以直接实现 Redis 分布式锁。
```

听起来特别像 Spring：

```text
@Controller
@Service
@Transactional
@Async
```

所以：

```text
@AutoRedisLock
```

听起来也非常合理。

但它可能：

```text
根本不存在。
```

这种在程序员使用 AI 时特别常见：

```text
不存在的类
不存在的方法
不存在的 Maven 依赖
不存在的配置项
不存在的注解
不存在的版本
```

------

# 十三、第三类：虚构引用

例如模型说：

```text
根据 Spring 官方文档第 7.4 节……
```

或者：

```text
根据某篇论文……
```

然后：

```text
论文不存在
```

或者：

```text
论文是真的，
但根本没有说那句话。
```

甚至：

```text
作者是真的
论文题目像真的
年份也像真的
```

组合起来却是假的。

------

# 十四、第四类：错误归因

资料是真实的。

内容也可能真实。

但是模型说：

```text
这句话是 Martin Fowler 提出的。
```

实际上：

```text
不是。
```

这种叫：

```text
错误 Attribution
```

也属于事实可靠性问题。

------

# 十五、第五类：错误数字

这个对业务系统特别危险。

用户：

```text
campaign 123 今天花了多少钱？
```

模型没有数据库权限。

却回答：

```text
今天消耗约 5321 元。
```

数字：

```text
看起来特别真实。
```

甚至不是：

```text
5000
```

而是：

```text
5321.47
```

越精确，人越容易相信。

但：

```text
可能完全是生成出来的。
```

------

# 十六、精确不等于真实

这是一定要形成的直觉。

例如：

```text
2026 年 3 月 17 日 14:32
```

比：

```text
去年三月份
```

看起来更可信。

但对模型而言：

```text
精确的日期
精确的小数
精确的章节
精确的 API 名称
```

全部都可以：

> **被生成出来。**

所以：

> **Specific ≠ Verified**

即：

```text
具体
≠
经过验证
```

------

# 十七、第六类：推理幻觉 / 推理错误

模型拿到的事实都是真的。

但是推导过程错了。

比如：

```text
Campaign A：
100 个转化
花费 1000

Campaign B：
10 个转化
花费 500
```

模型说：

```text
B 的 CPA 更低。
```

实际上：

```text
A CPA = 10
B CPA = 50
```

这里不是：

```text
事实不存在
```

而是：

```text
推理出了错误结论。
```

在广义讨论中，这也常被放进 LLM 不可靠输出的问题里。

------

# 十八、第七类：Context 不忠实

这是做 RAG 后特别重要的一类。

假设检索出来的公司规定明确写着：

```text
预算超过 10000 元时，需要主管审批。
```

用户问：

```text
预算改成 20000，需要审批吗？
```

模型回答：

```text
不需要审批。
```

这时候：

```text
正确资料已经给它了
```

但模型：

```text
没有忠实依据资料回答。
```

这种问题常讨论为：

```text
Faithfulness
```

也就是：

> **回答是否忠实于提供的 Context。**

------

# 十九、Factuality 和 Faithfulness

以后做 RAG Evaluation 时会经常碰到。

可以先简单区分。

## Factuality

回答：

> **是不是事实正确？**

例如：

```text
北京是中国首都。
```

事实正确。

------

## Faithfulness

回答：

> **是不是忠实依据我们提供的资料？**

例如 Context：

```text
预算超过10000需要审批。
```

模型却说：

```text
预算超过10000不需要审批。
```

这是明显：

```text
不忠实于 Context
```

------

两者相关，但不完全一样。

------

# 二十、为什么 LLM 会出现幻觉？

不能只用一句：

```text
因为它会预测 Token。
```

这还不够。

真正原因有很多。

------

# 二十一、原因 1：模型目标不是“事实验证器”

LLM 的训练目标之一是让生成：

```text
更符合语言规律
```

但是：

```text
语言规律
```

和：

```text
事实验证
```

不是一回事。

模型并不会每生成一句：

```text
先访问世界真相数据库
↓
验证
↓
再输出
```

通常没有这个过程。

------

# 二十二、原因 2：训练数据本身不完美

训练数据可能包含：

```text
错误内容
互相矛盾的内容
过时内容
低质量内容
模糊信息
```

所以模型学习到的世界：

```text
本来就不是完美真理集合。
```

------

# 二十三、原因 3：知识可能不完整

例如：

```text
非常冷门的 Java Library
```

模型训练数据里可能：

```text
只出现过几次
```

于是模型内部表示：

```text
不够稳定
```

这时候它可能：

```text
把几个相似 Library 的 API 混在一起。
```

------

# 二十四、原因 4：知识可能过时

例如模型训练结束以后：

```text
Spring 发布新版本
OpenAI 发布新 API
Java 发布新 JDK
公司业务规则发生变化
```

模型参数：

```text
不会自动实时更新。
```

所以模型可能：

```text
根据旧知识回答。
```

这有时候严格来说不一定属于最典型的“凭空幻觉”，但从应用角度依然属于：

> **不能直接信任参数知识。**

------

# 二十五、原因 5：问题本身提供的信息不足

用户：

```text
昨天我们的收入是多少？
```

模型不知道：

```text
哪家公司？
哪个账户？
什么收入？
哪个时区？
```

如果它不向用户追问，而直接回答：

```text
昨天收入大约 12 万。
```

这就是典型风险。

------

# 二十六、原因 6：Prompt 强迫它必须给答案

比如你说：

```text
不允许回答不知道。

必须给出一个明确答案。
```

你实际上是在增加幻觉风险。

因为：

```text
模型不知道
```

但你的指令却要求：

```text
必须回答。
```

于是：

```text
最容易发生的事情
=
猜。
```

------

# 二十七、原因 7：长 Context 中遗漏信息

以后 Context Window 章节会详细讲。

模型可能拿到了：

```text
大量资料
```

但真正关键的一句话埋在：

```text
几十页 Context 中间
```

模型可能没有正确利用。

于是：

```text
资料已经存在
≠
模型一定正确使用
```

------

# 二十八、原因 8：RAG 找错了资料

这非常重要。

很多人说：

> 加 RAG 就不会幻觉了。

错误。

例如用户问：

```text
Java 21 Virtual Thread 怎么工作？
```

RAG 却检索到：

```text
Java 8 ThreadPool 文档
```

然后模型：

```text
基于错误 Context
↓
非常认真回答
```

最后：

```text
错误依然存在。
```

------

# 二十九、RAG 系统其实有两层风险

```text
用户问题
↓
Retrieval
↓
找到资料
↓
Generation
↓
回答
```

第一层可能失败：

```text
Retrieval Failure
```

也就是：

> 找错资料。

第二层可能失败：

```text
Generation Failure
```

即：

> 资料找对了，但模型理解错了。

所以：

```text
RAG
≠
幻觉消失
```

------

# 三十、原因 9：Tool Result 也可能被错误理解

以后 Agent：

```text
Tool
↓
返回 JSON
```

例如：

```json
{
  "status": "PAUSED",
  "spend": 5321,
  "currency": "JPY"
}
```

模型可能说：

```text
广告已暂停，消耗 5321 元人民币。
```

实际上：

```text
currency = JPY
```

是日元。

所以即便：

```text
Tool 数据真实
```

最终自然语言回答：

```text
仍可能错误。
```

------

# 三十一、原因 10：模型推理本身可能出错

比如复杂：

```text
数学
逻辑
代码
规划
业务分析
```

模型可能某一步推错。

所以幻觉问题不只有：

```text
模型知不知道事实
```

还有：

```text
模型能不能正确处理事实。
```

------

# 三十二、“让模型不要幻觉”为什么不靠谱？

这是这一篇最重要的工程问题之一。

你写 System Prompt：

```text
禁止产生任何幻觉。
任何内容必须100%正确。
```

有帮助吗？

可能：

```text
有一点。
```

能彻底解决吗？

```text
不能。
```

------

# 三十三、为什么？

因为 Prompt 只是在：

```text
影响模型行为
```

它没有给模型新增：

```text
真实数据库
实时搜索
内部公司资料
事实验证系统
```

例如模型不知道：

```text
campaign 123 今日消耗
```

你再怎么写：

```text
禁止胡说！
必须100%准确！
请务必确保事实！
```

它依然：

> 没有真实数据。

------

# 三十四、Java 类比一下

假设方法：

```java
public Campaign getCampaign(Long id) {
    // 根本没有数据库连接
}
```

你在注释里写：

```java
/**
 * 请务必返回数据库中100%真实的 Campaign。
 * 禁止编造。
 */
```

😂

有用吗？

当然没用。

因为：

```text
你没有 Data Source。
```

LLM 也是一样。

------

# 三十五、解决幻觉的第一原则

> **不要只靠模型自己“更认真”。**

而应该：

> **给模型提供可以依赖的真实信息来源。**

这就引出了一个非常重要的概念：

```text
Grounding
```

------

# 三十六、什么是 Grounding？

```
Grounding
```

在 LLM 应用里可以先理解成：

> **让模型的回答建立在某些外部、明确、可验证的信息依据上。**

中文可以理解：

```text
给回答找“地基”
```

------

没有 Grounding：

```text
用户
↓
LLM 参数知识
↓
回答
```

模型主要依赖：

```text
自己训练时学到的内容
```

------

有 Grounding：

```text
用户
↓
真实资料 / 数据
↓
提供给 LLM
↓
LLM 根据这些资料回答
```

------

# 三十七、Grounding 来源有哪些？

很多。

例如：

```text
数据库
Tool API
RAG 文档
Web Search
业务服务
用户明确提供的数据
```

------

# 三十八、数据库 Grounding

用户：

```text
campaign 123 今天花多少钱？
```

不要：

```text
LLM 猜。
```

而是：

```text
LLM
↓
queryCampaignMetrics
↓
MySQL / Ads API
↓
5321 CNY
↓
LLM
↓
回答
```

这就是：

> 用真实业务数据 Ground 模型回答。

------

# 三十九、RAG Grounding

用户：

```text
按照公司规范，这种广告应该暂停吗？
```

流程：

```text
问题
↓
搜索公司规范
↓
找到真实规定
↓
提供给模型
↓
模型依据规定回答
```

这也是：

```text
Grounding
```

------

# 四十、Web Search Grounding

用户：

```text
Spring AI 最新版支持什么？
```

参数知识可能：

```text
已经过时。
```

于是：

```text
Search 官方文档
↓
得到当前资料
↓
LLM 阅读
↓
回答
```

也是 Grounding。

------

# 四十一、Grounding ≠ 100% 不会错

非常重要。

例如：

```text
真实数据库数据
↓
LLM
```

模型依然可能：

```text
看错字段
算错
理解错
漏掉条件
```

所以：

```text
Grounding
```

更准确应该理解为：

> **显著提高回答有依据、可核验和事实可靠性的能力。**

而不是：

> 绝对消灭所有错误。

------

# 四十二、Tool Calling 为什么能降低幻觉？

没有 Tool：

```text
用户：
订单 123 什么状态？

LLM：
应该已经发货了。
```

纯猜。

------

有 Tool：

```text
LLM
↓
queryOrder(123)
↓
{
  "status": "PAID"
}
↓
LLM
↓
订单已经付款，但还没有发货。
```

这时候事实基础明显变强。

------

# 四十三、但是为什么 Tool Calling 仍然不是完美的？

因为还有：

```text
调用错 Tool
参数传错
Tool 返回错误
Tool 数据过期
模型理解结果错误
```

例如模型应该：

```text
queryCampaign(123)
```

却调用：

```text
queryCampaign(321)
```

那后面说得再专业：

```text
都是错误基础上的分析。
```

------

# 四十四、RAG 为什么能降低幻觉？

模型不知道内部知识：

```text
公司广告规范
```

RAG 可以：

```text
检索
↓
获取真实文档
↓
放进 Context
```

于是模型不用：

```text
依靠模糊参数知识猜
```

而可以：

```text
依据明确资料回答。
```

------

# 四十五、但 RAG 也不能保证没幻觉

可能：

```text
Chunk 切坏了
Embedding 检索错了
TopK 没召回真正答案
文档本身过期
模型看到了文档却理解错了
```

所以生产 RAG 后面一定会学习：

```text
Retrieval Evaluation
+
Answer Evaluation
```

------

# 四十六、为什么需要 Source Citation？

如果模型回答：

```text
根据公司规定，预算超过 10000 元需要审批。
```

最好还能够告诉用户：

```text
来源：
《广告预算管理规范》
第 3.2 节
```

这样用户可以：

```text
自己检查
```

而不是：

```text
只能相信模型。
```

所以：

```text
Source Citation
```

本身也是建立可信 AI 系统的重要能力。

------

# 四十七、生产系统里应该相信谁？

这是一个非常重要的工程优先级。

例如：

```text
LLM说：
Campaign预算 = 10000

数据库说：
Campaign预算 = 8000
```

相信谁？

一般：

```text
数据库。
```

因为：

```text
数据库
=
业务事实来源
```

LLM：

```text
是解释、推理、生成层。
```

------

# 四十八、什么叫 Source of Truth？

以后工程里会经常遇到这个概念。

```
Source of Truth
```

就是：

> **某类数据最终应该以谁为准。**

比如：

```text
订单状态
→ Order Database
广告消耗
→ Ads Platform API / 数据仓库
公司规章
→ 当前正式发布的公司规范
账户余额
→ Financial System
```

而不是：

```text
LLM 记忆。
```

------

# 四十九、Agent 中非常重要的设计思想

以后我们应该设计：

```text
LLM
负责：
理解
规划
分析
解释

真实系统
负责：
事实
数据
权限
执行
```

而不是：

```text
LLM
=
万能事实数据库
+
业务数据库
+
权限系统
+
执行系统
```

------

# 五十、拿 Ads Agent 举一个完整例子

用户：

```text
帮我看看 campaign 123 今天是不是有问题。
```

------

## 错误实现

```text
用户
↓
LLM
↓
根据经验猜：
“今天 CPA 较高，可能素材疲劳。”
```

问题：

```text
根本没有今天的数据。
```

------

## 正确得多的实现

```text
用户
↓
LLM 判断需要数据
↓
queryTodayMetrics(123)
↓
真实业务数据
↓
querySevenDayAverage(123)
↓
历史数据
↓
RAG 查询内部异常规则
↓
LLM 综合分析
↓
输出结论
```

例如：

```text
今日 CPA：65
7日平均 CPA：38

主要变化：
CTR -3%
CPM +2%
CVR -39%

因此本次 CPA 上升主要与 CVR 下滑相关，
而不是流量成本明显上涨。
```

这种回答：

```text
有真实数据
有计算依据
有规则来源
```

可信度远高于：

```text
模型自由发挥。
```

------

# 五十一、甚至有些事情根本不应该让 LLM 算

例如：

```text
CPA = Spend / Conversion
```

如果：

```text
Java
```

可以精确计算：

```java
BigDecimal cpa =
    spend.divide(conversion, 2, RoundingMode.HALF_UP);
```

那很多情况下：

> 就应该 Java 算。

而不是：

```text
让 LLM 心算。
```

------

# 五十二、这是一个非常重要的 Agent 原则

> **确定性任务尽量交给确定性系统。**

例如：

```text
数学计算
数据库查询
权限判断
金额处理
状态变更
字段校验
```

传统代码通常更适合。

而 LLM 更适合：

```text
理解语言
判断意图
综合分析
解释结果
生成建议
```

------

# 五十三、幻觉和 Temperature 有关系吗？

有一定关系，但不能简单理解：

```text
temperature = 0
↓
没有幻觉
```

这是错误的。

降低随机性可能让输出：

```text
更稳定
```

但如果模型本身：

```text
不知道事实
```

它完全可能：

```text
非常稳定地答错。
```

例如每次都稳定输出同一个错误答案。

所以：

> **Deterministic ≠ Correct**

也就是：

```text
稳定
≠
正确
```

------

# 五十四、Structured Output 能解决幻觉吗？

也不能。

例如你要求：

```json
{
  "campaignId": 123,
  "spend": 5321
}
```

模型完全可以：

```text
严格输出合法 JSON
```

同时：

```text
spend = 5321
```

是编的。

所以：

```text
JSON Valid
≠
Fact Valid
```

这句话以后做 Agent 也很重要。

Structured Output 解决：

```text
程序能不能稳定解析
```

不是：

```text
内容事实一定正确。
```

------

# 五十五、模型说“我很确定”有用吗？

不能把它当可靠事实验证。

例如：

```text
我有 99% 的把握。
```

这句话本身：

```text
也只是模型生成的文本。
```

除非系统明确拥有经过设计和校准的置信度机制，否则：

```text
“我非常确定”
```

不应该直接理解成：

```text
真实概率 = 99%
```

------

# 五十六、那要求模型提供引用是不是就安全？

也不一定。

因为模型可能：

```text
伪造引用
```

所以引用必须来自：

```text
真实 Search Result
RAG Chunk
Database Record
Tool Result
```

应用程序应该保留：

```text
sourceId
documentId
URL
page
chunkId
```

而不是让模型：

```text
凭空生成一个引用。
```

------

# 五十七、幻觉能彻底消灭吗？

现实工程里，更合理的目标不是：

```text
绝对零幻觉
```

而是：

```text
降低发生概率
+
限制影响范围
+
让错误容易被发现
+
高风险任务必须验证
```

这其实和传统软件工程很像。

------

# 五十八、Java 系统也不是“永远不会错”

传统系统也会：

```text
Bug
数据库脏数据
网络超时
缓存不一致
第三方接口错误
```

我们并不会说：

```text
必须保证世界上永远不出错。
```

而是通过：

```text
Validation
Retry
Transaction
Monitoring
Test
Audit
```

降低风险。

AI 也一样。

只不过多了一类：

```text
概率性错误
```

------

# 五十九、工程上如何降低幻觉？

可以建立一个分层思路。

------

## 第一层：让模型允许说“不知道”

不要：

```text
必须回答。
```

可以明确：

```text
如果提供的信息不足，
不要猜测，
明确说明缺少哪些信息。
```

这可以降低部分：

```text
强行作答。
```

但：

> 不能单独依赖这一层。

------

## 第二层：Grounding

用：

```text
RAG
Web Search
Database
Tools
API
```

给真实信息。

这是最重要的一层之一。

------

## 第三层：限制任务边界

例如不要让模型：

```text
自己猜 Campaign 金额
```

Tool Schema 和 Prompt 明确：

```text
金额必须来自 queryMetrics。
```

------

## 第四层：程序验证

例如模型输出：

```json
{
  "campaignId": 123,
  "budget": -999999
}
```

Java：

```java
if (budget.compareTo(BigDecimal.ZERO) < 0) {
    throw new IllegalArgumentException();
}
```

不要：

```text
模型说什么就执行什么。
```

------

## 第五层：Source Citation

让回答：

```text
可追溯。
```

------

## 第六层：Evaluation

建立测试：

```text
问题
↓
正确答案
↓
模型答案
↓
比较
```

长期评估：

```text
事实准确率
Tool Accuracy
RAG Recall
Faithfulness
```

------

## 第七层：Human-in-the-loop

高风险任务：

```text
转账
删除数据
暂停大额 Campaign
修改预算
发送正式邮件
```

即使模型判断：

```text
应该执行
```

仍然：

```text
等待人确认。
```

------

# 六十、Hallucination 和 Agent 的关系

普通聊天幻觉：

```text
回答错了。
```

有时候用户发现以后：

```text
重新问。
```

风险还比较有限。

Agent 幻觉：

```text
模型错误判断
↓
调用 Tool
↓
真实世界发生变化
```

风险就完全不同了。

------

# 六十一、例如

模型幻觉：

```text
用户要求：
分析广告，不要修改。
```

模型却错误判断：

```text
需要暂停 Campaign。
```

然后：

```text
pauseCampaign(123)
```

如果 Agent 没有权限控制：

```text
真实业务已经被修改。
```

所以：

> **Agent 时代，幻觉不再只是“回答错误”，还可能变成“错误行动”。**

这也是为什么后面一定要学：

```text
Tool Permission
Human Approval
Guardrail
Audit
```

------

# 六十二、Read Tool 和 Write Tool 为什么风险不同？

以后会专门学习。

先建立一个直觉。

## Read Tool

```text
queryCampaign()
```

即使模型判断错：

```text
通常不会直接修改业务数据，
但仍可能越权查询、泄露敏感信息或产生额外成本。
```

因此 Read Tool 风险通常低于 Write Tool，但仍然需要权限和数据范围控制。

------

## Write Tool

```text
pauseCampaign()
deleteUser()
transferMoney()
```

模型一旦判断错：

```text
会真正修改世界。
```

所以：

```text
Write Tool
```

必须受到更严格控制。

------

# 六十三、为什么生产 AI 不能“相信模型”？

更准确地说：

不是：

```text
永远不相信。
```

而是：

> **根据任务风险决定信任程度。**

例如：

```text
帮用户把一段话润色一下
```

错误风险：

```text
低。
```

可以比较自由。

------

但是：

```text
患者应该吃多少药？
现在应该转多少钱？
是否删除生产数据库？
```

错误成本：

```text
极高。
```

必须加入更多：

```text
Grounding
Validation
Human Review
权限
规则
```

------

# 六十四、一个非常重要的工程公式

以后做 Agent 可以经常想：

```text

        ↓
灵活性 ↑
        ↓
不确定性通常也 ↑
```

而：

```text
确定性程序约束 ↑
        ↓
灵活性可能 ↓
        ↓
可靠性更容易控制
```

所以好的 Agent 往往不是：

```text
让模型决定一切
```

而是：

```text
该自由的地方自由
该确定的地方确定
```

# 六十五、LLM 最适合扮演什么角色？

例如：

适合。

适合。

应该：

应该：

```text

```

# 六十六、建立一个非常关键的思想

# 六十七、幻觉和“聪明”不是一个维度

# 六十八、模型升级也不能自动解决所有幻觉

------

# 六十九、以后 Debug Agent 时应该怎么想？

假设 Agent 回答错了。

不要简单写：

```text

```

然后结束。

应该沿调用链排查：

# 七十、一个错误答案可能根本不是模型的问题

> 根本不是 LLM Hallucination。


```text

```

# 七十一、我们以后为什么需要 Tracing？

# 七十六、Hallucination 和 Creativity 是什么关系？

带来的灵活性也是模型创造力来源之一。

写小说：


完全没问题。

甚至就是我们想要的。

例如：

```text

```

模型：

```text
疯狂编。
```

这时候不是 Bug。

而是 Feature。

------

# 七十七、所以“幻觉”取决于任务目标

如果任务是：

```text
写一个幻想故事
```

虚构：

```text

```

如果任务是：

```text

```

虚构：

```text
灾难。
```

所以真正问题不是：

```text
模型会不会创造。
```

而是：

> **在要求真实的场景里，它有没有无依据地创造事实。**

------

# 七十八、这也是为什么 System Prompt 需要明确任务边界

例如：

```text
你可以根据已提供的数据进行分析。

对于没有通过 Tool、Context 或知识库提供的业务事实，
不要自行猜测。

如果信息不足，请明确说明缺少哪些数据。
```

这比：

```text
禁止幻觉。
```

更具体。

但仍然记住：

> Prompt 只是第一道防线，不是最终保障。

# 八十、这一篇最核心的 12 句话

以后忘了整篇，只记这 12 条。

## 1

> **LLM 幻觉就是模型生成了错误、虚构或缺乏依据，却看起来合理的内容。**

## 2

> **语言流畅不等于事实正确。**

## 3

> **LLM 不是数据库，它没有一个可以保证精确查询事实的内部知识表。**

## 4

> **模型拥有相关 Knowledge，不意味着每次生成的答案都是真实 Truth。**

## 5

> **具体、专业、自信、带数字，都不能自动证明答案真实。**

## 6

> **一句“禁止幻觉”无法给模型创造它原本没有的真实信息。**

## 7

> **Grounding 的核心，是让模型的回答建立在真实、可验证的外部信息上。**

## 8

> **RAG、Tool、Search、Database 都可以成为 Grounding 来源。**

## 9

> **RAG 和 Tool 能降低幻觉，但不能保证绝对没有错误。**

## 10

> **确定性事实和业务操作应该尽量由确定性程序负责，而不是让模型自由猜。**

## 11

> **Agent 中的幻觉比普通聊天更危险，因为错误判断可能进一步触发真实 Tool 行动。**

## 12

> **生产级 Agent 的目标不是幻想“零错误”，而是通过 Grounding、Validation、Eval、权限和人工审批控制错误。**
